## 一、一句话结论

Tiptap/ProseMirror 与 Lexical 两个内核都通过了**全部关键验收项**。后续独立「编辑器迁移」change 建议**优先采用 Tiptap/ProseMirror**，Lexical 保留为备选。两者功能验收均合格；Tiptap 在 20 万字真机测试中输入延迟略低，且 ProseMirror 的选区映射机制更成熟。

这个结论**只决定后续 change 的优先候选**，不代表当前生产编辑器已经迁移。当前生产编辑器仍是两个原生 `textarea`；本次原型没有修改生产 `src/`，也没有把 Tiptap 或 Lexical 加入生产依赖。

## 二、这次验证做了什么、没做什么

### 做了

- 在一个**隔离原型** `prototype/editor-kernel/` 里，把 Tiptap/ProseMirror 和 Lexical 两个内核做进同一个 Tauri 2 桌面外壳。
- 两内核共用同一套 `src/` 适配层：**纯文本投影 + 冻结选区快照 + AI 不写回**。
- 用同一套验收标准，对两候选做二元判定（通过/失败）+ 双证据（自动化红转绿 + 真机操作实录）。
- 在真实的 Windows + WebView2 + 微软拼音环境里人工实敲验证中文输入法与长文档压力。
- 打包成真实的 Tauri 分发包（MSI/NSIS/exe）并确认 WebView2 实际运行。
- 静态审查两候选及其分发依赖的开源许可。

### 没做（明确的边界）

- **没有替换生产编辑器**。生产端全程是两个 `textarea`，`src/` 未动一行。
- **没有引入生产依赖**。Tiptap/Lexical 只存在于隔离原型，未进入主 `package.json`。
- **没有做富文本功能、DOCX 导入导出、AI 写回、背景上下文、临时对话持久化**——这些都被明确排除，不作为附带迁移工作。
- **没有做最终选型定案**。本报告是后续迁移 change 的输入，真正落地必须另开 change 并经用户确认。

### 撤销粒度差异（非缺陷，记录备迁移参考）

Tiptap（ProseMirror）默认按输入事务分组，一次 Ctrl+Z 撤销本次输入的整批字符；Lexical 默认粒度更细，逐字符撤销。两者撤销/重做均正确，仅手感不同。后续迁移时可通过配置调整撤销分组策略，**不构成任一候选的否决项**。

## 八、回滚决策规则与最终选型

真机三项（4.4 / 4.5 / 5.1）完成后，按以下规则判定，**不得强行选型**：

1. **存在通过全部关键项的候选** → 给出选型建议。若两者都通过全部关键项，用重要项（4.2/4.3/4.5/5.2）与工程成本、ProseMirror 选区映射成熟度打破平局，Tiptap 为默认优先，但须以真机 4.4/4.5 数据为准。
2. **只有一个候选通过全部关键项** → 直接建议该候选。
3. **两候选都在关键项失败** → 记录「暂缓迁移」，回到运行时/方案讨论，原型可整体删除。禁止在关键项失败时强行选定。

### 实际落点：规则 1（两者均通过全部关键项）

- 自动化关键逻辑：两候选均通过，同构成立。
- Windows + 微软拼音真机：两候选组合输入、选字、转换、删除、撤销/重做、切焦点均通过。
- 20 万字压力：两候选均低于 p95 50ms 与增量内存 300MB 预算；Tiptap p95 13.2ms，Lexical p95 19.7ms，堆增量均约 14.6MB。
- Tauri 2 分发构建与 WebView2 桌面运行均通过；许可无否决项。

**选型建议：后续迁移 change 优先采用 Tiptap/ProseMirror，Lexical 保留为备选。**

打破平局的依据：Tiptap 实测输入延迟略低；ProseMirror 提供更成熟的选区映射原语（`SelectionBookmark`、`Mapping`、`StepMap`、`coordsAtPos`），对「冻结选区在编辑后如何找回」这一最高风险点更有基础。撤销粒度差异属于可配置体验差异，不构成 Lexical 缺陷。

## 九、纸面研究阶段留下的未决风险（已由真机验证覆盖）

真机验证之前的桌面调研（记录在 `.omo/ulw-research/20260810-214721/`）曾标记三个「纸面无法证明、只能真机验证」的高风险项。本次真机验证正是为回答它们而做，结果如下：

| 纸面阶段的未决风险 | 真机验证结果 |
| --- | --- |
| WebView2 下中文 IME 是否丢字/重复（WebView2 #5625、Tauri #15436） | 微软拼音真机实敲，两候选全通过，无丢字/重复/乱序 |
| 真实剧本长度的输入/选区/撤销/保存重开表现 | 20 万字真机，两候选 p95 均达标，无文本损坏或选区漂移 |
| 冻结选区在编辑后能否恢复 | 自动化 + 真机复核，可确定性恢复或明确报告原位置已变 |

纸面研究同时确认的架构事实：当前编辑器是端到端纯文本系统（两个 `.txt` 是保存事实源，保存/读取不做归一化，空本子保持空串，脏状态比较字符串，选区快照用 UTF-16 偏移）。块树编辑器会重新打开持久化、选区、几何、脏状态、大小限制、空白与空文档语义——因此必须先有一个新 OpenSpec change 才能动代码。

## 十、决策边界与后续必须守住的契约

本报告只保留测试结果。一次性原型和隔离 worktree 在验证结束后删除，不进入生产代码。

本 change 只产出评估结论与原型工具，**不替换现有 `textarea` 生产编辑器**。任何内核落地必须另开独立「编辑器迁移」change 并经用户确认，`src/` 全程未动。

后续任何实际编辑器迁移 change 必须继续保护以下三条契约：

1. 草稿本和正文本的纯文本事实源不能被内核悄悄改写。
2. AI 请求使用点击时冻结的原文、UTF-16 起止偏移和本子标识。
3. AI 永远不能直接写入、替换、删除或整理草稿本和正文本中的任何字符。
