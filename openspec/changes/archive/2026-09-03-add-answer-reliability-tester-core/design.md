## Context

当前 `sidecar/driver/test-driver.mjs` 用真实 DSH driver 验证常驻会话协议和生命周期，但它的案例是协议级断言，不能判断模型对作品事实、版本更新、否定或未知信息的回答是否可靠。第一轮可靠性测试还发现，关键词判分会把引用或否定中的词误当成模型结论。

本 change 只建立离线核心检验闭环。它运行在现有 Node/TypeScript 体系内，复用 driver 的 JSONL 协议，不进入用户产品路径，不修改用户作品，也不修改现有常驻会话规格。

## Goals / Non-Goals

**Goals:**

- 用结构化案例描述可重复的回答可靠性问题。
- 用真实 DSH driver 执行单轮、多轮和版本相关案例。
- 保存足以定位问题的脱敏运行证据。
- 将协议/运行错误与模型回答问题分开。
- 对自然语言回答进行保守初筛，无法确定时明确进入人工复核。
- 为第二步的人工复核页面和更丰富指标保留稳定的案例、结果和证据边界。

**Non-Goals:**

- 不做用户可见的测试 UI 或在线监控平台。
- 不引入 Python sidecar、DeepEval、Inspect AI 或 Phoenix 作为第一版依赖。
- 不实现通用 RAG、知识图谱或作品上下文生产能力。
- 不自动修改模型回答或任何用户文档。
- 不把开放性创作判断转化为单一正确答案。

## Decisions

### 1. 独立测试 runner，复用 driver 协议

新增测试器作为 `sidecar` 周边的离线工具，与已有协议回归脚本分开。runner 负责读取案例、拉起或连接 driver、按案例发送协议消息、收集终态和事件摘要；driver 继续只负责 DSH 会话能力。

**选择原因**：这样可以区分“会话基础设施测试”和“模型回答可靠性测试”，也避免为了测试器改变生产 driver 的行为。

**替代方案**：直接扩展 `test-driver.mjs`。这会让协议回归脚本同时承担模型事实判定，案例、超时和报告逻辑容易互相污染，因此不采用。

### 2. 案例使用 JSON/JSONL，结果使用独立证据 JSON

每个案例至少包含案例标识、材料版本与哈希、会话步骤、问题、预期事实边界、允许的不确定表达、明确错误结论、原文依据位置和风险标签。每次运行独立生成结果文件，保存完整模型回答、事件摘要、耗时、退出状态、运行错误、配置摘要和自动判定理由。

**选择原因**：结构化文件便于版本控制、批量运行和未来迁移到 Inspect AI 或 Phoenix；独立结果避免改写测试案例。

**替代方案**：只输出终端表格。终端适合快速查看，但无法为误判提供完整证据，也不利于第二步人工复核，因此不采用。

### 3. 自动评分采用分层、保守的结果模型

自动结果固定为 `PASS_LIKELY`、`FAIL_LIKELY`、`NEEDS_REVIEW`、`RUNTIME_ERROR`。协议完成、空回答、进程提前退出、超时和敏感信息泄漏等可确定问题可以直接判定；涉及否定、引用、未知、事实与推测边界的复杂自然语言，除非证据足够明确，否则必须标记 `NEEDS_REVIEW`。

人工结论不覆盖自动原始结果，另存为 `MODEL_OK`、`MODEL_ERROR`、`SCORER_ERROR` 或 `UNRESOLVED`。

**选择原因**：避免再次把关键词或 LLM-as-judge 当作绝对裁判，保留区分模型错误和评分器错误的能力。

**替代方案**：使用一个总分或单个关键词规则。它实现简单，但已被现有压测证明会误判，因此不采用。

### 4. 证据脱敏优先于完整日志

证据可以保留完整问题和回答，以及用于诊断的 DSH 事件摘要，但不得写入 API Key。运行配置只保存 API base 的非敏感标识、模型名、测试器版本和材料哈希；发生错误时截断并脱敏错误文本。

**选择原因**：测试器需要可复查，但不能因为保存 trace 破坏密钥边界。

### 5. 第一批案例优先覆盖高风险语义

第一批固定案例覆盖：v1/v2 事实修改、明确否定、未提及信息、否定句引用、事实与推测区分、多轮旧事实冲突、compaction 后事实保持和多场景多跳关系。案例预期描述“事实边界”，不要求开放性回答逐字匹配。

**选择原因**：这些案例正是当前关键词判分最容易失败、又最影响作品上下文可信度的地方。

## Risks / Trade-offs

- [风险] 真实模型回答具有随机性，重复运行可能产生不同表述。→ 保存完整原始回答和运行元数据；自动结果使用 `LIKELY`/`NEEDS_REVIEW`，不宣称绝对稳定。
- [风险] 事件摘要不足以定位上下文传递问题。→ 第一版保留协议事件和必要配置摘要的扩展字段；完整 Phoenix 式 trace 留待后续 change。
- [风险] 测试材料或报告包含作品敏感内容。→ 测试器只读取明确指定的离线材料，结果目录不进入生产作品存储；文档和实现中明确报告保密责任。
- [风险] 评分规则逐渐膨胀成隐性剧作理论。→ 规则只核对案例声明的事实边界、未知和不确定标记，不评价创意质量或故事方向。
- [风险] runner 与现有 driver 协议耦合。→ 通过独立协议客户端和端到端测试验证 `ready`、会话、消息终态及 `shutdown`，不复制 DSH 内部实现。

## Migration Plan

这是新增离线测试工具，无生产数据迁移和用户界面迁移。实现完成后先用脱敏固定材料运行核心案例，检查证据文件，再将命令和案例目录写入开发文档。若结果格式或判定规则需要调整，只影响测试工具和证据，不影响用户作品或现有会话。

## Open Questions

- 第一版是否保存完整协议事件，还是只保存与每轮回答相关的摘要；实现时以隐私和诊断需要作最小化决定。
- 首批案例的预期事实边界和原文位置需要在实现前由人工确认。
- 是否将 compaction 案例纳入同一次 runner，还是作为已有协议探针的独立入口；不影响本 change 的核心结果格式。
