## Context

应用当前的视觉是脚手架自带的"默认灰"（`src/styles.css` 里 `#e2e8f0` 边框、`#4a5568` 按钮、圆角、柔和阴影）。`src/styles.css` 的 `:root` 已有一小组 CSS 变量（`--color-surface`、`--color-border` 等），但大量组件样式仍直接写死颜色/边框值（如 `.save-btn { background-color: #4a5568 }`、`.tab-btn.active { border-bottom-color: #4a5568 }`）。

项目已确认视觉方向为「全量新粗野主义」（见 `.omo/二阶段-01/…探讨和确定.md` 二.6），并有一份方向确认渲染稿 `.omo/ui-direction-comparison.html` 作为参考（非应用代码）。

关键约束（用户明确提出）：**不要写死**——后续 UI 更新迭代的可能性很大，视觉值必须能在不散改代码的情况下快速调整。

## Goals / Non-Goals

**Goals:**

- 把所有视觉值（颜色、边框粗细/颜色、阴影、圆角）收敛到 `:root` 里的设计令牌（CSS 自定义属性），组件样式只引用令牌、不写死字面值。
- 用令牌把新粗野主义方向落下去：白底、黑色结构线、硬边偏移阴影、零/小圆角、主色钴蓝 + 辅助暖金。
- 把"文本编辑区是视觉焦点、chrome 更轻"的主次关系编码进令牌分层，而不是散落在各处。
- 选中/激活态统一用主色，不用黑色。
- 不改 DOM 结构、不改行为逻辑。

**Non-Goals:**

- 不改布局结构（三页导航、项目内容树等是二阶段未来 change，不属于本 change）。
- 不新增功能、按钮、交互。
- 不做主题/深色模式系统（现有 `prefers-color-scheme` 块的处理见 Open Questions）。
- 不冻结具体视觉数值——令牌名稳定、数值可迭代。

## Decisions

1. **用 CSS 自定义属性作为设计令牌，集中定义在 `:root`。** 这是最轻的机制：无构建步骤、无新依赖，vanilla TS 应用直接可用。备选 Tailwind 主题配置 / CSS-in-JS 被否——都会引入构建或依赖变更，收益不匹配。

2. **令牌用语义命名，不用原始值命名。** 例如 `--color-primary`、`--color-accent`、`--color-ink`、`--color-surface`、`--border-structural`、`--shadow-hard-md`、`--radius-none/sm`。理由：语义名在数值迭代后仍然成立（"primary" 永远是 primary，哪怕钴蓝换成别的色）；原始值命名（`--color-cobalt`）会在换色时被迫改名，违背"不要写死"。

3. **把主次层级编码进令牌分层。** 分别定义 chrome（顶栏/标签/工具栏/AI 面板）与文本编辑区的边框、阴影令牌，使"文本编辑区框最重、chrome 依次更轻"成为令牌层的结构事实，而非零散覆盖。理由：这是本次设计的核心意图，也是用户反复确认的焦点原则。

4. **黑色只做结构线（边框）和文字，选中/动作态归主色钴蓝。** 理由：用户明确要求"选中按钮不要黑色"；配色体系里主色承担"现在在哪 / 往哪点"，辅助暖金承担"候选 / 选区高亮"。

5. **圆角极小（0 或极小值），阴影用硬边纯偏移（无模糊、无扩散）。** 这是新粗野主义区别于默认灰的关键辨识度。

6. **行为与 DOM 结构不变。** 仅改 `styles.css`，必要时给 `index.html` 补充极少量 class/属性以表达状态，不移动、不增删结构节点。

## Risks / Trade-offs

- [现有样式相关测试（如 `tests/editor-layout-style.test.ts`）可能因颜色/边框断言失效] → 更新测试改为断言令牌或 class 状态，而非硬编码颜色值。
- [硬偏移阴影在窄窗口下可能被裁切] → 阴影距离控制在较小值（≤5px），并在窄窗口下验证。
- [长时间写作的可读性被"有性格"的 chrome 干扰] → 正文区保持近黑文字 + 白底的高对比；钴蓝/暖金只用于功能信号，正文内部不引入装饰色。
- [视觉值尚未最终确定、会继续迭代] → 这正是采用令牌的目的：迭代只改 `:root` 值，不动组件规则；本 change 的验收以"机制 + 方向"为准，不以某次具体数值为准。

## Open Questions

- 渲染稿 `.omo/ui-direction-comparison.html` 是否随 change 一并入库作为视觉参考，还是留在 `.omo` 不归档？
- 具体令牌数值（边框粗细、阴影距离、主色精确 hex）在实现后会经真机视觉验收再微调，不作为本 change 的冻结值。
