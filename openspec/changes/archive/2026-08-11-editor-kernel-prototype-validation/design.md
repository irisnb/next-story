## Context

当前 Next Story 编辑器是两个原生 `textarea`（草稿本、正文本），`.txt` 是内容事实源，选区 AI 依赖 `selectionStart` / `selectionEnd` 这两个 UTF-16 整数偏移（见 `src/selection-adapter.ts`、`src/editor.ts`）。二阶段方向要求换成成熟的结构化富文本内核，但这会重新打开一批当前不存在的风险：纯文本投影、换行/空白保持、选区偏移换算、保存重开一致性、中文输入法。

研究阶段（`.omo/ulw-research/20260810-214721/`）已把候选收敛为 Tiptap/ProseMirror 与 Lexical，并列出一张验收矩阵。本设计描述如何用一个隔离原型把这张矩阵在真机上跑出结论，而不是直接改生产编辑器。

**约束**：
- `AGENTS.md` 铁律：AI 永不写回草稿本/正文本；一次只开一个 change；一个概念一个名字；UI 可选项后端必须真实可用。
- 目标运行环境：Windows + Tauri 2 + WebView2，含简体中文输入法。
- 原型必须与 `src/` 生产代码隔离，不污染现有构建产物的用户可见路径。

## Goals / Non-Goals

**Goals:**
- 在同一 Windows Tauri/WebView2 环境为 Tiptap 与 Lexical 各建一个最小实例，接入相同的"纯文本投影 + 冻结选区快照"适配层。
- 对两个候选执行同一组可二元判定的验收测试，产出可对比的实测证据。
- 得出一个有证据支撑的选型结论，或在两者都失败时明确"暂缓迁移"。

**Non-Goals:**
- 不选定并落地最终内核（选型结论只是本 change 的产出，落地是后续独立 change）。
- 不实现二阶段富文本能力（粗体、标题、列表等）、项目树、AI 参考优先级、DOCX 导入导出、新粗野主义 UI。
- 不改动现有 `textarea` 生产编辑器、选区 AI、保存流程或 AI 边界。
- 不做性能极限调优；只验证是否达到约定阈值。

## Decisions

**决策 1：隔离原型，不改生产代码。**
原型放在独立目录（如 `prototype/editor-kernel/`），有自己的入口，不接入欢迎页/现有编辑器。理由：内核验证有失败可能，隔离可保证随时整体丢弃而不留下半套迁移代码，符合"一次只开一个 change、做完归档"的纪律。备选（直接在 `src/editor.ts` 上改造）被否决——一旦候选失败，回滚成本高且可能污染事实源。

**决策 2：两个候选共用同一套"纯文本投影 + 冻结选区快照"适配层。**
无论内核内部结构如何，AI 只接收从结构化选区生成的冻结纯文字快照（本子类型、可见原文、UTF-16 起止偏移），与现有 `selection-adapter.ts` 契约一致。理由：这样两个候选在同一条件下受测，差异才可比；也确保 AI 边界在原型里就被强制。备选（各自用各自的选区表示）被否决——无法公平对比，且可能把 Lexical 的临时节点标识误当持久标识。

**决策 3：Tiptap/ProseMirror 先测。**
ProseMirror 提供成熟的 `SelectionBookmark` / `Mapping` / `StepMap` / `coordsAtPos`，对"冻结选区在编辑后如何找回"这一最高风险点更有基础。Lexical 作为对照，用于在 Tiptap 某项失败或明显笨重时提供替代证据。

**决策 4：验收采用二元判定 + 双证据。**
每项测试预先写死通过条件（如"保存重开后 `.txt` 字节与行尾完全一致"），并要求两类证据：自动化测试的红→绿，以及真机操作的实录（中文输入法必须人工在 WebView2 里实敲）。理由：内核选型是地基决定，"应该能用"不算数。

## Risks / Trade-offs

- [中文输入法在 WebView2 下仍可能丢字/重复/乱序] → 这正是原型要验的核心项；若两个候选都失败，触发回滚规则，暂缓迁移并回到运行时/方案讨论，不强行选型。
- [富文本内核把纯文本存歪，破坏事实源铁律] → 保存重开逐字节比对为硬性通过条件；失败即拒绝该候选或重新设计投影/持久化适配层。
- [原型引入的 npm 依赖后续污染生产] → 依赖在原型阶段隔离；是否进入生产由验收结果和后续独立 change 决定，本 change 不把它们加进生产依赖。
- [Tiptap Pro / DOCX 等付费或托管能力被误当免费核心] → 许可与依赖审查列为独立验收项；核心 MIT 与 Pro/托管边界分开记录，且不构成法律意见。
- [原型做着做着扩大成"顺手把二阶段也实现了"] → Non-Goals 明确列出禁止项；tasks 只覆盖验收矩阵，任何富文本/项目树/DOCX 工作都必须另开 change。

## Migration Plan

- 本 change 不产生用户可见的迁移；原型是评估工具，非发布物。
- 结束状态有两种：(a) 某候选通过全部关键验收项 → 产出选型结论，供后续"编辑器迁移"独立 change 引用；(b) 两候选均在关键项失败 → 记录失败证据，暂缓迁移，原型可整体删除。
- 回滚：删除 `prototype/` 目录及其隔离依赖即可，`src/` 生产代码全程未动。

## Open Questions

- 真机验收由用户在其 Windows 环境执行，还是有其他可用的 Windows + 中文输入法环境？（中文输入法项无法在无 IME 的自动化环境中替代）
- "真实剧本长度"和"可接受的输入延迟/内存阈值"的具体数值，需在 tasks 执行前与用户约定。
- 原型目录的确切位置与命名（`prototype/editor-kernel/` 为建议值），以及是否纳入版本控制（`.omo/` 被忽略，但 `prototype/` 默认会进 git）。
