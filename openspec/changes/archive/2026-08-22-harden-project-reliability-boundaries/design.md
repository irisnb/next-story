## Context

第一批工作针对系统审查中最接近用户损失的异常路径。当前 `src/editor.ts` 用 capture 阶段监听全局 keydown，`applyTree` 在当前文档消失时会直接切换或清空编辑器，`loadDocument` 对读取失败没有统一 UI 错误处理。Rust 侧已经有事务阶段和故障注入测试，但恢复入口需要明确区分暂存和提交状态；内容树部分操作仍使用递归函数。

## Goals / Non-Goals

**Goals:**

- 保护非编辑器输入控件的原生编辑行为。
- 在删除或读取失败时保留用户可判断、可恢复的状态。
- 让不完整事务和深层内容树输入以确定性错误处理。
- 通过最小定向测试覆盖每个新增边界。

**Non-Goals:**

- 不拆分 `editor.ts` 或 `operations.rs`。
- 不改变作品格式、Tauri command、回收站协议或 AI 能力。
- 不实现跨进程锁、DSH 请求大小限制或长期 Agent 能力。

## Decisions

### 1. 在快捷键入口统一判断可编辑文本目标

捕获监听在执行编辑器命令前识别 `input`、`textarea`、`select`、`contenteditable` 以及 AI/配置面板中的文本控件；这些目标直接返回，不阻止默认事件。编辑器自身 ProseMirror/Tiptap 区域继续使用既有快捷键。

这比给每个输入框添加独立阻止逻辑更完整，也避免未来新增输入控件再次被全局监听劫持。

### 2. 删除确认放在编辑器状态拥有者

由 `applyTree` 在发现当前文档从树中消失且存在未保存状态时触发确认；确认前不销毁编辑器。这样文件管理入口无需了解编辑器内部状态，取消操作也能保持原有树更新结果与编辑器状态一致。

### 3. 读取失败采用保留旧状态策略

`loadDocument` 捕获读取错误，只有成功读取且 generation 仍然有效时才替换编辑器；失败时保留当前有效编辑器，并通过注入的错误提示通道报告中文错误。首次加载失败时维持空编辑器但不把失败文档标记为成功加载。

### 4. 内容树使用显式栈和统一深度常量

校验和子树收集使用携带 depth 的显式栈；超过上限返回结构错误。限制是防御性资源边界，不截断或自动修复旧作品。

### 5. 事务恢复保守处理

不改变已验证的正常事务流程。对缺少 manifest 的目录，只有能够证明尚未提交时才清理；提交阶段或用途/映射不明时保留文件并返回人工恢复错误。先补故障测试，再调整恢复分支。

## Risks / Trade-offs

- [确认提示可能改变现有删除流程时序] → 只在当前文档确有未保存状态时提示，并覆盖确认/取消测试。
- [读取失败时旧编辑器与新内容树不一致] → 只在成功读取后提交编辑器替换，使用 generation 防止旧请求覆盖。
- [深度上限拒绝极深但合法的作品] → 使用明确常量和中文错误，不静默截断；后续可单独设计迁移。
- [事务异常状态信息不足] → 保留事务目录并返回路径，禁止静默覆盖或删除提交阶段文件。

## Migration Plan

1. 先补前端快捷键、删除确认和加载失败测试，再实现前端行为。
2. 补 Rust 内容树深度与 manifest 异常测试，再实现显式栈/恢复边界。
3. 运行定向测试、TypeScript typecheck/lint 和 Rust 项目测试。
4. 运行项目总检查；失败只修复本 change 范围内的问题。
5. 完成后更新本 change 任务，再检查 `.omo/systematic-project-hardening-roadmap/`，确认下一批次仍按顺序推进。

## Open Questions

- 内容树最大深度的产品数值尚未在总路线中固定；本批使用代码常量并在测试中验证行为，数值选择需保持足够宽松。
- 若现有事务格式无法区分“无 manifest 的暂存”和“已提交”，不猜测恢复；应保留目录并返回明确人工恢复错误。
