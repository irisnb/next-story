## Context

Next Story 当前由 Tauri/Rust 承担作品文件事务、LLM 配置持久化和 AI 生成三块后端职责。DSH sidecar 已完成 headless 真实生成、追问、钥匙串读取、错误映射和工具禁用的链路验证，但尚未成为正式生产入口，也尚未完成打包、生命周期管理和版本隔离。

本次迁移只把 AI 生成/追问链路迁到 DSH。作品文件事务和 LLM 配置持久化留在 Rust——作品文件事务是用户文档安全边界（铁律 1 的最稳防线），LLM 配置的 API Key 本就在系统钥匙串中、由 Rust 持有。DSH 保留插件市场、profile、patch、Agent、工具和未来事件流能力，但本次只接通已验证的 headless one-shot 生成与追问。

## Goals / Non-Goals

**Goals:**

- 以 DSH 作为 AI 生成与追问链路的运行引擎。
- 保持作品创建、打开、保存、校验、LLM 配置、AI 召唤和临时追问的用户可见语义不变。
- 保持 `GenerateAiRequest`、`GenerateAiResult`、`GenerateAiError` 和错误码契约稳定。
- 建立可扩展 Runtime Contract 与能力网关，首版支持 one-shot 生成和追问，并为事件、取消、能力发现、工具和结构化结果留下正式扩展位。
- 保留 DSH 插件市场及其安装、依赖、profile、patch 和加载机制。
- 通过能力网关保护用户文档和系统资源，AI 永远不能写入用户文档。
- 将 DSH 版本、Node runtime、DSH_HOME 和插件状态隔离，支持验证后升级和失败回滚。
- 迁移验证完成后删除旧 Rust HTTP 生成路径和临时双生成后端。

**Non-Goals:**

- 作品文件事务不迁移，保持现有 Rust 实现（原子保存、符号链接防护、大小上限、崩溃恢复、迁移框架、串行化）。
- LLM 配置持久化不迁移，保持现有 Rust 实现（钥匙串 + 磁盘原子写非敏感字段）。
- ACP 长驻协议、流式 UI、工具调用、多 Agent 产品流程——本次不上，作为后续扩展。
- 作品树、草稿本/正文本废弃或作品数据模型重做。
- Memory、Skill、Policy、Evaluator、Reflection、自我进化。
- AI 修改、插入、追加、替换、删除、移动或整理用户文档。

## Decisions

### 1. 使用稳定的产品 Runtime Contract，隔离 DSH 适配细节

Next Story 内部以任务请求、任务事件、任务结果、错误和能力声明表达核心交互。首版只返回一次非流式结果，但类型和边界不得退化成永久的 `string -> string` 函数。DSH 版本特定的 CLI 参数、stdout 格式、退出码和 preview API 只出现在 adapter/sidecar 层。

备选方案是让前端直接理解 DSH CLI 或把 DSH 响应直接透传到 UI；这会把 preview 细节扩散到产品层，阻碍升级，也削弱权限控制，因此不采用。

### 2. Rust 保留宿主与数据职责，DSH 只接管 AI 生成

Rust 负责 Tauri 窗口、sidecar 的启动/看守/终止、系统钥匙串、作品文件事务、LLM 配置持久化、外部链接和最小权限控制。DSH 只接管「AI 生成与追问」这一件事。前端仍调用稳定的 Next Story API，不感知后端是 Rust 直连还是 DSH。

备选方案是让 DSH 接管作品文件事务和配置持久化（「全迁」）；DSH 0.1.0-rc.7 无跨文件事务、无跨进程确定性调用入口，会迫使把用户文档安全地基重写进 preview 平台，违反铁律 1，因此不采用。

### 3. DSH 每个版本使用独立安装目录和 DSH_HOME

应用维护 `versions/<version>`、`homes/<version>` 和当前版本指针。新版本先独立安装、加载 Next Story patch 与插件、执行回归测试，成功后才切换指针；旧版本保留以便回滚。API Key 仍在系统钥匙串中，与 DSH 版本解耦。

备选方案是继续使用全局 `~/.dsh`；这会让不同版本和其他应用的状态互相污染，且难以可靠回滚，因此不采用。

### 4. 插件能力通过能力网关进入产品

DSH 插件市场和插件运行时完整保留，但插件访问作品、文件、网络、命令和任务控制必须经过 Next Story 明确定义的能力边界。用户文档写入能力永久不存在；默认禁止任意命令执行和任意文件写入。插件不得通过 stderr、配置或绕过 adapter 取得密钥。

备选方案是为迁移省事而关闭所有插件和工具；这会直接砍掉选择 DSH 的核心价值，不采用。备选方案是完全信任插件；这违反产品文档安全铁律，也不采用。

### 5. LLM 配置所有权留在 Rust，spawn DSH 时注入

API Key 仍在系统钥匙串中由 Rust 持有；模型名与 API 地址由 Rust 在 spawn DSH sidecar 时通过受控方式注入（不与 DSH 版本绑定、不落明文 key）。这样 LLM 配置的保存/加载/校验/测试连接逻辑全部保持不变，只有生成路径换成 DSH。

备选方案是把模型名和 API 地址也交给 DSH 的 `ctx.settings` 持久化；这会把配置持久化职责从 Rust 移到 preview 平台，且 API Key 与配置需要跨进程协同，增加风险而无收益，因此不采用。

### 6. 迁移采用「接通、验证、删除」的单向收敛流程

迁移期可以保留内部开关或兼容分支作为测试保险，但默认行为、测试矩阵和可观测性必须覆盖 DSH 路径。生成、追问、错误、超时、插件和进程清理全部通过后，删除旧 Rust HTTP 生成路径和开关，避免长期双生成后端。作品文件事务与配置持久化路径不参与切换。

## Risks / Trade-offs

- [DSH preview 版本发生兼容性变化] → 精确锁版；每次升级使用独立目录和独立 DSH_HOME，先跑回归测试，失败时切回旧版本。
- [插件或 DSH 工具绕过用户文档边界] → 只暴露能力网关；默认禁用写文件和命令工具，并增加尝试写入的拒绝测试。
- [Windows stdout/stderr 管道阻塞导致 sidecar 卡死] → 并发排空 stdout/stderr，设置壳侧超时和强制终止，测试进程退出与残留清理。
- [DSH 错误信息泄露密钥或用户文本] → adapter 只使用稳定错误码和脱敏 message；原始诊断仅写入受控日志并过滤敏感字段。
- [生成后端切换造成前端行为回归] → 保持 GenerateAi* 契约和错误码分类不变；复用现有生成/追问测试，先接通 DSH 再删旧路径。
- [未来能力被首版契约限制] → Contract 使用任务/事件/能力声明的可扩展类型；首版 one-shot 只是实现能力子集，不将字符串结果作为唯一抽象。

## Migration Plan

1. 固化 Runtime Contract、能力网关和 DSH adapter 边界，补齐 DSH 版本、profile、patch、插件和凭据配置。
2. 将 DSH sidecar 与 Node runtime 纳入开发和生产打包，完成启动、看守、超时、终止、日志脱敏和独立运行目录。
3. 接通 AI 首次生成和临时追问入口，保持前端 API 和用户行为不变；LLM 配置由 Rust 在 spawn 时注入。
4. 运行 keyring、生成、追问、错误、插件安全、升级回滚和进程清理的完整测试矩阵，同时复用作品文件事务与配置持久化的既有测试确保无回归。
5. 在所有测试通过后删除旧 Rust HTTP 生成路径、旧生成入口、临时 A/B 开关和不再使用的兼容配置。

回滚策略：迁移未完成时保留旧生成实现作为开发期回退路径；正式切换前保留上一个 DSH 版本及其独立 DSH_HOME。若新核心验证失败，将当前版本指针切回已验证版本，不回滚或改写用户作品文件。

## Open Questions

- DSH 插件市场的安装 UI 和插件审批流程是否在本次只提供运行时接缝，还是需要新增 Next Story 管理界面；本次默认只实现底层接缝，不新增产品 UI。
- DSH 未来事件流的具体协议尚未稳定；本次只定义 Next Story 内部扩展位，不绑定 preview 的长期 wire format。
