# 下一阶段任务：确认弹窗与项目审查

记录时间：2026-08-05

> **文档性质**
>
> 这是一份下一阶段任务记录，用来保存接下来需要讨论和审查的范围。它不是 OpenSpec，不是实现事实，不是已经确认的设计方案，也不是正在执行的 change。
>
> 任何代码实现、UI 改动或模块拆分，都仍然必须先走 OpenSpec propose，让用户确认“要做什么”之后再 apply。

## 一、背景

刚完成的 `fix-silent-first-preview` 修复解决了一个关键问题：首次发送创作内容前的确认弹窗被 Tauri 权限拒绝时，AI 面板不应静默停在“正在思考”。

这个修复把当前确认机制重新拉回可用状态，但它也暴露了两个后续问题：

- 创作内容确认弹窗的弹出时机和 UI 仍需单独讨论，不能只按当前实现惯性继续扩展。
- AI 面板、AI 请求协调、确认状态、追问状态和测试已经开始变重，需要做一次专门的项目检查，判断哪些模块已经臃肿，哪些边界需要拆清楚。

这两个问题都不适合直接在刚修完 bug 后顺手改。它们需要先被写清楚，再分别进入 OpenSpec 流程。

## 二、确认弹窗仍需讨论的事项

当前策略是：应用本次打开周期内，对每个 API 服务来源确认一次。更换服务地址、取消确认或下次重新打开应用后，再次发送创作内容前会重新弹出确认。

下一阶段需要重新讨论以下问题。

### 1. 弹出时机

需要确认哪些动作必须触发创作内容发送确认：

- 选区 `AI 及时召唤` 首次生成。
- 选区 `思维扩展` 首次生成。
- 首次成功后的继续追问。
- 失败后的重新请求。
- 修改追问后的重发。
- 未来如果加入 `思考收束`，是否沿用同一确认边界。

讨论时要区分两类请求：

- `测试连接` 只发送固定测试语句和身份凭据，不发送用户剧本文字或临时对话。
- `AI 生成` 会发送选区原文、思维扩展方向和当前临时对话中的成功轮次，属于创作内容离开本机。

### 2. 确认粒度

需要确认确认状态按什么粒度记忆：

- 按应用打开周期记忆。
- 按 API 服务来源记忆。
- 按作品记忆。
- 按具体模型记忆。
- 每次发送都确认。

当前实现偏向“应用打开周期 + API 服务来源”。这只是当前状态，不等于最终产品决策。

### 3. 用户可见 UI

需要讨论弹窗应如何表达，尤其是：

- 是否显示规范化后的 API 来源。
- 是否明确区分测试连接和 AI 生成。
- 是否说明会发送哪些创作内容类型。
- 是否提供“继续发送”和“取消发送”。
- 取消后面板如何显示，是否保留冻结选区和重试入口。
- 是否需要在 LLM 配置页同步放置更稳定的说明。

UI 文案必须避免泄露 API Key、Authorization、选区原文、方向、临时对话或完整请求正文。

### 4. 产品边界

这个讨论不能改变永久边界：

- AI 不能直接改草稿本和正文本。
- AI 输出仍是临时材料。
- 用户自己决定是否复制、编辑、保存。
- 确认弹窗只是在发送创作内容前让用户知情，不是让 AI 获得写回权限。

## 三、项目审查与模块拆解任务

下一阶段还需要做一次彻底项目检查，目标不是追求“文件越小越好”，而是看清责任是否已经混在一起。

### 1. 审查对象

重点检查以下区域：

- AI 入口和选区冻结链路。
- AI 面板 DOM 渲染与交互。
- AI 面板状态模型。
- AI 请求协调和确认状态。
- 追问、重试、取消和失败状态。
- 前端测试中已经过长或覆盖过多职责的测试文件。
- Rust 侧 LLM 配置、生成请求和错误规范化链路。
- Tauri capabilities 与前端调用边界。

审查时可以从文件长度、职责数量、测试难度、变更频率和跨模块耦合五个角度判断，而不是只看行数。

### 2. 需要产出的审查结果

审查结束后，应产出一份清单，至少包含：

- 当前最臃肿或最容易继续变乱的模块。
- 每个模块现在承担了哪些不同责任。
- 哪些责任应该保留在原模块，哪些可以拆出。
- 拆分后建议的新模块名和单一职责。
- 拆分风险：哪些测试、状态转换或 UI 行为最容易被破坏。
- 建议的 OpenSpec change 顺序。

这份清单只提出候选，不直接改代码。真正拆分仍要逐项 propose。

### 3. 拆解原则

模块拆解应遵守这些原则：

- 不改变用户可见行为。
- 不改变草稿本和正文本边界。
- 不顺手增加新功能。
- 不引入多模型、多 provider 或新 AI 架构。
- 不把当前 bug 修复和结构拆分混在同一个 change。
- 优先拆“责任已经明确分离”的模块，而不是为了行数好看强拆。
- 测试必须跟着职责边界更新，不能因为拆分而削弱测试。

## 四、建议的后续顺序

建议下一阶段按以下顺序推进：

1. 先讨论确认弹窗的弹出时机和 UI。
   - 目标：把发送创作内容前的用户知情边界设计清楚。
   - 产物：一个 OpenSpec propose，范围只覆盖确认弹窗和相关说明。

2. 再做项目审查。
   - 目标：找出当前最需要拆分的模块和测试。
   - 产物：一份审查清单，不直接改代码。

3. 根据审查结果选择一个最小拆分 change。
   - 目标：只拆一个明确边界，验证拆分方式不会破坏现有 AI 闭环。
   - 产物：一个 OpenSpec propose，用户确认后再实现。

## 五、不要混入的事项

下一阶段不要顺手加入这些内容：

- AI 自动写入、插入、替换、改写、删除或整理草稿本和正文本。
- `应用到正文`、`插入正文`、`替换选区` 等写回入口。
- 多个临时对话、历史列表或持久化 AI 会话。
- 附近上下文、全文摘要或完整作品认知。
- 多 provider、多模型选择或前端展示后端不可真实调用的模型。
- AI 内容库、用户确认的作品信息或说明性文档。
- 为了拆模块而同步改产品行为。

## 六、当前最短行动建议

下一步可以开一个 OpenSpec explore 或 propose，主题限定为：

```text
确认创作内容发送提示的时机与界面
```

它只回答“什么时候提醒、提醒什么、用户取消后界面怎样保持可恢复”，不处理模块拆分。

确认弹窗讨论完成并归档后，再单独启动项目审查，避免产品设计和工程治理互相覆盖。
