# 设计：GitHub 门面重整

## Context

主仓库 `irisnb/next-story` 已随 v0.1.0 公开。现行 README 266 行，由 2026-10-24 `site-and-readme-launch` 定下的骨架演化而来，其中「里程碑表」「撤出清单」承担的是内部账本职责，外部访客视角显得不专业（2026-10-29 用户反馈，参照思源笔记、pot-desktop 等同类项目门面）。同日用户复确认：截图不直出 README（维持 2026-10-24 拍板）。另发现 2026-10-24 首发Release 说明乱码根因（PowerShell 5.1 向 `gh` 内联传中文参数按 GBK 编码、GitHub 按 UTF-8 解释），已在线修复，本设计把防复发规则落入文档。

## Goals / Non-Goals

**Goals**

- README 双受众导向：创作者三屏内呈现「是什么—能干什么—如实边界—去哪下载」，开发者获得「AI＋本地文件读写边界」的一等叙事分区。
- `docs/ARCHITECTURE.md` 把框架能做什么、基础功能有哪些向开发者说明白。
- 开发者手册完整外移到 `docs/DEVELOPMENT.md`，不丢信息。
- 发布说明编码防复发规则版本化。

**Non-Goals**

- 不改应用代码、CI、构建配置。
- 不新增界面截图、不改官网、不动 LICENSE 与许可状态。
- 不做框架抽取、不开放许可、不写「可复用框架」承诺（参考实现定位：可读可学）。
- 不建 CHANGELOG.md（见 D2）。
- 不处理 `AGENTS.md` 内部链接 404 与 `.opencode/` 可见性问题（见 Open Questions）。

## Decisions

**D1 README 双受众信息架构**：依次为居中标志与定位语＋徽章 → 简介（创作者一段说清，官网承接细节）→ 核心特性（四组短句，三条稀有能力前置）→ 如实说明 → 下载（含 SmartScreen 提示）→ 给开发者（一等分区）→ 协作与协议。目标约 140 行。理由：GitHub 访客天然偏开发者，官网已承担创作者产品叙事；徽章排与定位语现状良好，保留。（2026-10-29 二轮拍板：双受众）

**D2 里程碑表删除而非改造**：17 行全「已完成」的表对访客无信息量，对项目自身与 `openspec/changes/archive/` 重复。不建 CHANGELOG.md——openspec 归档与 Releases 页已经是两份现成的历史真相源，再抄一份徒增同步负担。README「协作与协议」区留一行：能力真相源 `openspec/specs/`，版本历史见 Releases。

**D3 「如实说明」产品语言化**：只保留访客能据以决策的三条边界——作品正文手动保存（无自动保存/自动备份/版本快照；讨论档案自动保存另说）、全应用仅一份 OpenAI 兼容 API 配置（无多服务方/多模型选择）、仅发行 Windows 版。删除「已撤出、非待办」内部治理概念清单：诚实保留，表达方式换成产品语言。规格原「如需提及撤出功能须标注已撤出」规则保留不动（新 README 根本不提及，空满足）。

**D4 核心特性详略尺度**：五组（写作空间与项目 / AI 陪想 / 讨论管理 / 制作模块 / 导入导出与基础）。取舍原则：砍内部账本，不砍能力细节——编辑器格式与功能完整列举、写作宽度三档数值、两种问法与生成控制（追问/取消/停止/排队/压缩）、讨论列表分组与管理、制作模块双标签与零卡链路、导入导出格式清单均保留，让访客能判断能力规模；MUST NOT 出现内部工具名（`story-read` 等）、存储路径、规格/归档计数、实现术语（「快车道」「阶段五 A」等）。每条能力句仍须可追溯 `openspec/specs/`（事实口径要求维持）。三条稀有能力（未保存快照可问、授权补读、参考出处可查）前置呈现——它们是同类产品少见的能力，也是「受控只读」架构的直接体现。（2026-10-29 三轮修正：首版压至每组 3–6 条被用户判「过于简略」，改为细节充分原则。）

**D5 「给开发者」分区设计**：结构为三段——①普遍问题一句话（AI＋本地文件：怎么让模型看得见内容、又不给它任何写权限）；②解法概览四点（保管者/使用者分离、受控只读接口、文档级可见性与授权补读、AI 无写能力）；③架构示意图（ASCII 代码块，非界面截图，不违反 2026-10-24 截图拍板）＋深读链接 `docs/ARCHITECTURE.md`（是什么、能做什么）与 `docs/DEVELOPMENT.md`（怎么跑起来）。开发者速览（依赖安装两条命令＋命令小表）并入本分区收尾。理由：这是本项目对外最独特的差异化叙事，对创作者对应「安全感」、对开发者对应「架构答案」。

**D6 ARCHITECTURE.md＝框架能力清单**：向开发者把「框架能做什么、基础功能有哪些」说明白（2026-10-29 用户拍板口径）。结构：①保管者/使用者分离总图（同 README 示意图的完整版）；②六组基础能力清单——内容保管（内容树/保存/校验/版本迁移/崩溃恢复）、受控只读接口（目录投影/正文/字面检索及硬上限）、可见性与授权（文档级可见性、越权拒绝、讨论级授权补读、失控保险丝）、常驻会话可靠性（流式/多讨论并发调度/上下文压缩/停滞看护/崩溃恢复重放）、材料可追溯（本次参考了什么/出处持久化）、隔离边界（AI 无写能力、项目服务不注册 AI 写工具、日常与制作上下文隔离）；③每组能力标注对应 `openspec/specs/` 规格名。口径红线：只写已归档规格背书的能力，MUST NOT 宣称未实现或已撤出方向（语义检索、完整作品认知、后台预加载等）为已有能力；许可维持现状，文档定位是「可读可学的参考实现」，不写「可复用框架」承诺。

**D7 外移目标为 `docs/DEVELOPMENT.md` 而非 CONTRIBUTING.md**：本仓库许可为保留所有权利、不允许再分发，暂无对外贡献流程；内容实质是「自己人开发手册」，用 DEVELOPMENT.md 名实相符。结构：开发环境准备 → 依赖安装 → 检查科目（`npm run check` 全序）→ 持续运行命令 → Windows 打包三步 → 简明文件索引 → 数据保存明细表与 API Key 安全说明 → 发布流程。

**D8 发布流程防乱码规则**：`docs/DEVELOPMENT.md` 发布一节写明——创建/编辑 Release 说明一律 `gh release create|edit <tag> --notes-file <UTF-8 文件>`；MUST NOT 在 PowerShell 内联中文 `--notes` 参数（Windows PowerShell 5.1 对原生程序参数按系统 ANSI 代码页编码，中文系统即 GBK，与 GitHub 的 UTF-8 期望错位即乱码）；发布后 `gh release view <tag>` 复查中文渲染。备选方案（改用 PowerShell 7、网页编辑）不采用：文件路径方案对工具链零依赖、最稳。

**D9 明确不动项**：截图不直出（2026-10-24 拍板，2026-10-29 复确认）；徽章排；命名口径（项目/讨论/新建讨论）；平台口径仅 Windows（CI 双平台句保留澄清）；图片资产自包含；许可段落与许可状态（保留所有权利；框架开放与抽取是独立方向决策，本 change 不涉及）。

## Risks / Trade-offs

- [风险] 里程碑删除后 README 不再自证「做了多少」 → [缓解] 协作与协议区留真相源与 Releases 一行链接；规格计数属于内部视角，本就不该是门面卖点。
- [风险] 压缩改写引入与规格不符的表述 → [缓解] 事实口径要求维持；tasks 含逐句对照 `openspec/specs/` 的验收项。
- [风险] 发布规则只是文档、无工具强制 → [缓解] 写明发布后 `gh release view` 复查步骤；未来若发版频繁可再议脚本化（超出本 change）。
- [风险] 精简后文案观感不及预期 → [缓解] README 全文在实现后交用户过目验收再归档。

## Migration Plan

纯文档变更：改写 `README.md`、新增 `docs/DEVELOPMENT.md`，一次提交完成；回滚 = git revert 该提交。无数据迁移、无运行时影响。

## Open Questions

- `AGENTS.md` 与 `.opencode/` 为公开推送，其中引用的 `反面案例/`、`方向/` 未推送、外链 404；是否需要处理（隐藏、改写或补推送）未拍板，本 change 不含。
- 官网是否需要承接「产品时间线/版本历史」展示，留给后续官网迭代讨论。
