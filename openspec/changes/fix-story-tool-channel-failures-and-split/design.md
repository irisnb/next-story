## Context

oracle 独立评审＋主控逐行核实的三条故障路径（行号为当前文件状态，实现时以内容定位为准）：

1. **授权写入失败**（`story_tool_channel.rs:847` 一带，`resolve_reading_request`）：先 `pending.remove(call_id)` 再 `grant_on_demand_reading(...)?`——写入失败时函数直接返回错误，**不向驱动回填 `tool_result`**。前端 invoke 的 catch 会把面板状态置为「已拒绝」，但模型侧轮次仍在等工具结果；由于待决表已清空、授权等待探针不再报告等待，停滞看护约 180 秒后以「生成停滞」错误收场——有界但语义错误（应立即结构化收束）。
2. **授权请求无接收通道**（`:764` 一带）：`story-request-reading` 到达而 `reading_request_sink` 未安装时，仅 `eprintln` 日志；待决表已插入、轮次进入授权等待——而授权等待豁免停滞看护，**理论无时限悬挂**。生产装配总会安装 sink，属装配降级路径。
3. **驱动未接线**（`:471` 一带）：`handle_tool_call` 在驱动缺失时丢弃调用、仅日志，与模块注释「所有失败路径都结构化回填、绝不悬挂」不符。实际不可达（无驱动即无事件源、不会有工具调用进来），属防御分支的注释失实。

文件现状：`story_tool_channel.rs` 1928 行——生产约 925 行（`:926` 起 `mod tests` 约 1000 行）。生产部分挤了四件事：通道结构与驱动/接收器接线、轮内读取状态（版本固定/同轮去重/阅读程度/保险丝）、待决授权表与决定回填、事件编排。审计（`方向/开发前全面工程复核-2026-09-23.md` §6.1/§6.3）建议沿「授权 / 出处 / 轮内读取状态」边界拆分——其中「出处落档」已在 Change 3 移入 `conversation_store`（通道只调用），剩余拆分未做。

调用方（门面约束的依据）：`ai_host.rs`（5 处，经 `story_tool_channel::global_story_tool_channel()`）、`ai_orchestration.rs`（2 处）、`dsh_driver.rs`（注释与授权等待探针说明）、`lib.rs`（模块声明）。全部经模块路径访问——保留模块名做门面即可零改动。

既有测试网：通道内联测试（轮内监管专项、工具往返、授权挂起与决定、熔断等）＋ `on_demand_reading_negative_test.rs`（无路由/未授权/伪造身份/越权/零磁盘副作用）＋ `real_link_on_demand_reading_test.rs`（真实链路，手动）。三条故障路径当前无覆盖。

用户决定：失败收束与拆分**同一 change**一起做；本设计以「两阶段、分笔提交」承接（先钉行为、后纯移动），保住独立回退与审查清晰。

## Goals / Non-Goals

**Goals:**

- 三条故障路径按模块自身承诺收束：结构化回填、失败关闭、轮次不悬挂。
- `story_tool_channel.rs` 按职责拆为三文件；调用方零改动；拆分为纯移动。
- 三条故障路径有集成测试钉住；全部既有测试保持通过。

**Non-Goals:**

- 不改授权语义（成功 / 拒绝 / 迟到决定 / 跨重启保留 / 随时关闭）。
- 不改工具面（四个工具）、协议、能力网关与前端交互。
- 不做超出这三条的其他故障路径清扫（后续按需另立）。
- 不动 `conversation_store`（出处与授权存储已是其后端所有权）。

## Decisions

### D1：两阶段同一 change、分笔提交

第一笔：失败收束（行为修复＋新增测试）；第二笔：拆分（纯移动）。理由：用户拍板一起做；分笔提交沿用项目执行规则（先例：Change A 四笔逐项），第二笔可独立回退而不丢第一笔的修复。审查纪律：第二笔 diff 只允许「移动＋use 路径调整」，混入任何逻辑改动即拆开重做。

被否决的替代：拆成两个 change。用户已明确选择合并；两阶段分笔已保住等价的可回退性。

### D2：三条路径的修法

1. **授权写入失败**：`resolve_reading_request` 在 `grant_on_demand_reading` 失败时，**仍向驱动回填结构化拒绝**（`{granted:false, recovery:<稳定恢复提示>}`，与既有「用户拒绝」结果同构——拒绝是合法结果，模型继续有限回答），随后把错误如实返回给前端 invoke（界面提示「授权未能保存」类信息，具体文案实现时与既有错误风格统一）。pending 清理时机保持在身份校验之后、回填之前（迟到/未知决定继续按「没有该身份的待决授权请求」失败关闭，不动档案）。
2. **无接收通道**：`story-request-reading` 到达而 sink 未安装 → **不插入 pending、不进入等待**，直接回填结构化拒绝——与「用户拒绝」回填同构（`ok=true`＋`result {granted:false, recovery:…}`，携带既有恢复提示常量；实现时确认该形状才能端到端走通有限回答路径并保留恢复提示，优于原先设想的「未授权系 reason」错误形状）。理由：等待一个永远不会呈现给用户的授权没有意义；失败关闭与模块承诺一致。
3. **驱动未接线**：防御分支注释如实化——说明「无驱动即无事件源，此分支仅为装配顺序防御，不回填（无回填对象）」；行为不变。

### D3：拆分方案（门面＋三文件）

- `story_tool_channel.rs`（保留名，门面）：通道结构、驱动/接收器接线、路由表、`handle_tool_call` 编排、`global_story_tool_channel`；re-export 公开类型与函数。
- `story_tool_round_state.rs`：`RoundReadingState` 纯逻辑（版本固定、同轮去重、阅读程度累计、保险丝判定）＋其专项测试随行迁移。
- `story_tool_authorization.rs`：待决授权表（`PendingAuthorization`）、授权请求事件构造、`resolve_reading_request` 的决定回填逻辑＋相关测试随行迁移。
- 出处落档不建第四个文件（已在 `conversation_store`，通道只调用）。
- 约束：纯移动——不重命名公开项、不改逻辑、不改错误文案；`lib.rs` 增加两个模块声明；调用方 `use` 路径不变。

### D4：测试

- 三条故障路径集成测试（复用现有夹具风格：临时作品＋假驱动脚本＋通道），断言：驱动收到结构化 `tool_result`（ok=false＋reason＋恢复提示）；轮次收束不悬挂（等待驱动侧收束，而非停滞看护）；授权档案未被写入（`on_demand_reading_grant` 保持原值）。
- 既有全部测试（内联＋负向＋真实链路编译）保持通过；拆分后测试计数不减。

## Risks / Trade-offs

- [拆分引入行为漂移] → 纯移动纪律＋全量测试＋第二笔 diff 逐块审查；任何行为差异都视为第一笔未覆盖的路径，补测试而不是默默改。
- [回填文案变化影响模型行为] → 拒绝结果与既有「用户拒绝」同构（granted:false＋恢复提示），模型侧路径已被既有测试覆盖。
- [无 sink 场景从「等待」变「立即拒绝」属行为变化] → 该场景生产不可达（装配总会装 sink），变化方向是从坏到好（悬挂→收束），规格增量如实记录。
- [文件行数不降反升（门面 re-export）] → 接受；目标是职责可寻，不是行数指标（审计明言不以行数为目标）。
