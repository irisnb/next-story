# establish-content-tree-storage Design

## Context

当前作品事实由 Rust/Tauri 后端保管，采用固定双本子结构：`作品文本/草稿本.json` 与 `作品文本/正文本.json` 承载正文，`next-story-system/project.json` 承载作品元信息（`name`、`created_at`、`updated_at`、`version`，当前版本 `2`）。保存采用「一次保存 = 一个一致世代」的事务机制：先把草稿、正文、元信息三份文件整体暂存进 `next-story-system/save-transaction/`，再按 草稿 → 正文 → 元信息 的顺序替换可见文件，元信息是最后的完成标记；`Staged` 阶段直接丢弃，`Committing` 阶段前滚提交。打开作品时先走迁移框架（当前 `PRODUCTION_MIGRATIONS` 为空，版本 2 即最新），再严格校验结构，最后读取内容。同一作品的所有打开、保存、迁移操作通过 `ProjectLocks` 在进程内串行化。

二阶段方向已确认：取消固定的「草稿本 / 正文本」，改由「作品内容树」（文件夹 + 文档）承载作品组织。内容树只是帮助陪想 Agent 理解作品的**后台基础设施**：用户在写作空间里亲手写，通过常驻 AI 面板直接提问；用户不需要配置任何 AI 参考优先级，旧「四级 AI 参考优先级」及继承、覆盖模型已撤出用户概念，未来 Agent 如何选择上下文是未定的内部方案，完全留给后续 change。本 change 只把内容树在 Rust/Tauri 侧落成可靠的作品事实存储地基，不含作品结构页 / 写作空间 UI，不含 DSH 读取作品，不含上下文选择、预加载、检索、摘要、记忆或 Agent 循环。AI 永不写用户文档的永久边界不变，本 change 不新增任何 AI 写文档的能力。

约束与利益相关方：Rust/Tauri 后端是作品数据的可靠保管者，负责内容树、文档保存、格式校验、版本迁移、事务一致性与崩溃恢复等确定性工作；DSH 是作品内容的智能使用者，只能通过受控只读接口取得被允许提供的内容，本 change 不接入 DSH。前端 IPC 契约会因作品结构变化而调整，但本 change 不实现新 UI，前端适配另行 change。

## Goals / Non-Goals

**Goals:**
- 在 Rust/Tauri 侧建立作品内容树的事实存储：文件夹与文档两种节点、父子层级、同一父级内文件夹与文档共享的混合排列顺序、稳定节点 ID。
- 提供创建、重命名、移动、删除（进回收站）与恢复的确定性存储操作，删除与恢复支持完整子树。
- 把「一次保存 = 一个一致世代」的事务、写入前校验与崩溃恢复扩展到内容树结构，覆盖正文保存与结构变更两类事务。
- 通过迁移框架把旧双本子作品原子迁移为根层两篇普通文档（名称保留「草稿本」「正文本」，仅作为普通文档名称），保留正文文字与格式，不保留特殊本子身份，不恢复双本子模型，不额外包裹迁移文件夹。
- 内容树元数据只保存结构信息，不包含任何 AI 参考程度 / 优先级 / 筛选字段；未来 Agent 上下文选择完全留给后续 change。
- 明确 Rust/Tauri 是唯一作品事实写入者，DSH/AI 不接入，不新增任何 AI 写用户文档的路径。

**Non-Goals:**
- 不实现作品结构页 / 写作空间 UI，不实现 F2 重命名的界面交互（本 change 只提供重命名存储操作）。
- 不实现 DSH 读取作品、上下文选择、预加载、检索、摘要、记忆或 Agent 循环；未来 Agent 如何选择上下文是未定的内部方案，完全留给后续 change。
- 不实现回收站的永久清空（本 change 只做「删除进回收站」与「恢复」）。
- 不实现模板、DOCX 导入导出、剧本化/脚本化。
- 不改变单篇文档的 Tiptap JSON 格式（`structured-notebook-storage` 的格式版本 2 保持不变）。
- 不实现任何让 AI 写入、插入、追加、替换、删除或移动用户文档的能力。

## Decisions

### D1：作品结构版本 2 → 3，注册首个迁移步骤

把 `ProjectMetadata::CURRENT_VERSION` 从 `2` 升到 `3`，并在 `PRODUCTION_MIGRATIONS` 注册 `2 → 3` 的迁移步骤。打开作品时：版本等于 3 直接通过；版本高于 3 拒绝（不支持的作品结构版本）；版本低于 3 且存在已注册步骤时逐级迁移，迁移前备份、迁移后校验、失败回滚、幂等。版本 1（旧 `.txt` 本子）仍无迁移步骤，继续被拒绝，与迁移框架出现前的行为一致。

**备选**：不升版本，直接在版本 2 上叠加内容树。**否决**：内容树是破坏性结构变更（固定双本子 → 任意树），必须用版本号表达，否则无法区分新旧布局，也无法让迁移框架正确驱动旧作品升级。

### D2：正文与树元数据解耦的磁盘布局

作品事实分成两类，分开存放：

- **正文（用户文本）**：每篇文档一个文件，放在用户文本区（沿用 `作品文本/` 语义），文件按稳定 ID 命名（如 `作品文本/documents/<id>.json`），内容为 `structured-notebook-storage` 定义的 Tiptap JSON（格式版本 2 不变）。
- **树元数据（结构）**：节点身份、类型、父级、子级顺序、名称，放在系统抽屉（`next-story-system/`）下的独立树元数据文件（如 `next-story-system/content-tree.json`），不包含任何正文，也不包含任何 AI 参考程度 / 优先级 / 筛选字段。
- **作品元信息**：`next-story-system/project.json` 继续保存 `name`、`created_at`、`updated_at`、`version`，不包含正文，也不包含树结构。

解耦的意义：重命名、移动、排序只改写树元数据文件，不触碰正文文件；正文文件由稳定 ID 寻址，与名称、路径无关。这延续了「作品元信息与用户文本分离」的既有原则，并让结构变更事务只涉及树元数据（见 D6、D7）。

**磁盘布局保持实现弹性**：上述目录名、文件名、JSON 字段名是设计草案，具体格式与版本号在实现阶段以代码证据为准确认，不在本 design 中硬编码为不可变契约。唯一固定的是职责边界：正文在用户文本区、树元数据在系统抽屉、作品元信息在 `project.json`。

### D3：稳定节点 ID 与正文寻址

每个节点（文件夹与文档）在创建时获得一个稳定且唯一的 ID（如 UUID 或时间戳 + 进程内计数生成的唯一串）。正文文件按文档 ID 命名，因此：

- 重命名文档不改变其正文文件路径；
- 移动文档不改变其正文文件路径；
- 排序不改变任何文件路径。

ID 只用于内部寻址与父子引用，不面向用户展示。树元数据中所有父子关系、子级顺序、回收站引用都使用 ID，而不是名称或路径。

**备选**：用「父路径 + 名称」寻址正文文件。**否决**：重命名 / 移动会改变路径，导致结构变更必须同时移动正文文件，事务复杂且易错；稳定 ID 让结构变更与正文文件解耦。

### D4：根容器不显示

作品根是一个隐式容器，不是树中的一个节点。根级可直接包含文件夹和文档，它们作为根容器的子项存在。根容器不显示在内容树中，也没有名称或类型。树元数据用一个根级子项 ID 列表表达根级内容。

### D5：同一父级内文件夹与文档共享一个混合排列顺序

每个父级（文件夹或根容器）维护一个有序的子节点 ID 列表。文件夹与文档在同一父级内按该列表混合排列，不按类型分组。排列顺序只由用户控制的排序决定。排序操作 = 重排父级的子节点 ID 列表。

**备选**：文件夹与文档分别维护两个顺序列表。**否决**：与「混合排序」需求冲突，且无法表达文件夹与文档交错排列。

### D6：回收站是元数据级容器，正文文件不移动

删除节点时，把该节点及其完整子树从内容树移入一个**回收站容器**（树元数据内的特殊隐藏容器，不显示在内容树中），正文文件保持原位、仍由稳定 ID 寻址。恢复时把该子树从回收站容器移回其原父级。

- 删除文件夹连同完整子树一并移入回收站；恢复文件夹连同完整子树一并恢复，层级、顺序与名称保持删除前状态。
- 因为正文文件不移动，删除与恢复都只改写树元数据文件，是纯元数据事务，简单且不易出错。
- 回收站容器为每个被删子树保留原父级引用与完整内部结构，以便精确恢复。
- 本 change 不实现回收站的永久清空；永久删除（真正删除正文文件）留待后续 change。

**备选**：删除时把正文文件物理移动到回收站目录。**否决**：需要跨目录移动文件，事务复杂、易在中断时留下半套状态；元数据级回收站让删除 / 恢复成为纯树元数据事务，更安全。

### D7：事务机制泛化，覆盖正文保存与结构变更两类事务

把现有「三份固定文件」的保存事务泛化为「一组文件」的事务，保持「一次保存 = 一个一致世代」与「元信息是最后完成标记」的原则：

- 事务暂存一组文件：受影响的正文文件（如有）、树元数据文件、`project.json`，以及事务清单。
- 事务清单记录阶段（`Staged` / `Committing`）、事务 ID、目标 `updated_at`、用途（正文保存 / 结构变更 / 迁移），以及**暂存文件到目标路径的映射**（因为正文文件按 ID 命名，数量可变）。
- 提交顺序：受影响正文文件 → 树元数据文件 → `project.json`（最后，作为完成标记）。
- 恢复：`Staged` 阶段直接丢弃；`Committing` 阶段按清单记录的映射与顺序替换各目标文件，再清理事务目录。恢复前校验暂存内容与目标 `updated_at` 一致。

两类事务：
- **正文保存**：改写一篇或多篇文档正文文件 + `project.json`（更新 `updated_at`），树元数据不变。
- **结构变更**：创建 / 重命名 / 移动 / 排序 / 删除 / 恢复，改写树元数据文件 + `project.json`；创建时另写一篇新的空正文文件。

**向后兼容**：打开旧版本 2 作品时，先按旧的三份固定文件事务恢复（旧清单格式），再走迁移。恢复逻辑需同时识别旧清单（固定三文件）与新清单（映射式），或按版本分派到对应恢复路径。

**备选**：为结构变更另建一套独立事务。**否决**：两套事务机制重复且易漂移；泛化一套机制统一覆盖正文保存与结构变更，复用既有崩溃恢复与串行化。

### D8：结构变更操作集与校验

提供以下确定性存储操作，全部作为事务执行（见 D7），并在提交前校验完整目标结构：

- **创建**：在指定父级下创建文件夹或文档，分配默认名（与同级冲突时生成不冲突名称，如「未命名文档」「未命名文档 2」）；创建文档时生成空正文文件。
- **重命名**：校验新名称非空、不含当前操作系统非法文件名字符、与同一父级内其它节点不重复；失败则拒绝并保持原名。F2 触发重命名是 UI 行为，本 change 只提供重命名存储操作。
- **移动**：把节点（含完整子树）移动到另一父级（含根级）；禁止把文件夹移动到其自身或任意后代之内（循环检测）；移动后节点及其完整子树保持完整。
- **排序**：重排父级内子节点 ID 列表。
- **删除**：把节点（含完整子树）移入回收站容器（见 D6）。
- **恢复**：把回收站中的子树移回原父级，保持层级、顺序与名称。

打开作品时校验内容树结构：节点类型合法性（文件夹 / 文档）、父子层级合法性（文档无子节点、文件夹可含子节点、无循环）、同级名称唯一性、排列顺序完整性（子节点 ID 都存在、无孤儿、无重复），以及所有被引用正文文件存在且为合法 Tiptap JSON。校验失败拒绝打开并显示中文可读错误，不把失败内容替换为空白或默认结构，不覆盖任何原文件。

### D9：旧双本子作品原子迁移为根层两篇普通文档

注册 `2 → 3` 迁移步骤：读取 `作品文本/草稿本.json` 与 `作品文本/正文本.json`，创建内容树根层两篇普通文档，名称保留「草稿本」「正文本」。这两篇文档只是名称恰为「草稿本」「正文本」的普通文档：不保留特殊本子身份，也不恢复双本子模型；正文保留原 Tiptap JSON 文字与格式（格式版本 2 不变）。不额外包裹一层迁移文件夹。

迁移通过迁移框架执行：迁移前备份、迁移后校验、失败回滚、幂等。迁移是**原子切换**——在事务内从版本 2 布局切换到版本 3 布局：写入两篇新正文文件、写入树元数据、把版本号升为 3，并移除旧的 `草稿本.json` / `正文本.json`（旧内容已由迁移框架备份，可人工恢复）。迁移中途崩溃后再次打开时，由事务恢复机制恢复到一致有效世代。

### D10：Rust/Tauri 是唯一作品事实写入者，DSH/AI 不接入

所有正文保存与结构变更都通过 Rust/Tauri 后端执行，Rust 是唯一作品事实写入者。本 change 不注册任何可被 AI 调用的写文件工具，不新增任何 AI 写用户文档的路径。DSH 不接入本 change：不读取作品、不参与存储、不获得任何写入能力，也不实现任何上下文选择、预加载、检索、摘要、记忆或 Agent 循环相关代码。AI 输出只能留在用户文档之外，由用户亲手复制、编辑并保存后才成为作品内容。

## Risks / Trade-offs

- [事务泛化引入回归] → 复用既有事务框架并扩展，保留旧清单格式的向后兼容恢复路径；用故障注入测试覆盖 `Staged` / `Committing` 各阶段与结构变更中断，确保不出现部分应用的结构。
- [迁移删除旧本子文件有数据风险] → 迁移框架先备份再迁移，旧文件内容保留在备份目录；迁移失败回滚恢复原文件；迁移幂等，崩溃后可再次打开恢复一致世代。
- [迁移后「草稿本」「正文本」名称可能被误认为特殊本子] → 迁移后两篇文档只是名称恰为「草稿本」「正文本」的普通文档，不保留特殊本子身份，也不恢复双本子模型；名称可在内容树中自由重命名。
- [回收站为元数据级，正文文件长期留在用户文本区] → 被删文档正文文件仍占用磁盘且不随删除消失；本 change 不实现永久清空，需在后续 change 处理；删除 / 恢复的简单性与安全性优先。
- [磁盘布局草案可能偏离实现] → 明确布局为设计草案，实现阶段以代码证据为准确认，避免未经代码证据硬编码；职责边界（正文 / 树元数据 / 作品元信息分离）固定不变。
- [前端 IPC 契约变化] → 本 change 只改 Rust 存储层，前端适配另行 change；需在归档时同步更新 `desktop-project-lifecycle` 与 `structured-notebook-storage` 规格，避免前后端契约漂移。

## Migration Plan

1. 实现内容树存储层（树元数据模型、稳定 ID、正文文件寻址、校验、事务泛化）。
2. 实现结构变更操作集（创建 / 重命名 / 移动 / 排序 / 删除 / 恢复）与回收站容器。
3. 把 `ProjectMetadata::CURRENT_VERSION` 升为 3，注册 `2 → 3` 迁移步骤（旧双本子 → 根层两篇普通文档「草稿本」「正文本」，无特殊本子身份）。
4. 更新打开 / 保存 / 事务恢复路径以支持版本 3 与两类事务，保留旧版本 2 事务的向后兼容恢复。
5. 更新 `desktop-project-lifecycle` 与 `structured-notebook-storage` 规格以反映新结构。

**回滚策略**：迁移框架在迁移前备份，失败回滚恢复迁移前文件；若回滚失败，保留备份目录并给出人工恢复路径。版本 3 作品无法回退到版本 2（破坏性升级），但迁移前备份提供数据安全网。

## Open Questions

- 树元数据文件与正文文件的**确切磁盘布局**（目录名、文件名、JSON 字段名、版本号）——实现阶段以代码证据为准确认，不在本 design 硬编码。
- 回收站的**保留策略**（是否限制数量 / 大小、是否自动清理）——本 change 只做删除进回收站与恢复，永久清空与保留策略留待后续 change。
- 打开作品时是否校验**孤儿正文文件**（树中未引用的正文文件）——本 design 倾向不拒绝，仅作为实现期确认项。
- 结构变更是否更新 `project.json` 的 `updated_at`——本 design 倾向每次事务都更新（与现有保存行为一致），实现期确认。
- 迁移后旧 `作品文本/草稿本.json` / `正文本.json` 的移除是否需要在迁移报告中向用户说明——实现期确认。
