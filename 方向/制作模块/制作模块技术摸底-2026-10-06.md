## 0. 一页摘要

- **提示词现状**：全部系统提示词由 Rust 侧一个总装函数按四层硬编码拼出（红线 / 入场姿态 / 语境 / 工具使用），以**第一条用户消息的文本前缀**方式发给模型；Rust 从不使用 system 角色。追问轮不重发提示词，只发增量问题＋本轮材料。
- **「多思维链路」的雏形已存在**：入场姿态层已按「直接提问 / 选区召唤」二选一分叉——这就是一个两值的"组装方式"枚举；语境层是**故意留空的扩展点**（代码注释自证）。结构上离方向很近，但配置化为零：提示词 100% 写死，无任何外部承载。
- **DSH 侧**：模型真正收到的 system prompt 是 DSH 框架默认的英文「你是一个编程助手」persona，Next Story 未覆盖；技能（Skills）机制四件套已随依赖装入仓库但被三层真相源＋两端契约测试锁死；skill 的内容格式（Markdown＋frontmatter＋纯指令正文，工具不随 skill 走）与「制作成果＝预组装提示词」形态合拍。
- **两个独立小问题被顺带发现（未立项，仅记录）**：①信封身份错位（见 §4）；②长对话压缩后红线前缀是否保留未验证（见 §4、§5）。
- **在 §9 清单上的位置**：§9.4 主体完成；下一步＝§9.2「走通一例」（需用户提供真实案例）。

## 2. 已核实事实（合并两路侦察）

### 2.1 提示词组装链路（Rust 宿主侧）

1. 系统提示词唯一源头是 `compose_system_prompt`（`src-tauri/src/llm_config/generate.rs:83-89`），四层硬编码、两值入口分叉，无任何配置读取。
2. 语境层 `context_clause` 恒为空字符串，注释明示为未来扩展点（generate.rs:55-59）。
3. 入口枚举 `PromptEntry` 仅 `DirectQuestion` / `Summon` 两值（generate.rs:19-24）——当前唯一的"组装方式"分叉维度。
4. 系统提示词以**首条 user 消息文本前缀**方式进入模型，Rust 从不发 system role（`src-tauri/src/dsh_driver.rs:1223-1227`；`sidecar/driver/protocol.json:16-27`）。
5. 追问轮无系统提示词（靠常驻会话历史），只发增量问题＋本轮重新组装的语境块（generate.rs:679-689）。
6. 三入口装配差异：常规首轮＝DirectQuestion 提示词＋问题＋授权选区＋语境块；召唤首轮＝Summon 提示词＋冻结选区、**不经过常规取材**、补读工具被工具路由硬门禁关闭；追问＝只发增量＋语境块（`src-tauri/src/ai_orchestration.rs:423-561`，召唤门禁 444-461）。
7. 语境块三段式（关注文档正文→目录投影→相关片段）硬编码于 `compose_context_text`（`src-tauri/src/project/story_search.rs:447-483`）。
8. 前端显示历史标签（`src/ai-feature.ts:72-95`）与后端 `direct_question_user_content`（generate.rs:623-628）是同一格式的**两处独立硬编码**，靠注释人工对齐。
9. legacy 无状态链路 `build_task_string`（generate.rs:460-545）前端已不调用，但 Tauri 命令仍注册（`src-tauri/src/lib.rs:982`）。
10. **零配置化**：`llm_config` 只存 API 地址 / Key / 模型 / max_tokens（`src-tauri/src/llm_config/mod.rs`），提示词无任何外部配置文件或数据库承载。
11. 崩溃恢复把同源提示词前缀拼回首轮重放文本（generate.rs:386-391, 412-416）。

### 2.2 DSH 技能与工具边界（驱动侧）

12. `sidecar/driver/denied-capabilities.json` 共 58 条拒绝能力，`skill` / `skill-filesystem` / `tool-skill` 在列且 `gateway:true`（22-24 行区段）；`skill-badge` 不在清单内、由 profile 层在 yaml 中禁用（`sidecar/driver/cordis.driver.yaml:169-171`）。
13. 禁用唯一表达＝插件条目 `disabled: true`，由 `sidecar/driver/gen-config.mjs:30-39` 从 denied-capabilities.json 静态生成 yaml；Rust 侧 `FORBIDDEN_TOOL_IDS`（`src-tauri/src/capability_gateway.rs:19-38`）与 gateway=true 子集由**两端契约测试双向钉死**。
14. skill 内容格式＝`<name>/SKILL.md`（或平铺 md）＋YAML frontmatter（必填 name＋description），**正文即指令文本，工具不随 skill 走**——模型经唯一 `skill` 工具按名加载（`sidecar/node_modules/@deepseek-ai/dsh-skill-filesystem/README.zh.md:29-59`、`dsh-tool-skill/README.zh.md:9-31`）。
15. skill 调用策略为 `{modelInvocable, userInvocable}` 四组合；存在运行时嵌入式注册接口 `ctx.skills.register()`（rank 250），driver.mjs 已有同型先例（工具注册在 `agents.create` 的 `setup` 回调里，`sidecar/driver/driver.mjs:242-246`）——理论上可编程注册 skill 而不启用文件系统 provider。
16. story-* 四件套：驱动侧纯桥接声明（driver.mjs:145-234，"本进程不读取任何作品文件"），执行全在 Rust 宿主（`src-tauri/src/story_tools.rs`），窄化只读接口＋逐次校验＋轮内限额＋零写回。
17. DSH 真 system prompt 由已启用的 `system-prompt` 插件组装（cordis.driver.yaml:360-365）：harness 身份段＋部署 persona 段（当前为英文 coding agent 文案）＋插件工具引导段。
18. `agent-instructions` 插件处于启用状态（cordis.driver.yaml:159-162，maxBytes 65536），但其指令加载依赖可选 `ctx.fs` 提供方，驱动装配里没有任何 fs provider——按其 README 自述应惰性为无操作。
19. 协议 `start_session.system_prompt` 字段：驱动侧接受并存储（driver.mjs:397）但 `buildSeedEvents` 的 `system` 参数**从未被使用**（driver.mjs:257-302）；Rust 侧根本不发该字段（dsh_driver.rs:58-60）——**宿主→驱动的 system_prompt 通道是死路径**。
20. 仓库内无任何 DSH skill 定义样例；`.dsh/skills`、`.agents/skills` 目录不存在；无用户提示词成果的存储位置或宿主侧管理代码。

## 3. 独立发现的小问题（未立项，仅记录）

- **P1 信封身份错位**：模型真正的 system prompt 是 DSH 默认英文「coding agent」persona，与产品定位（剧本创作陪想）不符；产品宪法红线只是贴在第一条用户消息开头。出处：cordis.driver.yaml:360-365（已核实配置）；模型实际收到的完整 system 段落组合未抓包验证（见 §5-2）。
- **P2 长讨论红线漂移（待验证）**：追问轮不重发红线页；长对话压缩由 DSH 框架承担，**压缩后是否保留首条 user 消息里的红线前缀未验证**。若丢失，长讨论后半段实际上下文中无红线层（目前靠每轮语境块的诚实声明兜底）。这直接影响「思维链路该怎么发」的设计选择（信纸前缀 vs 真信封通道）。

## 5. 对制作模块方向的含义（解读，非拍板）

- **结构上离「多思维链路」很近**：四层纯函数＋两值入口枚举就是一个极简版"组装方式"系统；未来多链路大概率是把这个枚举广义化，语境层是现成预留空位。
- **配置化为零是真实的从零建设**：制作成果的存储、管理、启用入口、版本与生效规则全需新建；但动刀位置非常集中（总装只有 `compose_system_prompt` 一处）。
- **Skills 是候选承载且形态合拍**（指令文本为主体、工具不随行），但启用要同时改三处真相源（denied-capabilities.json ＋ 重新生成 yaml ＋ Rust FORBIDDEN_TOOL_IDS）＋两端契约测试——这是当初设计的安全双保险，不是技术障碍；另有运行时注册路径可能绕开文件系统 provider（待实测）。
- **红线发送方式是设计决策点**：协议里预留的 system_prompt 通道两端各差一步（宿主不发、驱动存而不用）；接通它还是继续 user 文本前缀，属于方向决策，须在制作模块设计中一并考虑（关联 §3 P2）。
- **选型未定提醒**：Agent / Skills 仍是候选技术（共识文档 §1），本文只记事实，不做方案设计、不预定架构。

## 附录 A：侦察一原始报告（提示词组装链路）

### `generate.rs` 中的提示词分层（唯一系统提示词源头）

组装器 `compose_system_prompt`（generate.rs:83-89）按固定顺序拼 4 层，全部为 Rust 内硬编码字符串、无任何配置读取：

| 层 | 行号 | 顺序 | 内容概括 |
|---|---|---|---|
| 红线层 `constitution_prompt()` | generate.rs:32-37 | 1 | 产品铁律落地：不改文档、不代写、不判断好坏、只依据实际提供材料、不冒充已读、无跨讨论记忆、追问语义、禁 Markdown/HTML 纯文本输出。两个入口共用同一份 |
| 入口层 `entry_stance(entry)` | generate.rs:40-53 | 2 | 按 `PromptEntry` 枚举二选一：`DirectQuestion`（有问题+可选选区）vs `Summon`（只有冻结选区、无问题），各给一段立场句 |
| 语境层 `context_clause(entry)` | generate.rs:57-59 | 3 | 恒为空字符串，注释明说"先立结构留空，未来动态化时在此填入"——现成的扩展点雏形 |
| 工具层 `tool_reading_prompt(entry)` | generate.rs:64-78 | 4 | 按入口二选一：DirectQuestion 版介绍 story-list/read/search + story-request-reading 授权流；Summon 版明说禁用补读工具 |

入口枚举 `PromptEntry`（generate.rs:19-24）：仅 `DirectQuestion` / `Summon` 两个值，这是当前唯一的"组装方式"分叉维度。

user 内容组装器（同样硬编码）：
- `first_user_content` 选区+可选探索角度（generate.rs:613-620，旧 legacy 链路）
- `direct_question_user_content`「用户问题：…\n\n重点参考材料（可选）：…」（generate.rs:623-628）
- `summon_user_content` 纯选区原文无标签（generate.rs:632-634）
- `compose_message_text` 按消息种类拼最终 task（generate.rs:645-691）：`First` = 系统提示词+问题+授权选区+语境块追加在尾部（662-665）；`SummonFirst` = Summon 提示词+选区，语境块被忽略（668-677）；`FollowUp` = 只有增量问题+语境块，无系统提示词（679-689，历史由常驻会话维护）
- 旧无状态链路 `build_task_string`（generate.rs:460-545）：系统提示词+全量历史按「用户追问：/你的上一次回应：」角色标注拼单字符串——legacy 命令路径，前端已不再调用（`src/` 全目录 grep `generate_ai_thinking` 零命中），但 Tauri 命令仍注册着（lib.rs:982）
- 崩溃恢复前缀 `replay_prompt_prefix`（generate.rs:386-391）：按 `ReplayOrigin` 把对应入口的系统提示词拼到重放首轮 user 文本最前（generate.rs:412-416）

### `ai_orchestration.rs` 材料装配

装配流水线（全部在命令层 `ai_send_message`，ai_orchestration.rs:423-561）：

1. **选区授权**：`authorize_selection`（114-161）→ `authorize_selection_sync`（171-216）：作品锁+受控只读 `read_material` 校验身份/可见性/版本/快照，选区必须落在授权正文内，失败关闭
2. **授权材料重写**：`authorized_selection_text`（243-261）+ `apply_authorized_selection`（266-330）：原始 `selected_text` 被替换为受控材料子串，提示词组装只见授权内容
3. **常规取材**：`assemble_context_under_lock`（570-589）→ `project::assemble_round_context`（`src-tauri/src/project/story_search.rs:534-585`）：关注文档现场材料（已保存正文或校验快照）+ 目录投影 + 跨文档字面检索，产出 `RoundContext { context_text, provenance }`
4. **语境文本格式**：`compose_context_text`（story_search.rs:447-483），三段式：`关注文档《名》正文：…` → `作品可见文档目录（只用于了解结构…）：- 名` → `相关片段（候选参考，不是作品事实…）：- 《名》：片段`

三入口装配差异：
- **常规首轮 `First`**：DirectQuestion 系统提示词 + 问题 + 授权选区（`material`）+ 语境块（有关注文档身份才组装，失败关闭不静默回退，492-543）
- **选区召唤 `SummonFirst`**：Summon 系统提示词 + 冻结选区；不经过常规取材，语境块恒 None（542）；补读工具被工具路由硬门禁关闭（`register_round` 第四参数，444-461）
- **追问 `FollowUp`**：无系统提示词（靠会话历史），只发增量问题 + 本轮重新组装的语境块
- 讨论身份注册进工具通道（444-461）：未携带讨论身份的会话清路由，补读调用一律失败关闭

### 其他注入系统提示/指令的位置（全集）

- **DSH 框架层 persona**：`cordis.driver.yaml:360-365` 启用 `@deepseek-ai/dsh-system-prompt` 插件，persona 硬编码英文 "You are a coding agent powered by the {{model}} model. Your working directory is {{cwd}}."——这是真正以 system 身份进模型的提示词，Next Story 代码未覆盖它
- **agent-instructions 插件**：cordis.driver.yaml:159-162 启用，maxBytes 65536，未配置内容（无 fs provider 时惰性）
- **其余 DSH 插件全部 disabled**（plan-mode/persona 之外的工具、子代理、web、todo 等均关）
- **工具描述即指令**：四件套工具的中/英文 description 硬编码在 `sidecar/driver/driver.mjs:147-180`（STORY_TOOL_META），每会话注册（driver.mjs:199-234）；实现在 Rust 宿主（story_tools.rs）
- **面向模型的恢复提示**：`RECOVERY_READING_UNAUTHORIZED` 英文常量，`story_tool_channel.rs:587`，经 tool_result 拒绝帧回给模型（protocol.json:84-85 的 `recovery` 字段）
- **前端唯一提示词样文本**：`src/ai-feature.ts:72-95` `historyTurnsOf` 用「用户问题：/重点参考材料（可选）：」标签构造显示历史投影（崩溃恢复重放用），与后端 `direct_question_user_content` 格式手动保持一致（双处硬编码、靠注释对齐）

## 附录 B：侦察二原始报告（DSH 技能与工具边界）

### 拒绝/允许能力清单与禁用表达

- denied-capabilities.json（装配禁用清单单一真相源）：每条 `{id, group, gateway}`；`gateway: true` =「危险工具」子集，与 Rust `capability_gateway::FORBIDDEN_TOOL_IDS` 一一对应，两端契约测试双向断言。skill 相关三条（`skill`、`skill-filesystem`、`tool-skill`）全部 `gateway:true`；`skill-badge` 不在清单但在 yaml 中 disabled（profile 层禁用）。

### DSH 里 skill 的定义/加载/启用

- 分四包：`dsh-skill`=纯注册表服务（`ctx.skills`，运行时嵌入式注册 rank 250）；`dsh-skill-filesystem`=本地文件系统 provider；`dsh-tool-skill`=面向模型的目录消息 + `skill` 工具；`dsh-skill-badge`=客户端 UI 徽标。
- 内容格式：`<name>/SKILL.md` 目录包或平铺 `<name>.md`；YAML frontmatter 必填 `name`（kebab-case）+ `description`，可选 `whenToUse`、`metadata`、`disable-model-invocation`、`user-invocable`；正文即指令文本，资源（references/scripts/assets）只给指引不自动加载——**提示词为主体，工具不随 skill 走**，模型通过唯一的 `skill` 工具按名加载。
- 发现根与优先级（rank 越小越近越赢）：`.dsh/skills`(100) → `.agents/skills`(200) → customSkillDirs(300) → `<dshHome>/skills`(400) → `<agentsHome>/skills`(500)。
- 调用策略：每个 skill 必带 `{modelInvocable, userInvocable}` 四组合；`disable-model-invocation: true` 的 skill 只能经用户手势注入。
- 启用路径：yaml 去掉 disabled + 重新生成；但 Rust 侧 FORBIDDEN_TOOL_IDS 拦截，须同步改真相源+常量+两端测试。
- 仓库内无任何 DSH skill 样例：`.dsh/skills`、`.agents/skills` 不存在；sidecar 源码零处 import skill 包。

### 工具开放边界（story-* 四件套）

- 驱动侧（桥接，不读文件）：driver.mjs:145-180 定义 STORY_TOOLS + 中文 description + JSON Schema；registerStoryTools（driver.mjs:199-234）在 `agents.create` 的 `setup` 里注册进 Agent 私有作用域。execute 只做 emit tool_call 事件 → 挂起等宿主 tool_result 回填。「本进程不读取任何作品文件」（driver.mjs:141-144）。

### 指令注入层次

- Rust 宿主把「系统提示词」发在 user 消息文本里，不是 system 角色（见附录 A）。

### 未来承载「用户制作提示词成果」的现有挂载点与缺口（仅事实）
