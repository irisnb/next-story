# verify-import-fidelity-ui Design

## Context

`fix-import-fidelity` 于 2026-10-03 归档，四项 P1 修复、真实样本回归与规格同步完成，但任务 6.2 在用户拍板下**移交而非通过**归档：三个复杂样本的真实 UI 导入与冻结预期比对、三个新增损耗标签的 UI 链路、`cargo clippy --all-targets`／`cargo fmt --check`、独立规范审计全部未完成（归档 `openspec/changes/archive/2026-10-03-fix-import-fidelity/验收记录.md` §5、§6.4）。本 change 只做这批验收，不触碰产品行为。

已具备的前提（2026-10-03 核对均存在）：

- 归档 §6 已在三个复杂样本**首次真实 UI 导入之前**冻结源推导预期、字面源、哈希与允许损耗计数（§6.0 哈希核对相符；§6.1 Markdown、§6.2 DOCX、§6.3 FDX）。
- 执行门槛文档：`docs/superpowers/plans/2026-10-03-fix-import-fidelity-acceptance.md`（任务 1–4 与证据要求）。
- 输入与辅助清单已收纳于本变更 `verification/`：`inputs/acceptance-complex.md`；`expected/`（三份 manifest 与 `fdx-acceptance-expected.json`）；`tools/`（期望生成脚本与 UI 探针）。DOCX 夹具及其生成脚本同目录于 `src-tauri/tests/fixtures/docx/`；FDX 源样本在 `src-tauri/tests/fixtures/fdx/`（只读）。材料丢失时可按归档 §6 内嵌内容重建并核对哈希。
- 验收对象＝**当前工作区构建**（含尚未提交的 fix-import-fidelity 实现改动）；提交与推送须另行获得用户确认。

先例参照：`2026-09-22-app-real-chain-validation`（应用级真实验证，证据落档 `verification/`）、`2026-09-09-dsh-capability-integration-validation`（验证型能力规格）。

## Goals / Non-Goals

**Goals:**

- 三个复杂样本逐一走真实 UI 路径（原生选文件 → 预检 → 确认导入 → 编辑器比对 → 保存重开 → 视觉抽查），以归档 §6 冻结清单为唯一预期来源做**全量**比对，不靠计数或抽样。
- 三个新增损耗标签（`list_overflow_degraded`／`symbol_dropped`／`style_degraded`）在预检中的实际呈现逐项核对：样本触发的必须呈现计数与详情；未触发的不虚报。
- 质量门槛复跑并如实分账：全量测试、限定范围 Clippy、构建、`cargo clippy --all-targets`、`cargo fmt --check`；未通过的不得宣称通过。
- 独立规范审计 DOCX 符号映射、样式覆盖与编号规则；规范依据独立于实现与合成测试。
- 全部实测、偏差、矛盾与未验证项进入本 change 验收记录，供用户逐项判收；完成与否以证据为准。

**Non-Goals:**

- 不改产品代码、依赖或数据格式；验收中发现的产品缺陷不在本 change 内修复（另行立项，用户拍板）。
- 不重写、不移动、不改动归档 `验收记录.md` §6 冻结清单与既有证据；不以实测结果反推或修订预期。
- 不把浏览器级 `invoke`、文件输入注入或无头流程当作 UI 证据。
- 不重复向既有作品导入已测过的小样本；不使用 `C:\Users\Administrator\Desktop\test\导出验收-20261001`。
- 不处理审计 P2 项；不因质量门槛的既有范围外差异顺手改动范围外文件。
- 未经用户确认不提交、不推送、不删除任何归属未明的样本目录。

## Decisions

### D1. 预期唯一来源＝归档 §6 冻结清单（只读引用）

验收预期、字面源、哈希与允许损耗一律引用归档 `验收记录.md` §6，本 change 不复制、不改写。实测与预期不符时，记录「预期 vs 实测」原始对照，冻结清单保持原样——清单是验收的标尺，不是验收的产物。

### D2. 真实 UI 路径为唯一有效证据

每个样本必须经生产应用的**原生文件选择器**选文件、可见预检卡片（字数／段落数／损耗标签与计数／拆分选项）与可见「确认导入」按钮完成。自动化不可靠时由用户在真实选择器中选择确切路径；浏览器级调用或替换文件输入只能作辅助观察，不能充当 UI 证据。预检与确认前记录拟导入文件哈希与目标树，确认后记录新增文档 ID／名称与既有条目不变。

### D3. 目的地＝新鲜可弃作品

每轮导入前确认目的地是**新鲜可弃**作品（空树或专用测试作品），绝不用既有用户作品或 `导出验收-20261001`；导入前后记录树行差异。顺序上先建立基线，再逐格式导入；每格式导入后核对该样本文档，不混入其他样本结果。

### D4. 全量比对与保存重开

比对以**完整文本序列**为准（逐条按序对照冻结预期），并按样本特征核对：Markdown 列表层级／起点与溢出降级位置；DOCX 符号映射、样式级联（docDefaults→段落样式链→字符样式→直接属性）与编号续算／重置／覆盖；FDX 双栏对白拆分顺序与代表性格式。随后经生产 UI 保存、关闭并重开作品与文档，重复全文与关键格式断言，并对开头、中段、结尾及每个结构转换处做视觉抽查，记录截图或确切 DOM 观察及验证限制。

### D5. 质量门槛如实分账，不混淆范围

必跑：`cargo test --quiet`（src-tauri）、`npm run test:frontend -- --run`、`cargo clippy --lib --bins --tests -- -D warnings`、`npm run build`；复跑并如实报告 `cargo clippy --all-targets -- -D warnings` 与 `cargo fmt --check`。既有范围外差异（如 `src-tauri/examples/docx_read_spike.rs`、`src-tauri/src/project/fdx_import.rs`）与当前范围问题分开记录；不为清除门槛而擅改范围外文件，也不以门槛结果替代 UI 证据。

### D6. 独立规范审计的规范依据独立

DOCX 符号映射、样式覆盖与编号规则由独立于实现作者的审计核对；结论须引用规范来源（OOXML/ECMA-376）或冻结预期，不得以产品导入器输出或合成测试本身当规范依据。审计发现与既有规格的出入记录为 finding；是否修复另行走变更流程。

### D7. 偏差与缺陷的分流

验收偏差（预期与实测不一致）如实入档并保持显式；疑似产品缺陷**停止扩大该样本的验证范围、记录可复现证据**，由用户拍板是否另行立项修复。本 change 不静默修复、不静默调整预期、不勾销未验证项。

## Risks / Trade-offs

- [原生选择器自动化不可靠] → 用户在场手动选择（慢但真）；不注入、不降级为浏览器协议调用，宁可如实记录「未取得该证据」。
- [临时目录样本与辅助清单可能丢失] → 归档 §6.1 有逐字节字面源与哈希，可重建后用 §6.0 哈希核对；执行前先核对存在性与哈希。
- [验收对象是未提交工作区，可能与最终提交不一致] → 验收开始时记录 git 状态（rev＋dirty 清单）；如验收后代码变动，相关证据失效需重取，不把旧证据套用到新构建。
- [质量门槛存在既有失败] → 分账记录（范围外／当前范围），未通过项不宣称通过；是否修复由用户另拍。
- [长会话中应用崩溃／重启] → 已有崩溃恢复与讨论重放能力；按生产行为如实记录，重开结果以实际观察为准。
- [UI 观察覆盖有限（截图／DOM 不是全量渲染证明）] → 记录确切观察范围与限制，声明不超出证据边界。

## Migration Plan

不支持数据迁移。回滚＝终止验收、保持所有未验证项未勾选；不修改产品代码与归档记录，无残留副作用（测试作品为可弃）。

## Open Questions

- 「新鲜可弃作品」的具体位置与创建方式（执行时与用户确认，绝不复用既有作品）。
- 视觉证据在自动化受限时的最低接受形态（截图文件落点与命名，或确切 DOM 记录格式）。
- 独立规范审计的执行方式与范围边界（由独立子代理承担；发现 finding 的处置是否当场拍板）。
