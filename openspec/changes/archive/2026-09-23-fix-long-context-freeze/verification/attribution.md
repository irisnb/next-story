# 归因台账（attribution.md）

> 任务 1.5 产出。三路并行源码调查（2026-09-23）：A＝DSH 压缩插件研读、B＝agent-loop 与会话日志研读、C＝宿主挂起语义与装配审计。本档为静态归因结论；实弹判别项单列第七节。

## 一、结论速览

**冻结 = 我方 Rust 宿主的结构洞（H1，代码级坐实）× DSH/端点在长上下文下的停滞（H2，触发侧，子变体待实弹判别），并叠加名额烧伤放大器（H3）。** 压缩链（原始首要嫌疑）经 A 路排除为 8b 冻结的触发因素（H4 配置缺陷使压缩实际上从未触发）。

## 二、观察基线（8b，全部四项签名）

1. 无流式输出、无错误、状态点保持生成态（「正在思考…」）；
2. 持续 6 分钟以上，计时异常值 165／292 秒（常态总时长 5–40 秒），均以手动停止收场；
3. 间歇性：同讨论三轮冻结、后半夜自愈一轮；同时段新讨论同材料 3–6 秒正常；
4. 手动停止始终有效。

## 三、假设台账

### H1　Rust 宿主挂起分支无超时（结构洞）——**成立，代码级坐实**（C 路）

- `is_suspended` 唯一置位点：`dsh_driver.rs:610`（路由到 `ToolCall` 事件即置位，先于 sink 存在性检查——sink 为 None 工具被丢弃时挂起标志也已立起）。
- 清除点仅三处：终态事件（`:593`）、带 message_id 的 Error（`:636`）、`send_tool_result` 回填后（`:818`）。
- 等待循环（`:1089-1148`）：180 秒 deadline 到期时若挂起中 → 裸 `rx.recv()` **无任何计时**（`:1096`）；**resume 不唤醒该线程、流式 Delta 不进等待通道（`:565-584` 只发 sink）**——工具结果回填后若 DSH 停滞（或慢），超时永不复燃。
- 推演排除法：非挂起的完全静默路径最迟 ~190 秒必报 Timeout（`:1113-1123` cancel＋10 秒宽限）——与 292 秒无错误观察矛盾，排除。**唯一能同时满足四项签名的宿主路径就是挂起分支**。
- 判死条件（已满足）：代码路径审计穷尽替代解释。剩余不确定仅「前端是否吞错误」——已被排除法绕开（若超时错误发出，宽限逻辑必然返回，前端状态应由错误事件收尾）。

### H2　DSH／端点在长上下文下停滞（触发侧）——**成立（必然有一侧停滞），子变体待实弹判别**（A/B 路）

冻结轮的停滞来源候选（按当前权重）：

- **H2a　真实 LLM 请求挂在长上下文预填充上**：glm-5.3 不在 llm-deepseek 模型目录 → 回退 `defaultContextWindow = 1,000,000`（`dsh-llm-deepseek/lib/index.js:411,513`），压缩阈值 = 80 万 token，17 轮讨论（估 2–5 万 token）**从未触发压力压缩**；冻结发生在工具回填后的续跑请求（本身就是全量长上下文重放）。
- **H2b　SSE 保活注释击穿 5 分钟空闲看门狗**：适配器看门狗是「逐读空闲」且 SSE 注释会 `watchdog.pulse()` 重置（`dsh-llm-deepseek/lib/index.js:544-546`）——若智谱网关在排队/预填充期间周期发保活注释，连接活着但无内容增量，TIMEOUT 永不触发，可解释「超过 5 分钟仍静默」。**源码侧无法确证智谱是否发注释，标注不确定，实弹可判别。**
- **H2c　压缩摘要请求挂起**：机制上存在（压缩 = 对同端点的一次 ~84% 全量重放请求，失败不冻结、**挂起**才冻结，`compaction-basic/lib/index.js:301,780-793`），但 H4 表明 8b 冻结时压缩大概率未触发——降为次要。
- 注意：165–292 秒 < 300 秒看门狗，也可能是「首字节极慢、本会完成」——8b 一轮后半夜自愈与此相容。**H1 修好后（有界等待＋诚实报错），「慢」与「死」对用户不再有区别——都变成有限等待＋可重试。**

### H3　冻结轮永久烧伤全局并发名额——**成立，代码级坐实**（C 路）

`GenerationPermit`（RAII，`dsh_driver.rs:516-533`，acquire 于 `:1077`）被阻塞线程持有——冻结轮永不返回则名额永不释放。**「连续三轮冻结」＝ 烧 3/4 名额**，第四路冻结将使全应用拒绝一切生成（只能重启）。H1 修复（等待有界返回）自动治愈 H3。

### H4　contextWindow 误报 100 万（疑似配置缺陷）——**核实为不成立：默认值近似正确，无需修补**（lib-1 权威查证，2026-09-23）

- 原怀疑链：runtimePatches 只补模型名/baseURL/thinking/maxTokens（`driver.mjs:104-113`），未补 contextWindow → glm-5.3 按默认 100 万窗口计 → 压缩阈值 80 万 token → 疑似压缩从未运行。
- **权威事实反转**：智谱官方文档明确 glm-5.3 上下文窗口＝**1M（1,048,576）**、最大输出 128K（131,072）——模型卡片（docs.bigmodel.cn/cn/guide/models/text/glm-5.3）与模型概览表双页一致；coding 端点无独立的上下文数值（端点适用性为「模型级官方声明＋端点级无覆盖」的高置信推断）。DSH 回退默认 1,000,000 与官方 1,048,576 仅差 4.6%，对 0.8 阈值（80 万 vs 83.9 万）无实质影响。
- **结论**：这不是缺陷——讨论规模（数万 token）远低于 80 万阈值，压缩按 DSH 设计本就不应触发；「长上下文越聊越易挂」的压力来自端点侧重放全量历史的真实延迟/停滞，由 H1 修复（有界等待）承接。**不修配置。**
- 顺带登记（观察项，不动作）：①我方 patch `thinking:"disabled"` 与官方「思考始终开启（`thinking.type` 仅支持 enabled）」有出入——8b 实测能正常产出，容忍但记录；②coding 套餐对非指定工具环境返回错误码 1113——实测未被拦，遇 1113 时应识别为套餐环境限制而非参数错误；③SSE 保活注释行：官方文档无任何说明（未找到文档化证据），H2b 无法从文档侧证实或证伪。

## 六、停滞窗口校准提案（任务 3.2 输入）

- 基线（8b 42 条）：首字 0.9–59.7 秒（中位约 3 秒，59.7 含驱动冷启动）；常态总时长 5–40 秒；异常值 165–292 秒全部冻结轮。
- 提案：**STALL_WINDOW = 180 秒事件间隔静默**。依据：约为最差正常总时长的 4.5 倍、与既有 REQUEST_TIMEOUT=180 秒数值一致（语义统一：「180 秒什么都不发生＝停滞」）；授权等待豁免；内部常量、不做用户设置项。实现时可注入短窗口供测试。

## 七、实弹判别项（并入修复后验证窗口，任务 2 调整依据）
