01 / 范围与约束

这份报告服务于一个具体判断：当前原生 textarea 是否已经足够，何时值得做轻量增强，什么情况下才需要迁移编辑器或引入剧本解析器。

先画边界：报告不是 OpenSpec，不代表采用任何项目，也不改变 Next Story 的产品铁律。草稿本和正文本仍由用户亲手产生内容；AI 输出永远是两个本子之外的临时材料，不能插入、追加、替换、改写、删除或移动其中任何字符。

比较对象分为五组：原生 textarea 兼容增强、线性编辑器、结构化编辑器、剧本解析器，以及当前方案基准。版本和发布时间以制作日 npm 注册表现场值为准；本稿没有把无法现场锁定的数字填成猜测值。

02 / 先看结论

保留基准

先保留原生 textarea

现在保存的就是纯文字，AI 也靠 `selectionStart/End` 记住选区。原生输入法、复制粘贴和文件保存的路最短。没有明确痛点，换编辑器反而先增加风险。

轻量增强

有痛点再试小包

OverType、textarea-markdown-editor、headless-mde 可以用来试快捷键、预览或命令。但要先证明它们不会打乱选区，也不会把作品变成另一种格式。

线性迁移

CodeMirror 6 比 Monaco 更顺手

如果确实需要搜索、标记、长文本和更可靠的编辑事务，CodeMirror 6 更像写作工具。Monaco 更像 IDE 内核，功能多，包体和集成成本也更大。

结构化迁移

暂时别把结构树当正文

Lexical、ProseMirror、Tiptap、Slate、Quill 会把文字变成节点或 Delta。它们适合富文本，但会重新定义保存、选区、撤销和导出。

解析辅助

解析器只做只读助手

fountain-js 或 screenplay-js 可以识别场景、角色和对白。它们可以帮助导航和观察，但不能把解析结果写回草稿本或正文本。

决策原则

先做小原型，再改架构

先测中文输入法、冻结选区、长文本、Tauri WebView 和复制粘贴。只有测试暴露结构性问题，才进入新的 OpenSpec change。

05 / 项目档案

原生 textarea 与兼容增强

低迁移
包含项目
当前原生 textarea、textarea-markdown-editor、@can3p/headless-mde、OverType
可取之处
保留浏览器原生输入、复制粘贴和整数选区；增强层可以提供 Markdown 命令、预览或更好的显示。
限制
增强项目的内部选择映射、composition 事件、滚动同步和包维护不能仅凭名称判断。
适合
只想改善快捷键、预览、工具栏或视觉反馈，而不想改变纯文本保存合同的阶段。
不适合
需要复杂协同、节点级格式、结构化撤销或 IDE 级语言服务的场景。

判断：这是最符合当前产品边界的实验组，但也最需要用小原型确认是否真的比原生能力多带来价值。

暂无官方界面截图；本报告不把任何宣传页面当作 Next Story 实测。

CodeMirror 6

优先线性候选
核心模型
可组合的线性文档与状态系统，选择由文档位置和范围表达。
优点
模块化、装饰和事务能力较强，仍然可以把文本视作连续字符；适合搜索、标记、长文本和更复杂的编辑反馈。
限制
从 textarea 迁移后，必须把 selectionStart/End 转换成编辑器 selection，并重新接入保存和 AI 冻结。
适合
原型证实原生输入层不够，但仍坚持纯文本事实源的写作工具。
不适合
只是想加一个按钮或提示条的轻微需求。

暂无官方界面截图；官方文档与仓库见来源附录。

Monaco Editor

较重线性候选
核心模型
线性文本模型，同时提供行列坐标、标记、命令和 IDE 风格能力。
优点
功能面广，适合需要代码编辑器级搜索、诊断和多光标的产品。
限制
worker、包体、主题、加载方式和 WebView 运行环境带来额外工程面；这些能力与剧本写作未必匹配。
适合
明确需要 IDE 级编辑能力并愿意承受集成成本的场景。
不适合
以写作现场、稳定中文输入和极短启动路径为优先的第一版。

暂无官方界面截图；不把 VS Code 等其他产品的界面当成 Monaco 截图。

Lexical / ProseMirror / Tiptap / Slate / Quill

结构化候选
共同变化
编辑内容从字符串变成节点树或 Delta。选区不再天然是文件 offset，保存通常需要 JSON、HTML 或自定义序列化。
优点
适合节点级格式、嵌入、结构校验、协同和复杂事务。
限制
会重新定义“什么是作品内容事实”，并增加纯文本导出、粘贴、撤销、错误恢复和 AI 选区映射的合同。
适合
产品明确决定作品将以结构化文档为核心，而不是仅仅想改善 textarea。
不适合
当前仍要求两个本子保存为用户纯文本、AI 只围绕冻结原文工作的最小闭环。

暂无官方界面截图；这些项目的官方站点展示的是各自编辑器能力，不是 Next Story 集成结果。

fountain-js / screenplay-js

只读解析辅助
核心模型
从 Fountain 或剧本文本识别场景标题、动作、角色、对白等元素，输出解析结果。
优点
可以在不改变原文的前提下提供导航、统计、结构观察或辅助提示。
限制
需要确认 Fountain 方言、中文角色名、混合文本、错误输入和原文 offset 映射；解析结果不可反写为作品事实。
适合
把解析当作可丢弃的只读索引，并保留原文为唯一事实源。
不适合
把解析 AST 当作用户必须服从的剧本结构，或用解析结果自动整理两个本子。

暂无官方界面截图；解析器不是编辑器，不能替代写作表面。

06 / 界面长什么样，适不适合写剧本

技术模型决定“文字怎么存”，但创作者首先感受到的是“写起来像不像一个能专心工作的本子”。下面的判断描述候选通常会带来的界面方向，不冒充 Next Story 已经集成完成。

原生 textarea

像一张干净的稿纸

一块连续文字区，光标、选区和复制都很直接。它不抢注意力，最适合当前“用户写正文，AI 在旁边临时帮忙”的边界。

好看程度：重点不在装饰，而在字体、行距、边距和面板比例。对剧本写作来说，这是稳妥的好看。

轻量增强

像带预览的 Markdown 工作台

通常会出现工具栏、快捷键提示、预览或更明显的格式反馈。视觉上更有产品感，但提示太多会打断写作。

好看程度：适合做工具感，不适合堆满控制条。

CodeMirror 6

像安静的专业编辑器

它没有固定外观，可以做成编辑器、侧栏、搜索和 AI 面板，也可以保持接近稿纸的安静感。

好看程度：上限高，但需要自己定视觉系统；最适合“写作区 + 临时 AI 面板”。

Monaco

像代码 IDE

行号、命令、诊断和编辑器状态容易带出开发工具气质，让写剧本像是在操作工程文件。

好看程度：能做得专业，但默认气质偏冷、偏技术。

结构化编辑器

像排版软件或富文本工具

节点、格式菜单和嵌入块会成为界面主角。丰富不等于适合，也可能把注意力从写句子带到选节点。

好看程度：先证明结构是用户需要，不要让 UI 替用户决定作品结构。

Fountain 解析器

它没有真正的写作界面

解析器最多提供场景列表、角色统计或定位提示。它是后台读文本的助手，不应被包装成新的编辑器。

好看程度：取决于外层界面，解析器本身不负责审美。

视觉参考判断：neobrutalism.dev 的粗边框、硬阴影、高对比强调色和模块化组件，适合做 Next Story 的“工具诚实感”：按钮像按钮，面板边界清楚，重要动作一眼可见。建议只局部吸收，用在 AI 面板、状态标签和实验性原型；正文写作区仍保持低干扰的浅色稿纸感。报告本身保留出版物的留白和打印稳定性，不全盘改成高饱和、重阴影风格。
候选方向用户看到的界面剧本写作匹配度视觉建议
原生 textarea连续稿纸、光标、选区高低干扰；把层次放在布局和字体上
轻量增强稿纸加少量工具栏/预览中高只留必要动作，避免工具栏变主角

视觉评价是基于公开项目定位和典型能力的工程判断，不是对每个项目当前默认主题的截图评分。真实集成前仍需做同一内容、同一字号、同一窗口尺寸的对照原型。

07 / Next Story 适配分析

事实源

草稿本和正文本是纯文本文件。当前编辑器的保存接口同时写入两个本子，作品内容事实来自用户保存的文字，而不是 AI 面板、解析树或富文本 JSON。

选区快照

用户点击入口时冻结本子类型、原文和起止位置。候选编辑器若改变 selection 表达，必须在请求前建立可靠的 offset 映射，并在文本变化后继续锚定冻结内容。

桌面边界

Tauri 将 HTML/CSS/TypeScript 放进 WebView。worker、字体、剪贴板、composition、滚动容器和大文档渲染都不能凭浏览器演示推断为可用。

工程建议：下一步只做一个小型对照原型：原生 textarea 与 CodeMirror 6 各实现同一套“选区冻结、复制、保存、AI 面板只读”流程。若原生已经通过测试，不要为了“编辑器更专业”引入结构化迁移。

决策顺序

  1. 先保留原生 textarea，补足实际阻塞写作的反馈。
  2. 如果出现可复现的线性编辑痛点，优先验证 CodeMirror 6。
  3. 解析器另行作为只读索引实验，不和编辑器迁移绑在一起。
  4. 只有作品事实源明确需要结构化节点时，才开启结构化编辑器 change。

08 / 待实测清单

实验方法通过条件失败后的影响
中文输入法 composition拼音未提交、候选词、删除和中英切换各输入一轮文字不重复、不丢失，选区入口不提前冻结暂缓迁移；原生路径保留
选区冻结触发后修改 textarea，再提交 AI 请求请求使用冻结原文，不读取修改后的实时选区违反当前 AI 合同，候选不可用
复制粘贴纯文本、跨编辑器、含换行和全角字符往返保存文本与用户粘贴内容一致需要额外转换层或放弃候选
长文本逐步加载 1 万、5 万、10 万字并滚动、搜索输入和选区响应仍可接受，未出现明显卡顿评估线性编辑器；不直接跳结构化
Tauri WebView生产构建而非开发服务器，重复打开/关闭面板无 worker、资源、焦点和滚动异常只接受已解决的问题，不凭文档判断
Fountain 解析中文场景、对白、空行、异常标记和未完成段落解析失败不修改原文，能返回可定位范围解析器只作为实验，不进入主路径

这些是原型验收项，不是已经完成的产品测试。报告本身没有宣称任何候选已通过。
