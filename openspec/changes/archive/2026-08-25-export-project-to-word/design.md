## Context

当前新项目的作品由内容树组织：`Folder` 节点只负责层级和顺序，`Document` 节点保存一份结构化 Tiptap 文档。文档 JSON 是作品事实源，前端按需读取，Rust/Tauri 后端负责可靠保存。当前没有文件导出能力。

导出需要跨越内容树遍历、文档读取、结构化内容转换、文件保存对话框和前端入口，但不能改变现有保存模型，也不能让导出结果反写作品目录。

## Goals / Non-Goals

**Goals:**

- 将当前作品中未删除的全部文档按内容树顺序合并为一个真正的 `.docx` 文件。
- 在文档中保留作品、文件夹、文档的可识别标题层级。
- 保留结构化正文的可编辑文字和已支持的基本格式，包括段落、标题、列表以及文字标记。
- 导出只读取已保存内容；目标路径由用户选择，默认文件名使用作品名称。
- 为后续 PDF、Markdown 导出留下独立的内容投影边界，不把格式特定逻辑散落到内容树代码中。

**Non-Goals:**

- 本次不实现 PDF、Markdown 或其他格式导出。
- 不导出回收站中的节点。
- 不猜测或生成场景、角色、对白等剧本语义。
- 不包含 AI 面板内容，不修改用户文档，不把未保存编辑器状态默认为导出内容。
- 不提供从 DOCX 反向导入或恢复作品的能力。

## Decisions

### 1. 使用真正的 DOCX 生成库

导出层使用能生成 Office Open XML `.docx` 的受支持依赖，而不是把 HTML/Markdown 改名为 Word 文件。这样用户可以在 Word 或兼容编辑器中继续修改，标题、段落、列表和文字标记也有明确的可编辑表示。

备选方案：HTML 改扩展名实现成本低但文件格式不可靠；先导出 Markdown 会增加用户手工转换步骤，均不满足本次流通和继续修改的目标。

### 2. 内容树遍历与 DOCX 渲染分层

先将内容树解析为稳定的导出序列：作品标题、文件夹标题、文档标题、文档结构化内容。再由独立的 DOCX 渲染器把该序列转换为 Word 节点。内容树顺序逻辑不依赖 DOCX 库，未来可复用给 PDF 或 Markdown 投影。

遍历从 `root_children` 开始，递归访问文件夹 `children`；遇到文档就读取其已保存 JSON；回收站不在活动节点集合中，因此不会进入序列。

### 3. 标题层级与正文映射

作品名称作为最高层级标题；文件夹名称和文档名称按固定、可读的较低层级标题输出。每篇文档正文紧随其文档标题之后，保持块顺序。编辑器已有标题等级在文档正文内部继续映射为 Word 标题样式；段落、无序/有序列表、粗体、斜体及可安全表达的文字标记映射为对应 Word 格式。

不把内容的视觉样式解释成剧本语义，无法一一映射的内部属性采用不损失可见文字的降级策略。

### 4. 通过保存对话框选择目标文件

前端在用户触发导出后调用 Tauri 保存对话框，建议的文件名为作品名称加 `.docx`，用户取消时不产生错误提示或文件。实际文件生成和写入由受控导出命令完成，错误以稳定的中文错误结果返回给前端。

### 5. 导出已保存内容，不隐式保存编辑器状态

导出命令从后端作品目录读取已保存的内容树和文档 JSON。这样导出不会把编辑器中的临时未保存文字悄悄纳入外部文件，也不会为了导出改变保存状态。界面应在用户未保存时明确提示当前导出基于已保存版本。

## Risks / Trade-offs

- **[DOCX 依赖体积或兼容性]** → 锁定具体版本，增加生成文件可打开性和关键格式的自动测试。
- **[大作品读取和生成耗时]** → 采用顺序读取、避免重复解析；前端显示导出中状态并防止重复触发。
- **[部分富文本属性无法表达]** → 保证可见文字和块顺序不丢失，对不支持的样式明确降级，而不擅自改变文本。
- **[用户误以为导出包含未保存内容]** → 在导出入口和结果提示中明确“导出已保存版本”，后续可单独设计导出未保存快照。
- **[文件写入中断留下半成品]** → 先在内存或临时文件生成，成功后再写入目标路径，并在失败时清理临时文件。

## Migration Plan

无需迁移现有作品数据或保存格式。发布后新增导出入口和导出命令；卸载或回滚只需移除入口、命令和 DOCX 依赖，作品目录不受影响。

## Open Questions

- DOCX 生成依赖最终选择及其在 Windows Tauri 构建中的打包方式，需要在实现前验证。
- 是否在第一版为文档之间增加分页符、目录或页码，可在设计确认后作为默认排版细节；不影响内容树和正文导出合同。
