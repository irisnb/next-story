## 一、已确认的目标与候选路径

起点：用户受 vibe coding 启发，认为「按需读取」——AI 能读到与当前问题相关的、跨文档的作品内容，而不是永远只看到「当前文档 + 标题结构」——正是下一步最该攻破的能力。

**产品目标**：用户直接用自然语言提问，系统自动准备有依据的作品材料，帮助用户重新看见故事。用户不必先配置上下文、整理参考文档或把问题改写成搜索词；AI 仍只提供观察、问题、假设和可能性。

围绕这一目标，有两种可以组合的材料准备方式：

- **A：系统主动附带材料**。程序按明确规则准备当前稿件、作品结构，并可增加字面检索结果，模型不决定这一阶段读什么。
- **B：Agent 按需补读**。复用 DSH 已有运行机制，让模型通过受控只读工具请求材料，再根据读到的内容决定是否继续补读。

**A 包含两项不同的工作**：自动附带写作现场，以及可选的自动跨文档字面检索。B 依赖受控读取、正确版本与权限，不依赖程序先替它完成抽词和排序。提供「搜索正文」的工具，与程序决定「本次先搜哪些词」，也需要分开理解。

此前讨论提出「先 A 后 B」。本轮进一步收敛的**开发建议**是：先设计共同边界、提前验证关键技术，再建立独立对话与保存、多窗口、只读基础，随后接 A 的现场材料与 B 的按需补读。A 的自动字面检索根据效果另行评估，不作为 B 的前置门槛。完整顺序见第五节；这是建议顺序，尚不等于批准实现。框架已有能力，也不等于 B 的产品接入工作已经完成或工作量已经明确。

**A 与 B 应共享受控只读作品接口**：读取文档、列内容树、搜索正文时，统一处理允许读取的范围、回收站和稿件版本。具体接口与接入方式待提案确认，避免形成两套权限或版本规则。

本轮用户进一步明确了三个需要：

- **等待体验**：主要在意用户使用时的等待，保留「AI 及时召唤」就是为了需要即时帮助时有快车道。
- **多个独立窗口**：希望多个 AI 对话窗口可以同时显示、移动、并排对照；不是只在一个面板里切换标签。
- **保留不同讨论**：常规讨论与及时召唤可能参考不同材料、沿不同路径形成解释，用户希望分别保留和比较，不因开启新讨论而丢弃旧讨论。

用户也明确希望先把整体关系设计完整，可以在开发上多花时间。由此不应推定用户愿意承受更长的日常等待，也不应把全部未来功能塞进同一个 change。

## 二、当前事实与待验证的接入方案

本节的实现事实以 2026-09-07 本地仓库及所安装依赖为依据。依赖或配置变化后须重新核对；候选方案不代表已实现。

### 2.1 DSH 是什么

- DSH = `@deepseek-ai/dsh`，全名 **DeepSeek Harness**，仓库 `github.com/deepseek-ai/deepseek-harness`，MIT 开源；本项目 `sidecar/package.json` 固定的版本为 `0.1.0-rc.7`。
- 是一整套 agent 框架，跑在 Cordis 插件框架上（容器配置 = `cordis.driver.yaml`）。

### 2.2 现在接了什么

- 当前只用了**会话能力**：Rust/Tauri 守护一个 node 驱动子进程（`sidecar/driver/driver.mjs`），stdin/stdout 行分隔 JSON 协议 v1，只有 7 条命令（`start_session` / `send_message` / `replay_history` / `replay_done` / `cancel_message` / `end_session` / `shutdown`），**没有任何工具调用**。
- 驱动通过 `agent.followup()` 发起一轮，生成期间轮询 `agent.session.events` 转发 `text-delta`，通过 `agent.whenIdle()` 等待结束。当前产品只呈现文本回应，没有接通作品读取工具及其过程信息；崩溃恢复也以用户与助手的文本历史重建会话。
- 当前产品只有一个临时对话。及时召唤以冻结选区、无需输入问题的方式发起流式首轮；新召唤会结束并替换旧对话，当前追问仍锚定首轮冻结选区。应用重启后不恢复对话。完整行为见 `openspec/specs/selection-ai-summon/spec.md` 与 `resident-ai-session/spec.md`。
- 多窗口、多对话保存、AI 可见性设置、自动作品上下文与按需补读，均尚未实现。已保留快速入口，不等于已有经过实测的速度保障。

### 2.3 框架已有循环，产品尚未接通自主读稿

- `sidecar/driver/cordis.driver.yaml` 已装配 `tools` 和 `agent-loop`。工具注册与执行的框架基础、Agent 循环基础，并未整体关闭。
- `sidecar/driver/gen-config.mjs` 的 `DENY_IDS` 禁用了具体工具（`tool-bash` / `tool-fs` / `tool-web` / …）、技能（`skill`）、子代理（`subagent`）、目标持续推进等附加能力（`goal` / `goal-round-driver` / `repeat-tool-reminder`），以及会话持久化相关插件。禁用这些插件不能等同于关闭循环核心。
- 本地依赖已有 `dsh-agent-loop`、`dsh-tools`、`dsh-mcp-client` 等可复用模块。但 Next Story 尚未接通「围绕问题自主读取作品」的产品能力；不能因框架存在循环，就把该能力写成已交付。
- 当前判断要区分两件事：**DSH 的相关运行时能力大多已经存在，只是当前配置锁住或尚未由 Next Story 接入；Next Story 的自主读稿产品能力仍未实现。** 因此 B 不是重新研究 DSH 能不能做，而是验证如何在作品权限、会话身份、材料版本、工具过程、停止取消和崩溃恢复边界内安全解锁并接入这些能力。
- B 仍需定义并验证只读桥接、读取授权、材料版本、工具过程信息、停止与取消、崩溃恢复等行为。不能简化为「只要打开开关、挂三个工具」，也不应因此另造一套 Agent 核心。

### 2.4 DSH 能力解锁的阶段性边界

DSH 是 Next Story 已选定的 Agent 运行时基础。当前只接通了会话运输和文本流式回应，不代表后续只能继续沿用“每轮发一段文本”的窄接口。后续应优先复用 DSH 已有的 Agent Loop、工具注册、工具调用事件、取消和可恢复运行机制，再由 Next Story 的 Rust/Tauri 作品服务负责权限和数据边界。

阶段 1 首批只验证并考虑解锁以下能力：

- Agent Loop；
- 受控只读作品工具；
- 工具调用的开始、成功、失败和取消事件；
- 需要扩大读取范围时的用户确认与可恢复中断；
- 单轮取消、超时和迟到结果隔离；
- 结构化错误返回，以及含工具材料的恢复记录。

阶段 1 暂不开放以下能力：

- `tool-fs`、`tool-bash`、`tool-web` 等绕过作品服务的通用工具；
- 网络检索；
- 子代理或泛化多 Agent 协作；
- 目标持续推进和无限循环；
- AI 对用户作品的写入、整理或保存。

这里的“暂不开放”是当前产品范围和权限边界，不是对 DSH 框架能力的否定。以后若有必要引入其他能力，必须根据真实创作问题单独讨论并走新的 OpenSpec change。

**阶段 1 验证结论（已完成）**：本轮已用确定性替身验证 Agent Loop 的文本流、只读工具请求、结构化工具事件、用户确认与拒绝、终态闸门、多会话隔离、取消与迟到结果、恢复降级、未保存快照身份校验和作品数据不变性。Rust `story_material` 与 `capability_gateway` 已有离线纯函数边界和测试，但尚未注册为 Tauri command，也未接入生产 `driver.mjs` 的作品工具协议。真实 DSH 事件字段、真实模型等待和生产读稿链路仍未验证，后续必须单独走 OpenSpec change。

### 2.5 候选桥接方案：MCP

- **MCP**（连接 AI 与外部工具的协议）是一个可评估的接入方案：提供只读 MCP server，由 `dsh-mcp-client` 接入。工具职责可以是列内容树、搜正文、读文档；`list_content_tree` / `search_story_text` / `read_document` 暂作候选接口名。具体接法及是否采用 MCP，须在提案中核对，不在本指引里锁成唯一答案。
- 无论采用哪种桥接方式，**作品读取都必须经过 Rust 的受控只读接口，AI 运行环境不能绕过它直接访问作品目录**。当前未保存内容须由前端提供，并通过同一读取边界校验，不能只读磁盘上的旧稿。
- **AI 可见性设置是已确认方向、尚未实现的功能**，见行动计划事项 6。它是否随事项 2 提前实现、怎样衔接，应在提案中明确并同步路线记录；不能假定目前已经存在开关。可见性规则一旦生效，必须覆盖目录信息、正文、当前未保存快照与选区，不能因材料来自编辑器而绕过权限。

### 2.6 存储模型

- 作品 = 内容树：只有「文件夹」和「文档」两种节点。
- 文档 = Tiptap JSON v2（外层 `format` / `version` / `document`），正文具有段落、标题、列表等结构，可按文档或块组织读取结果。
- **当前存储没有独立的「场次」节点类型**。不能假设「一场 = 一篇文档」；按文档或块检索是候选实现取舍，不能据此规定用户怎样组织剧本。

### 2.7 多窗口需要先处理的会话依赖

- `src/ai-session-transport.ts` 当前持有单一 `activeSessionId` 和 `currentStream`，每个连接实例的消息编号从 `msg-1` 开始。
- `src-tauri/src/dsh_driver.rs` 当前按 `message_id` 建立消息终态的等待与分发索引。直接复制连接实例用于多个窗口，会产生同名消息冲突风险，需要先统一对话、会话、轮次与消息的身份。
- `sidecar/driver/driver.mjs` 已有会话集合及按会话判断忙碌的基础，但这不能证明整个应用已支持多窗口独立生成。
- 当前主要恢复用户与助手文本。未来增加工具读取后，材料和工具事件怎样保存、怎样恢复，需要提前验证，不能等全部窗口与保存功能做完再考虑。

这些是开发依赖的核对结果，不代表本轮已经改造或验证了多窗口能力。

## 三、A/B 的分工与常规讨论流程

A 的候选做法：在常规讨论的每轮发送之前，加一个「上下文准备层」（按明确规则取材、只读、可测试）。以下是未来设计草案，尚未实现；不意味着 A 的所有部分必须先于 B 完成，也不能自动套用到「AI 及时召唤」。建议召唤首轮保持冻结选区直接回应，不等待完整取材；其后追问默认继续围绕首轮冻结选区，扩大到当前关注文档或其他文档须用户明确提出，不被悄悄自动升级。

```
常规首轮或追问发送：取得问题、可选重点材料及当前写作现场
  │
  ▼
① 经过读取边界校验，冻结本轮材料：
   - 当前文档最新内容（含未保存）——来自前端编辑器内存
   - 全作品标题结构
   - 排除回收站；可见性规则覆盖上述所有材料及选区
② 基础材料：默认提供允许读取的当前稿件全文与作品结构
③ 可选补充（若以后采用 A 的专名字面检索）：
   - 从问题里提取候选词 → 在允许的其他文档正文里搜
   - 按待确定的排序与体积规则选择材料
   - 拼装：文档名 + 命中位置 + 正文片段
④ 发给现有常驻会话，并提供轻量可查看的参考说明
```

**常规讨论每次追问重新取得发送时刻的本讨论关注文档最新快照，包括允许参与本次思考的未保存修改。** 发送后继续编辑，不改变已经发出的这一轮材料；下一轮再取得新稿。此要求承接行动计划事项 2 与账本第 13 条；关注文档是讨论创建时固定绑定的文档，不随编辑器切换改绑；召唤追问默认继续围绕首轮冻结选区，重新选区召唤开启新讨论、不改变原讨论取材范围。旧稿、最新快照与历史讨论的关系要说明清楚，不能把 AI 此前的推测当成新稿事实。

现有会话命令与增量追问机制可作为接入基础，但当前协议尚未定义作品材料的完整语义，须在提案中明确。基础材料超限如何处理也须明确；检索结果的选择与体积控制，不等于重新引入手工截断对话历史。历史仍由框架压缩承接，失败时诚实报错，不能静默丢弃。

### 3.1 A 的可选检索方案：专名字面检索

这张表只描述 **A 的自动字面检索**能够预先附带什么，不限制用户可以问什么，也不定义 B 的能力上限。是否实施这项补充，待基础 A 与 B 的实际效果明确后评估。

| 问题类型 | 例 | A 的字面检索如何处理 |
|---|---|---|
| 带明确名字 / 专名 / 道具 / 地点 | 「林晓为什么怕水」「那块怀表最早在哪出现」 | 尝试按问题中的词寻找原文入口；命中不保证材料充分或已找到答案 |
| 抽象 / 语义 / 代词称谓 / 别名 | 「这条关系什么时候变质的」「他为什么离开」 | 这项字面检索暂不保证预先找出相关跨文档材料；AI 仍可利用当前稿件和对话回应，接入 B 后也可从现场寻找线索再补读；依据不足时说明，必要时自然追问 |

如果采用这项补充，候选初版先评估「专名字面检索」：提取问题中可能有用、能在正文中精确匹配的词。它的规则较易检查和重复验证，但中文抽词、排序和漏读情况尚待验证，不能预先宣称它最便宜或能覆盖所有带名字的问题。用户无需维护专名词典或掌握检索写法才能提问。

**搜索结果只是阅读入口。** 没搜到不能表述为「作品里没有」，搜到同一个名字也不能据此认定人物动机、关系转折或唯一解释。回应须区分原文依据、可能解释与尚不清楚的部分。

更强的跨文档补读能力留待后续评估，不预设必须依靠语义检索或 LightRAG 才能处理代词、别名和关系问题。行动计划账本第 10 条提醒的是「语义相似不等于故事相关」，并不能据此推出字面匹配已经解决了故事相关性。

### 3.2 两者实现后如何配合

建议的常规流程：

```
用户自然提问
  → A 自动提供约定的当前稿件、作品目录与可选重点
  → 陪想 Agent 阅读问题与已有材料
  → 材料足够：直接回应
  → 需要补读：B 决定搜什么、读什么
      → 共同只读接口校验权限，返回原文与版本
      → Agent 根据新材料决定继续补读、回应或说明缺口
```

A 是程序准备材料，B 是陪想 Agent 按需使用工具；在同一段讨论中，它们共享材料记录并形成一份连贯回应，不必分别调用两个 AI 各答一遍。

例如用户问「他们这次争吵是不是来得太突然」：A 提供当前争吵稿件与目录；B 可以尝试从稿件辨认相关人物，寻找此前的互动，再决定是否阅读完整段落或其他文档。问题没有明确人名，不等于不能继续寻找依据；辨认不清或读不到时，保留不确定并向用户自然追问。

配合时需要明确四条规则：

1. **权限共用**：主动附带与工具补读都经过同一读取边界。
2. **材料记录共用**：B 知道 A 已提供的文档、范围和版本；同版全文避免重复装入，片段不足时允许补读前后文。
3. **本轮版本一致**：常规追问重新取得约定的最新现场；同一轮 B 再读当前稿件时应沿用本轮冻结版本，其他原文也须注明来源与版本，避免新旧稿混杂。
4. **允许停止**：材料足够时不强制搜索；达到读取次数或时间限制、权限不允许或材料不可得时，说明缺口，不为得出确定答案无限补读。具体限制待提案确定。

### 3.3 验证应围绕真实创作问题

提案应同时考虑读取正确性与陪想效果：检查未保存修改、追问版本更新、读取权限和材料范围说明；再用少量真实创作卡点，确认用户自然提问时，AI 能提供有原文依据的观察、问题和可能性，并把解释与选择留给用户。不能仅以「同样输入搜到同样的词」作为产品成立的证据。

## 四、及时召唤快车道、多窗口与等待体验

### 4.1 两种入口的分工

用户已明确及时召唤承担快速开始陪想的用途。下表是落实这一用途的设计建议，具体取材和追问规则仍须提案确认：

| 入口 | 用户此刻的需要 | 建议的处理方式 |
|---|---|---|
| 常驻面板直接提问 | 结合作品，把问题想清楚 | A 提供现场，B 按需要补读；允许为取得依据多花一些时间，同时设明确停止条件 |
| AI 及时召唤 | 围绕眼前选区，尽快开始陪想 | 冻结选区后直接生成首轮，不等待整篇或全作品检索、多轮补读；材料范围有限时如实表达 |

两种入口可复用同一套会话、保存和作品服务，但每段对话的材料和允许执行的步骤分别明确。不能把完整 A+B 设为所有入口的统一前置，也不能因为快速入口存在，就放任常规讨论无限等待。

当前召唤追问仍基于首轮冻结选区。已确认：后续追问默认继续围绕首轮冻结选区，扩大到当前关注文档或其他文档须用户明确提出；重新选区召唤开启新讨论，不改变原讨论取材范围。不能在本指引中假定已有自动升级能力。

### 4.2 多个独立窗口与讨论保留

**用户明确希望多个窗口能同时显示、移动、并排对照，各自保留讨论。** 其用途是容纳不同材料与不同提问路径形成的解释，让用户自行比较和判断。

面向这个目标，后续设计应处理：

- 新召唤开启另一段独立讨论，保留原来的常规讨论及已有结果；不能继续使用当前「新召唤替换并丢弃旧对话」的规则。
- 各个窗口分别追问、停止与重试；对话历史、材料版本、生成状态和取消结果互不串用。
- 不同窗口的 AI 推测不自动混入另一段对话，也不自动合并为一份作品结论。A/B 在同一段讨论中配合，与多个窗口分别讨论，是两个不同层面的关系。
- 可以保留不同解释；如果是同一处原文事实被说反，需要核对原文，不能将事实错误当成一种创作可能。轻量参考说明帮助用户理解各个回答依据的差异。

**关于关闭与保存（已确认行为）**：对话由应用统一管理，窗口负责显示；关闭窗口、停止本次生成、删除对话是不同操作。已确认：关闭窗口不删除讨论，若生成中则自动停止本轮生成；停止只结束当前生成、已完成内容保留；重新打开不自动重发、不重复生成；删除是单独的明确动作。默认只打开一个窗口、需要时再增加，是保持写作空间简洁的建议，不是新增强制规则。

行动计划事项 4 已决定保存聊天记录、提供会话列表和会话内快捷跳转。多窗口应与这条方向衔接，分别定义「应用打开期间保留多个讨论」和「应用重启后仍可恢复」；不能把多窗口已经设计等同于持久化已经实现。

### 4.3 快车道需要真实的独立请求能力

如果只是多开窗口，及时召唤仍排在常规长请求后等待，就没有达到用户需要的快车道效果。设计应允许它在常规请求未完成时独立发起，并明确同时生成上限、排队和取消规则。不能只复制界面、继续让所有请求共享一个全局忙碌状态。

主要可能增加等待的因素，是过量材料和多次模型往返。建议当前材料足够时直接回答，必要的多个读取尽量集中取得，补读有明确停止条件；不要让 A 的自动跨文档检索和 B 每次都完整重复执行。

等待测量从早期验证开始，至少分开记录：

- 提交到第一次实际模型回应的时间；「正在读取」等进度提示单独记录，不冒充回答已经开始。
- 提交到完整回答结束的时间。
- 应用内排队、作品取材和额外模型往返分别造成的等待。

需要在相同模型、可比较材料下，检查单独召唤、单独常规讨论，以及常规生成中再发起召唤的表现。具体首字与完整等待目标须在后续真实接入验证取得实测后再与用户确定，当前不承诺秒数，也不承诺应用能消除模型服务本身的排队。

## 五、建议开发顺序与整体设计

### 5.1 先把共同关系设计完整，再按依赖实现

本顺序是在聊天中确认整体方向后整理出的开发顺序，不是把所有后续阶段一次性批准为实施排期。阶段 0 的整体关系已经确认；从阶段 1 起逐项 propose、确认、实现、归档。如某阶段确需拆分，也须串行完成，不同时开多个 change。

| 顺序 | 阶段 | 主要交付 | 完成前必须证明什么 | 状态 |
|---|---|---|---|---|
| 0 | 整体设计 | 两个入口、多窗口、对话归属、保存、读取权限、稿件版本与请求运行的共同规则；整体行为与文字流程（不含视觉稿） | 典型使用过程能走通，用户能看懂并确认 | ✅ 已确认：阶段 0 整体行为已确认（后续阶段串行 OpenSpec 推进） |
| 1 | DSH 能力解锁与接入验证 | 在 Next Story 边界内验证 Agent Loop、受控只读工具往返、工具事件、用户中断与恢复、多会话请求隔离与取消、未保存稿件受控传递（离线确定性验证；真实等待基线不在本阶段，须后续真实接入验证取得） | 确定 DSH 能直接复用和需要新增的桥接部分，提前暴露会改变整体结构的风险；验证“怎样安全接入”，不是重新判断 DSH 是否具备这些能力 | ✅ 已完成并归档：离线验证，非生产接入 |
| 2 | 独立对话与可靠保存 | 各自的材料、轮次和请求状态；保存与重开、基本会话列表；新召唤保留旧讨论 | 不串历史、不串回答；重开应用能恢复已保存讨论；中断和失败不伪装为成功 | ✅ 已完成并归档（`openspec/changes/archive/2026-09-09-add-conversation-persistence-and-isolation/`） |
| 3 | 多窗口与及时召唤快车道 | 可同时显示、移动、并排对照的窗口；各自追问、停止和重试；及时召唤能独立发起 | 常规生成途中，召唤能在另一窗口开始；停止一段讨论不影响另一段；关闭与删除按约定区分 | ✅ 已完成并归档（`openspec/changes/archive/2026-09-11-add-multi-window-and-fast-lane/`）；真实链路验证通过（驱动丢失恢复未实测） |
| 4 | 受控只读接口与可见性 | 统一读取目录、正文和允许的未保存稿；可见性开关、回收站过滤、身份与版本校验 | 所有读取路径服从同一规则；旧材料按已确认权限规则处理；AI 无作品写入通道 | ✅ 受控只读与可见性基础已实现，待真实链路联合验收/归档（`openspec/changes/controlled-story-read-visibility/`） |
| 5 | A：常规讨论自动获得现场材料 | 常规首轮与追问取得约定的最新稿件；实际参考范围轻量可查看；缺失或过长时诚实说明 | 读到允许参与本轮的最新稿件；下一轮看到新修改；及时召唤不被强制加上完整取材流程 | ☐ 未开始 |
| 6 | B：Agent 按需补读作品 | 围绕问题调用只读工具、阅读原文、去重和识别版本；停止、取消、恢复及必要的过程说明 | 自然提问能得到有用补读；无依据时不编结论；恢复不丢关键材料语义；快车道保持独立 | ☐ 未开始 |
| 7 | 联合产品验收与针对性优化 | 真实创作卡点、等待、多窗口对照、版本变化、权限变化与恢复的整体验收 | 用户获得有原文依据的观察和可能性，能保留并比较讨论；等待符合约定目标，失败可理解、可恢复 | ☐ 未开始 |

三个排序理由：

1. **独立对话与保存先于窗口**：窗口需要可靠的讨论身份与记录支撑，不能先复制界面再补隔离。保存格式也应提前考虑未来作品材料与工具事件。
2. **读取权限先于自动读稿**：将原行动计划事项 6 前移到共同只读基础，避免全文读取已经接通后再补可见性。
3. **B 正式交付可以靠后，关键验证必须靠前**：先确认工具调用、材料恢复和等待是否可行，再完成其他依赖。A 的完整抽词与排序系统不阻塞 B。

每一阶段都要完成适当验证，不能等阶段 7 才检查可靠性。阶段 2 如需拆成「独立对话与请求隔离」和「保存与重开」，前项完成归档后再启动后项；阶段 3 依赖两者。

### 5.2 第 0 阶段已确认的共同规则（索引）

阶段 0 的整体行为已确认并沉淀到方向版阶段 0 文档，本文不再整段重复，只列索引：

- 已确认的窗口呈现、讨论归属与写作现场、窗口状态动作、多讨论与保留：见方向版 7.1–7.4；
- 保存、并发排队与取消、等待：见方向版 7.5–7.7；
- 权限与旧材料、版本与去重、材料与恢复：见方向版 6.1–6.4；
- 两个入口与 A/B 配合：见方向版 3.3–3.4、4.1–4.3；
- 后续提案需确定的问题：见方向版第九节；
- 阶段外后续探索：见方向版第十节。

当前已确认的是**整体行为与文字流程**；阶段 3 的多窗口与会话列表视觉稿已由 designer 出稿、经用户确认后落地（见该阶段归档的 `ui-design/`）；全应用视觉全量更新仍留后续。具体搜索算法和局部界面细节到对应提案再细化，不假定一次讨论就能消除所有后续调整。

### 5.3 第 1 阶段：DSH 能力解锁与接入验证

本阶段不是再确认 DSH 是否拥有 Agent Loop 或工具系统，而是用少量固定材料验证这些现成能力怎样受 Next Story 控制：

1. 两个独立对话各发起一轮生成，结果准确回到各自对话；单独取消其中一轮，不影响另一轮。
2. Agent 能提出已注册的只读工具请求；作品服务校验作品、文档、版本和可见性后返回原文；未知工具与越权读取被拒绝。
3. 工具调用产生可区分的请求、运行、成功、失败、取消终态；迟到的工具结果和模型结果不能污染已结束的请求。
4. 前端提供的未保存稿能作为受控快照进入取材链路；AI 运行环境不能直接访问作品目录，也不能取得任何作品写入能力。
5. Agent 需要扩大读取范围时能够暂停，请求用户确认后从同一轮恢复；拒绝、超时和取消都留下明确终态。
6. 一段讨论读过工具材料后发生进程重启，验证恢复需要哪些对话、材料、版本和工具事件；如果框架恢复能力不足，明确保留记录与继续讨论的降级边界。
7. 在同一模型与可比较材料下，测直接回应、一次补读、常规生成期间再发召唤的等待，不以进度提示冒充实际回应。

这些验证也是开发工作，必须单独 propose 并确认。当前阶段 1 验证 change 已完成；后续生产接入仍须依据本轮结果单独提出。先依据结果确定桥接方式、消息身份和记录格式；不能因为 DSH 已有插件就跳过边界验证，也不能因为当前配置锁住能力就另造一套 Agent 核心。

### 5.4 保存要为后续保留哪些扩展位置

在整体设计与关键验证结果上，明确作品、对话、轮次、请求状态、原文来源与版本、工具请求与结果、模型回应和恢复信息之间的关系。保存格式要能识别版本并迁移旧记录，避免接入 B 时推翻已有聊天档案。

保存由受控应用服务完成，系统对话档案与用户作品正文分开；保存 AI 回应不赋予 AI 修改作品文档的能力。显示历史与模型恢复材料也要分清。是否使用 DSH 的持久化插件，由它能否满足这些规则决定，不默认启用所有落盘能力。

会话列表随保存与重开一起交付；会话内快捷跳转在核心记录稳定后完善。可以为偏好、方法和工具记录明确边界，不为尚未确定的记忆或子 Agent 提前实现空框架。

### 5.5 后续内容与原路线的衔接

阶段 7 通过后，建议继续：

1. 稳定写作宽度、完善会话内快捷跳转，分别交付。
2. 作品导入与剩余导出，按实际使用优先级逐种格式完成；Word 导出已实现，复杂 PDF 导入后置。
3. 前端 UI 全量更新；整体布局提前设计，正式视觉更新按既有决定完整落地，时机可由用户调整。
4. 偏好记忆与功能开关；先评估用户明确表达、可查看修改删除的偏好，先定作用范围与遗忘规则。属阶段外后续探索，不在本阶段，仍是候选探索，不是已批准规格。
5. 低成本调整陪想方式，以及总控 / Skill / 子 Agent 按需协作；从真实反复出现的需求中选择，不默认每轮启动一组助手。属阶段外后续探索，不在本阶段。
6. 自然语言流程自定义复杂度；属阶段外后续探索，不在本阶段。

后台预加载、摘要、长期作品记忆、语义或关系检索，根据具体等待和取材问题再研究。以上阶段外探索方向以方向版阶段 0 文档第十节为准，均不作为已实现能力，也不得借未来扩展绕过「AI 不写作品」等永久边界。已有可靠性测试器可用于保存证据、保守初筛和人工复核；实时核对与自动重答仍须以后单独讨论，不为验收把它们插入每轮对话。

相较原行动计划，本顺序建议前移事项 4 的对话保存与列表、事项 6 的可见性，将事项 2 分为关键验证、读取基础、A 现场材料与 B 补读，事项 3 的验收贯穿并在最后联验。正式路线表和相关方向表述在用户确认后再同步；已归档规格仍只记录当前实现。

**阶段 0 整体行为已确认，可进入阶段 2 提案；阶段 1 离线验证 change 已完成并归档。** 进入阶段 2 前仍须按串行 OpenSpec：propose → 用户确认 → apply → archive，一次只开一个 change；生产 Rust/Tauri/DSH 只读接入的边界须在相应提案中单独确认。

## 六、已定边界与阶段性取舍

1. **目标不变**：用户直接自然提问，系统承担材料准备，AI 提供有依据的陪想，创作者保留判断权。
2. **建议顺序**：整体设计 → DSH 能力解锁与接入验证 → 独立对话与保存 → 多窗口快车道 → 只读与可见性 → A 现场材料 → B 补读 → 联合验收。按第五节逐项确认和实现，完整字面检索不作为 B 的前置。
3. **接入定位**：DSH 是已经选定的 Agent 运行时基础，当前许多相关能力只是被配置锁住或尚未接入 Next Story。B 应复用 DSH 已有运行机制，新增并验证受控只读工具链；MCP 是候选桥接方案，具体接口与工作量尚待核定。
4. **可选检索补充**：A 的自动字面检索根据实际效果再决定，不将其局限扩大成 B 或用户提问的限制；不预先引入语义 / 向量检索。
5. **已定权限方向**：可见性是开关，不是优先级，不得暴露成分级 / 继承 / 覆盖模型。功能尚未实现；实现后必须在读取边界由后端强制执行，覆盖所有材料来源。
6. **永久边界与本轮权限分开**：AI 永远不直接修改用户文档，作品读取工具必须只读。本轮候选范围不开放写入、命令执行、网络检索或子代理工具；后续能力是否需要，须另行讨论并经 OpenSpec 确认，不能把本轮不开放网络或子代理写成新的永久禁令，也不能借未来扩展绕过文档边界。
7. **材料与回答诚实**：「系统搜到的材料」不能写成「作品全集」；未命中、未读取或未完整提供的限制要如实说明。参考说明轻量可查看，默认不打断对话；原文事实、AI 假设与未知保持区分。
8. **常规讨论每轮最新稿件**：常规首轮与追问均取得发送时刻本讨论关注文档的最新快照，含允许参与本次思考的未保存内容；关注文档固定绑定、不随编辑器切换改绑。不能只在首轮读稿，后续沿用旧版。及时召唤的取材与追问范围单独定义，不强制经过完整 A+B。
9. **用户明确的窗口与保留需要**：及时召唤是快车道；多个独立窗口可以同时显示、移动、并排对照，分别保留讨论。窗口呈现、关闭/停止/删除语义、讨论归属已确认（见方向版 7.1–7.4）；并发上限与等待数值等技术细节仍须实测确定。
10. **不同解释可保留**：不同窗口不自动合并结论，不把对话记录变成作品事实；参考范围与版本应轻量可查看，事实冲突仍需依据原文核对。
11. **DSH 能力与产品接入分开判断**：DSH 已具备 Agent Loop、工具和插件扩展等运行时基础，当前配置只是有意锁住部分能力；Next Story 仍必须逐项验证受控解锁、作品权限、请求身份、取消、恢复和等待边界，不能把“框架有能力”写成“产品已实现”。

## 七、开放问题（整体设计及对应 OpenSpec 提案中要定）

1. **实施范围**：确认第五节的建议顺序，以及首个关键验证 change 的具体边界；每项做完归档再开下一项。桥接方式、记录格式与产品接入细节根据验证结果明确。
2. **可见性依赖**：落实可见性前移的具体范围，怎样与多对话保存及作品读取衔接？关闭可见性后，已经进入会话和保存记录的旧材料如何处理，新追问如何不通过历史重放或恢复重新发送已禁用材料？不能声称一次读取过滤能自动清除历史材料；具体隔离与重建方案未定，不假装已解决。
3. **抽词与检索单位**：若采用字面检索，怎样从中文问题提取有用的词？候选包括系统内部的专名词典、分词器、n-gram 匹配（连续字串匹配），不要求用户配置。命中返回整篇文档还是命中块及前后文，怎样减少漏读和脱离语境？
4. **材料体积与排序**：当前稿件或作品结构过大时怎么办？补充片段怎样排序、限量、说明未完整读取？区分本轮取材规则与已有对话历史的压缩机制，不重新引入静默截断历史。
5. **版本与去重**：草案用本讨论关注文档未保存快照配合其他文档的已保存正文。如何标明文档身份、来源和本轮版本，避免把关注文档旧磁盘稿混进最新快照？后续统一读取接口怎样保持这一语义？
6. **参考说明与验收案例**：怎样轻量呈现本次实际提供的材料及其限制，不把未读过的部分列成已知内容？选哪些真实卡点检验依据、未知、推测和用户判断权，而非只验关键词命中？
7. **多窗口与快速入口**：各窗口的对话归属、关闭与删除行为已确认（方向版 7.2–7.4）；待定的是及时召唤怎样在常规长请求后独立发起、并发上限与排队安排、忙碌时怎样处理，以及多窗口下的保存与恢复细节。
8. **等待与联合验收**：首字与完整回答各接受怎样的等待？如何比较单独使用与常规、召唤同时使用的结果？旧讨论重开、权限变化、新旧稿冲突、不同解释并存等场景怎样验收？
9. **DSH 能力解锁范围**：阶段 1 首先开放哪些已存在的 DSH 能力，怎样验证配置解锁不会绕过 Rust/Tauri 作品服务；工具事件、用户中断、恢复和错误终态采用什么协议？

## 八、不变的边界（每次动手前重读）

- AI 永不写用户文档（任何版本、任何授权）。
- AI 输出是临时材料，用户复制、编辑、保存才算进作品。
- 判断权在用户：内容权 / 解释权 / 评价权 / 方向权。
- 用户直接自然提问，选区只是可选重点提示，不要求先配置上下文或学习检索写法。
- 一次只开一个 change。
- 一个概念只能有一个名字，作品是承载文件夹和文档的容器。
- UI 里能选的每个模型，后端必须真实可调用。
- 实现前仍须 propose → 用户确认 → apply → archive；修订本指引不等于批准代码实现。
