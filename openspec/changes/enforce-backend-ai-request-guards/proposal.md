# 后端生成护栏与取材锁（enforce-backend-ai-request-guards）

## Why

2026-09-14 全量地基审计 P1-4 与 P1-5（修复队列第 3b 项，承接 3a 之后的第二个独立回滚面）：

- **P1-4 后端无并发硬上限**：全局同时生成上限只存在于前端 `ai-request-scheduler.ts:26`；Rust 侧 `pending` 等待无准入控制，任何绕过前端调度的调用（测试、内部调用、未来新入口）都能直接并发打满驱动与模型服务。阶段 6 引入循环工具调用后资源放大更明显。
- **P1-5 取材吞掉作品锁获取失败**：`lib.rs` 常规取材路径 `locks.acquire(...).ok()` 后继续读取——与「作品锁保护下读取」和失败关闭原则相反。

## What Changes

- **后端生成准入护栏（P1-4）**：`DshDriverManager` 内新增准入表（会话 → 进行中消息）与全局上限（默认与前端当前值 2 对齐，仅为当前安全策略、不表述为实测容量结论）；`send_message_and_wait` 入口先取 RAII 许可——同一讨论已有进行中请求返回 `conversation_busy`，达到全局上限返回 `capacity_exceeded`，两者都不写入驱动协议；许可 `Drop` 只释放自己的登记，覆盖注册、写命令、等待、超时取消宽限期与全部错误出口。前端调度器职责不变（FIFO 排队与排队状态展示）；Node 驱动的会话 `busy` 检查保留为最后一层防御。
- **新错误码**：`GenerateAiErrorCode` 新增 `ConversationBusy`（「当前讨论已有生成中的请求，请稍候」）与 `CapacityExceeded`（「已达同时生成上限，请等待进行中的生成完成后再试」）；前端 `types.ts` 联合类型同步扩展。不复用 `Service`——后端本地拒绝必须可与远端服务错误区分（测试与未来遥测）。
- **取材锁失败关闭（P1-5）**：`lib.rs` 常规取材路径的锁获取改为 `Result` 传播；锁不可得时本轮立即失败并返回固定安全文案「作品读取暂时不可用，本次请求未发送。」，绝不调用组装；`RecoveryRequired` 保持既有专用码路径，其余材料拒绝维持既有安全错误。
- **规格改写**：`ai-request-scheduling` 的「全局同时生成上限与排队」要求改写为双层归属——前端负责排队与展示，后端负责不可绕过的拒绝；新增绕过拒绝与同讨论重复生成拒绝两个场景。

## Capabilities

### New Capabilities

（无——不新增产品能力，只补齐后端护栏。）

### Modified Capabilities

- `ai-request-scheduling`：修改「全局同时生成上限与排队」——同一生效上限双层执行：前端调度器在正常界面路径按先到先服务排队并展示排队状态；Rust 后端以同一上限实施不可绕过的准入护栏，达到上限的绕过调用返回稳定容量错误且不写入驱动协议；同一讨论的重复生成在后端被明确拒绝；上限数值仍须由真实接入验证取得基线后确定并记录。

## Impact

- **Rust**：`dsh_driver.rs`（Inner 增准入表与上限、`send_message_and_wait` 入口护栏、`new_with_limit` 测试构造）、`llm_config/mod.rs`（错误码枚举）、`lib.rs`（取材锁 Result 化与错误映射）。
- **前端**：`types.ts` 错误码联合类型扩展；正常 UI 路径行为不变（前端先行排队，一般不会见到这两个码；竞态下的后端拒绝按既有失败态展示固定文案）。
- **规格**：`ai-request-scheduling` 一份 delta。
- **明确不做**：不把上限做成用户设置或环境变量；不改前端调度器；不新增协议命令/事件；等待基线实测数值仍待阶段 7（既有记录）。
