## 1. 结论与适用范围

**项目已有可继续迭代的结构基础，无需推倒重写。但在继续叠加产品能力前，建议先处理本报告的六项高优先级缺陷。** 它们涉及正文丢失、作品切换隔离、材料权限、停止请求及讨论档案可靠性，不是为了代码美观而重构。

模块化最值得保留的部分是：前端组合根、状态迁移与显示分离；后端作品事务与 AI 编排分离；驱动协议与受控只读工具有明确入口。最需要补齐的部分是：**跨模块的异步生命周期、共享档案的字段所有权、跨通道权限判定，以及完整统一的工程门禁**。

## 2. 检查方式与证据等级

1. **建立基线**：读 AGENTS.md、方向文件、旧审计、当前配置与目录，检查 Git 状态和活跃 change。
2. **建立责任图**：辨认装配、业务规则、状态、传输、存储的责任，检查依赖方向与公共接口。
3. **沿真实调用链检查**：从入口走到落盘或生成终态，重点看 await 前后身份、取消、权限和失败处理。
4. **运行现有门禁**：总检查之外补跑漏项，区分测试数量与测试覆盖范围。
5. **用反例挑战正常路径**：人为推迟读取、会话启动和窗口关闭，用实际模块验证迟到结果、撤销授权和大档案。
6. **按影响排序**：先保护用户内容和决定，再补工程门禁；结构改进尽量随对应功能进行。

证据等级：

- **A：离线复现**。调用实际生产函数，使用可控依赖或真实后端存储，观察到缺陷。并不等于已在桌面 UI 重现。
- **B：代码链确认**。实现与配置足以确认结构性缺口，具体线上发生频率未实测。
- **C：风险或改进候选**。没有足够证据定性为现行故障，需要容量、真机或具体产品场景验证。

优先级：P1＝优先修复的正确性/权限/数据问题；P2＝工程保障和可恢复性问题；P3＝维护便利性。这里不沿用旧审计的编号。

## 4. 应优先修复的六项问题

### F01 · P1 · 文档切换期间的新输入会丢失（A）

位置：`src/editor.ts:300`；`src/editor-document-session.ts:73`；`src/editor-save-state.ts`。

当前流程是“保存 A → 异步读取 B → 销毁 A 编辑器 → 显示 B”。读取 B 期间，A 仍可编辑。B 返回后没有复核 A 是否产生了新修改，直接销毁旧编辑器并设新保存基线。

复现：打开 A，点击 B；延迟 B 的读取；在 A 输入 `NEW TEXT DURING READ`；释放 B 读取。结果：A 的保存内容没有新增文字，A 编辑器已销毁，B 显示为无未保存修改。已用现有 editor 测试夹具和实际 `setupEditor` 复现。

**影响**：正常用户操作即可丢正文；慢磁盘、大文档会扩大窗口。保存本身的快照机制没有错，错在切换操作把“某次保存成功”当成“旧文档已没有未保存修改”。

修复验收：保存中和目标读取中继续输入都不能丢；切换失败保留旧编辑器；快速 A→B→C 不发生过期切换；作品打开流程也检查同类窗口。方案可以是冻结编辑或带修改代次的切换事务，须提案确定。

### F02 · P1 · 旧作品文件树的迟到结果可覆盖新作品（A）

位置：`src/file-management.ts:85`、`:93`、`showProject/unload`；`src/main.ts` 的 `onTreeChanged`。

`refreshTree` 读取完成后无条件写 tree、调用宿主并渲染。没有作品代次或请求序号检查；`unload/showProject` 也不使进行中的刷新失效。

复现：在 A 执行结构操作，延迟随后读树；切换文件管理器到 B；返回 A 的树。结果：B 文件视图变成 A 的树，`onTreeChanged` 收到 A 的树。宿主会把该树交给当前编辑器。

**影响**：至少界面与当前作品身份错配；后续文档选择与可见性计算可能基于错误树。未声称已复现磁盘串写，但这是进入串写或误判之前必须堵住的隔离缺口。

修复验收：A→B、A→欢迎页、A→B→A 三种迟到回写均丢弃；错误提示也不能污染新作品；同作品多次刷新不能被旧快照覆盖。

### F03 · P1 · 补读来源被隐藏后，讨论权限判断漏掉这类出处（A）

位置：`src/ai-panel-conversation.ts:194`、`:264`、`:281`。

重开、崩溃恢复和实时锁存只检查普通 `provenance`，没有检查 `on_demand_reading_provenance` / `onDemandReadingProvenance`。补读出处已被记录，但没有接入完整权限决策。

复现：档案普通出处为空，补读出处包含 `secret-doc` 且 `entered_model_context=true`；将该文档列入隐藏集合。实际函数返回：重开 `restricted=false`；恢复判定 false；实时锁存返回原对象。

**影响**：只通过按需补读进入讨论的隐藏材料，不能按约定使讨论永久只读；历史恢复也未被该判断拦截。这不是“隐藏后还能重新读取正文”的证明，而是**已经存在的模型上下文/显示历史仍可继续使用**的权限遗漏。

修复验收：普通材料＋补读材料统一权限影响关系；打开讨论、关闭讨论后重开、驱动恢复、隐藏后再开启都保持永久限制；只含补读出处的讨论也能持久锁存，不能靠给空普通出处加 revoked 标记来假装完成。

### F04 · P1 · 会话启动期间的停止/离开不能阻止随后发送（A）

位置：`src/ai-session-transport.ts:197`、`:239`、`:292`、`:307`。

会话在 `startSession` 返回后才加入 sessions；在途消息也到此后才登记。启动等待期间，`cancelMessage` 找不到目标，`endAllSessions` 遍历不到正在启动的会话；随后没有失效检查，仍登记并发送。

复现：延迟 startSession，发起问题，调用 cancelMessage 与 endAllSessions，再放行启动。实际 sendMessage 仍调用 1 次，endSession 为 0 次。

**影响**：用户已经停止或离开，问题仍可能发给服务，旧会话留存；仅丢弃晚到回答不能替代取消发送。相同生命周期原则也应覆盖 replaySession。

修复验收：启动、重放、发送都有代次/失效令牌；停止后不发请求，迟到启动产生的会话立即结束；作品切换与销毁不可使会话复活。

### F05 · P1 · 旧档案保存可重新开启用户已关闭的补读授权（A＋B）

位置：`src-tauri/src/conversation_store.rs:378`、`:503`；`src/ai-panel-conversation.ts:612`、`:725`；`src/ai-feature-on-demand-reading.ts`；`src-tauri/src/story_tool_channel.rs:927`。

普通前端保存携带完整授权字段，后端接受并覆盖。后端只保全“调用方未提供的补读出处”，没有把授权字段限定为专用授权操作所有。前端保存串行链不包含授权设置操作；工具出处读改写又使用自己的锁，与命令层作品锁不是同一临界区。

**实际后端复现**：保存已授权档案 → 读出旧副本 → 调 `set_on_demand_reading(false)`（确认磁盘未授权）→ 用旧副本调用普通 `save_conversation` → 磁盘重新变成已授权。调用的是此次测试构建出的生产 Rust 库，使用合成临时档案。

该顺序对应“已排队的旧保存晚于关闭授权落地”等时序。具体桌面事件交错未实测，存储层允许旧保存撤销用户决定已经证实。

同根风险：工具出处 `read → 修改 → save` 与其他整档写入未共享完整原子读改写边界，旧副本可能覆盖更新的轮次/标题/授权。单次文件原子替换只防半个文件，不防丢更新。

修复验收：明确字段所有者；普通保存不得授予或撤销补读；授权与出处采用后端窄更新，整个读改写共享同一讨论事务边界；交错测试覆盖“撤销优先、出处不丢、轮次不回退”。

### F06 · P1 · 大讨论可以保存成功，却不能重新打开（A）

位置：`src-tauri/src/conversation_store.rs:24`、`:299`、`:378`、`:419`。

读取上限为 1 MiB，但保存没有对应大小校验。长讨论不断积累显示轮次，最终可以写出自身读取器拒绝的档案。模型上下文压缩不等于磁盘显示历史缩短。

实际后端复现：构造序列化后大于 1 MiB 的合法档案，save 返回成功；read 返回错误；list 把同一档案列入 skipped。

**影响**：内存里看起来保存成功的长讨论，重启后无法从正常列表重开。文件仍在，不等于永久物理删除，但正常恢复路径失效。

修复验收：写入成功必须可读回；超限不能覆盖最后一份可重开的档案；不能静默截断讨论。选择扩大/分段存储或保存前拒绝并明确告知，需要先确定产品行为。

## 6. 模块化、结构化、规范化与可迭代性

### 6.1 模块化：方向正确，尚未形成一致的生命周期契约

前端静态依赖无环；组合根依赖较多符合装配职责：ai-feature 24 个本地静态依赖、editor 22、main 14。不能因组合根 import 多就判定耦合失控。

状态迁移集中到 reducer，显示由 view-model/dock/window 消费；请求网关与生命周期已有独立模块；编辑器的会话、保存、工具栏、查找等已拆分。这些成果应保留。

但实际接口仍有三个问题：

- 一些模块用作品代次隔离，一些只有 destroyed，一些完全没有；新增功能容易重复踩“旧结果写回新状态”。
- AiFeatureContext 暴露整个 state、transport、scheduler、coordinator、dock 等，显式化优于大闭包，但仍是较宽上下文。后续按各模块实际需要收窄到 Pick/小接口，避免它变成所有模块都能拿所有服务的总入口。
- 前端/Rust 的请求、档案、错误契约多处手写；驱动协议已有单一来源与契约测试，这是可复制的方向。优先对材料身份、授权字段、讨论档案补双端序列化样本，而非立即引入庞大生成框架。

**实用标准**：新增一种材料来源，只应新增读取/出处映射，不能要求开发者记得去多个地方补隐藏判断；新增一种讨论写操作，不能另开一条整档保存链。

### 6.2 结构化：目录扁平尚可，按职责迁移优于机械分文件夹

src 下 65 个 TS 文件主要靠 editor-/ai- 前缀分组；当前仍可导航。Rust 已有 project 与 llm_config 子模块，但 AI 主模块仍在根级。

建议在触碰对应功能时逐步形成清晰责任区：应用装配、写作、作品管理、讨论、AI 传输、共享契约。不要一次搬完全部文件；导入路径变动会制造巨大审查噪音，而当前优先问题并非路径排列。

共享原子写入现在从 project/operations 向讨论与最近作品复用，避免重复实现是优点；若继续扩充存储服务，可提取独立基础存储模块，但不能把业务权限一起下沉进通用工具。

### 6.4 规范化：规则已有，自动执行范围还不完整

已有 strict TypeScript、ESLint、fmt、clippy、锁文件、OpenSpec、中文错误信息、稳定协议名、禁工具清单及边界测试，是较好的基础。

短板：门禁集合漂移；sidecar 完全被 lint 排除；边界测试主要按源码字符串匹配、只扫描 src 顶层文件，未来搬到子目录可能不再覆盖；README、代码注释与规格之间状态同步不完整；源文件 NUL 会让普通搜索漏检。

建议让一条标准检查命令与 CI 共用相同必跑集合；迁移目录时同步改成递归/语法树边界检查；对关键契约使用行为测试，保留少量真正有用的结构检查。

### 6.5 可迭代性：优先建立不变量，不先增加抽象层

后续每个 change 最有价值的验收问题是：

1. 新异步操作在切作品、关闭、停止或重试后还能落地吗？
2. 新状态由谁唯一修改？是否有第二个模块拿旧副本整档覆盖？
3. 新材料来源是否进入权限、出处、恢复和隐藏锁存同一套判断？
4. 写成功的数据是否一定能用当前读取器重开？
5. 单元测试通过之后，真实装配是否还在传递身份并等待 Promise？
6. 生产安装包是否能在没有开发环境的机器上独立运行？

这些不变量比“再拆十个文件”更能降低迭代成本。

## 8. 推荐推进顺序

这是排序建议，不同时创建多个 change，也不要求所有 C 类风险解决后才能继续开发。

1. **先保护写作切换**：F01、F02，并一起理清同一打开/切换提交边界的 F08。验收聚焦正文不丢、作品身份不串。
2. **补齐权限与档案更新责任**：F03、F05。验收隐藏影响所有材料来源、关闭授权不能被旧保存复活、并发读改写不丢更新。
3. **完成异步会话与退出收尾**：F04、F07、F09。验收停止后不发送、退出前可确认保存完成、失败关闭可重试。
4. **修复长讨论可重开性**：F06。先确认大小增长时的产品行为，不能仅加一个静默截断。
5. **统一工程门禁与开发说明**：F10–F14；纳入独立 sidecar 的依赖更新与检查，修正文档和源码 NUL。

每次依然 propose → 用户确认 → apply → archive。不要把这份报告变成无限追加的“必须全清才能做产品”清单；六项 P1 应优先解决，P2 可按下一项产品开发涉及的边界安排，C 类按发行与容量需求验证。

后续真正新增产品能力时，优先选小范围的纵向闭环：界面入口、状态、后端契约、失败处理、真实装配验收同时完成。不要先扩展许多后台能力，再集中补用户路径。
