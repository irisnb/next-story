# 等待计时导出入口 · 最小设计稿

> 面向 change：`app-real-chain-validation` 任务 1.3（design.md D2）
> 交付物：本说明 + `mockup.html`（静态小样：菜单展开态 + 两种提示态，双击打开即看）
> 这不是完整视觉系统，只是给用户确认的最小设计稿。文案最终由编排者复核。

---

## 0. 一句话结论

入口做进**停靠区头 `⋯` 菜单**（「停靠所有浮动窗口 / 恢复默认布局」下面加一条分隔线，放两个开发者项）；菜单收起时**零新增视觉占用**——比图标级更轻，且窄轨态（停靠区收起）的 `⋯` 打开的是同一个菜单，任何时刻都可达。

---

## 1. 位置决策

### 主推荐：停靠区头 `⋯` 菜单

**一句理由**：`⋯` 菜单在上一稿设计里已定位为「全局动作收纳处」，等待计时是跨讨论的全局数据，语义同构；菜单收起时界面上一根毛都不多，完美满足「不进主用户流」，而「找得到」由菜单项的完整文字保证——点开 `⋯` 就看到一行明白话，不需要认图标。

### 备选：会话列表面板底部轻量行

**一句理由**：在列表底部加一行小字按钮（文字可读、比菜单好发现），但要多一步「先打开列表」，且把开发者仪器放进日常使用的用户面板，跟「不进主用户流」的精神拧着——所以只作备选。

### 已排除：停靠区头第 5 个常驻图标按钮

停靠区头动作排（列表 / 新建 / ⋯ / 收起）是主用户流，塞一个常驻的下载图标进去，等于给所有普通用户每天看一个看不懂的按钮——正是 D2 要避免的「进主用户流」。排除。

---

## 2. 菜单结构（在现有 `openDockMenu` 末尾追加）

```
⋯ 菜单（现 有）
├ 停靠所有浮动窗口          i-dock
├ 恢复默认布局              i-reset
├ ────────── 分隔线 ──────────
├ 导出等待计时数据…         i-export（新增 symbol）   ← 无数据时禁用
└ 清空等待计时数据…         i-trash，危险红           ← 无数据时禁用
```

- 「…」后缀沿用现有惯例（「删除讨论…」）：点了还有下一步（系统保存对话框 / 清空确认）。
- 分隔线把开发者仪器和用户的布局动作隔开，扫一眼就知道下面是「另一类东西」。

## 3. 视觉规格（全部用现有 token，不引入体系外东西）

| 项 | 规格 | 现有 token / 类 |
|---|---|---|
| 闲置态（菜单收起） | **无任何新增可见元素** | — |
| 菜单项文字 | 12.5px，继承正文色 | `.ai-menu button`（现成） |
| 菜单项内距 | 5px 9px，图标-文字间距 8px | `.ai-menu button`（现成） |
| 图标 | 16 × 16，描边 1.5px，方角，`currentColor`，向下箭头入托盘（export/download 语义） | 新增 `<symbol id="i-export">`，遵守上一稿 9.1 图标规范 |
| 清空项颜色 | `--color-danger`（#d6361e）文字 | `.ai-menu .ai-menu-danger`（现成） |
| 分隔线 | `--border-window-sep`，上下 3px | `.ai-menu .ai-menu-sep`（现成） |
| 菜单容器 | `--border-control`（2px 实边）+ `--shadow-control`（2px 2px 0 硬阴影）+ `--radius-sm` | `.ai-menu`（现成） |
| 禁用态 | opacity 0.4 | `.ai-menu button[disabled]`（现成） |
| 成功提示条 | 0.75rem 文字 + 左侧 3px `--color-success` 竖条 + `--color-surface-subtle` 底 | `.ai-dock-notice.ok`（现成，撤销删除同款） |
| 确认/警示提示条 | 左侧 3px `--color-warning` 竖条 + `--color-warning-surface` 底；确认按钮用 `--color-danger` 实底白字 | `.ai-dock-notice.warn` + `.ai-cl-btn.danger` 的配色（现成） |

**体系自洽性**：本方案没有发明任何新视觉——新增的只有一行菜单 × 2 和一个图标 symbol。neobrutalism 的权重秩序不动：编辑区仍然最重，停靠区头一个像素没变。

## 4. 交互状态表

| 状态 | 呈现 | 用户可做什么 |
|---|---|---|
| 闲置（菜单收起） | 界面与今天完全一样 | 无 |
| 悬停菜单项 | 底色变 `--color-surface-hover`（现有 hover 态） | — |
| 点击「导出等待计时数据…」 | 弹系统保存对话框，默认文件名 `wait-timing-YYYYMMDD-HHmm.json`，位置用户选 | 选位置保存 / 取消 |
| 导出成功 | 停靠区头下提示条（成功样式）：「已导出等待计时数据（N 条）」，数秒后自动消失（与撤销提示同寿命） | 无需操作 |
| 导出失败（写盘失败等） | 提示条（警示样式）：「导出失败：……」，不自动消失，直到下次提示顶替 | 重试（再点一次菜单） |
| 用户取消保存对话框 | **不出现任何提示**（取消不是成功也不是失败） | — |
| 点击「清空等待计时数据…」 | 菜单关，停靠区提示条变确认态：「清空等待计时数据？已导出的文件不受影响。[清空] [取消]」 | 清空 / 取消 |
| 确认清空 | 提示条变「已清空等待计时数据」（成功样式），数秒后消失；历史与在途全清 | — |
| 无任何计时数据时 | 两个菜单项都禁用（半透明），点不动 | 先去产生数据 |
| 停靠区收起（窄轨） | 窄轨 `⋯` 打开同一个菜单，导出/清空照常可用 | 同上 |

**范围边界**：提示条出现在停靠区层（`.ai-dock-notice` 槽位），不依赖会话列表开合、不打断任何窗口里的对话流；生成中的讨论不受任何影响。

## 6. 实现注意项（给 apply 阶段）

1. **菜单右溢出**：`.ai-menu` 定位现在是 `left = rect.right - 170`（按 170px 估宽右对齐），菜单项文字变长后实际宽度会超过 170px，停靠区在屏幕右缘，会把菜单顶出屏幕。实现时需把 `positionMenu` 对该菜单改为**右对齐锚定**（`right = window.innerWidth - rect.right`）或量实际宽度再定位。
2. **禁用条件**：历史条数 + 在途条数 = 0 时两项禁用（D3：导出＝历史全量＋当前在途，所以只要有在途就算「有数据」）。
3. **提示条复用**：确认态/成功态/警示态都走现有 `.ai-dock-notice` 槽位与 `ok`/`warn` 类，不新建组件；注意与「删除撤销」「保存失败」提示互斥时的顶替规则（后出现的顶替先前的即可）。
4. **图标**：`i-export` 按上一稿 9.1 规范进 sprite 表（16 viewBox / 1.5px 描边 / 方角 / currentColor）；清空复用 `i-trash`。

## 7. 与项目铁律的对照

- 这个入口**不碰用户文档**：导出写的是用户自己在系统对话框里选的位置，属用户主动落盘，与「AI 路径不写作品目录」不冲突（D2 已把「自动落盘」否掉，理由正是这条边界直觉）。
- 清空只清**内存中的计时记录**，不碰任何讨论档案与作品文件；已导出的 JSON 是用户自己的文件，清空动作声明「不影响已导出文件」。
- 入口标注「开发者用」，不向普通用户宣称任何能力或结果；导出的数据只落本机，不上报外部（D7 规格义务）。
