## 二、各事项详情

### 1. 常驻 AI 会话进程（运行时改造，已完成并归档）

- **状态**：已完成并归档。实现 commit `ab4c49a`；归档同步规格 commit `3949eec`；规格 `openspec/specs/resident-ai-session/spec.md`；归档目录 `openspec/changes/archive/2026-08-30-resident-ai-session/`。
- **是什么**：DSH 从"每条消息新起进程、用完即焚"的一次性模式，改为**对话期间常驻的会话进程**。会话生命周期与对话同寿命：用户召唤 AI 时确保会话就绪；退出应用、新建对话、切换作品时结束或更换会话。
- **已落地能力**（真实实现）：
  - 常驻 AI 会话：面板直接提问与选区「AI 及时召唤」两种首轮入口，进入同一种临时会话；回复流式逐字呈现；追问只发增量问题，历史由常驻会话在驱动进程内维护；
  - 首次回应成功后的线性临时追问，可取消生成；
  - 上下文自动压缩：长对话由框架压缩承接，超限报错提示新建对话，绝不静默砍历史；
  - 崩溃恢复：驱动进程意外退出后自动重启，重放显示历史恢复会话；临时对话不跨应用重启持久化，不提供历史会话列表。
- **为什么做**（2026-08-27 拍板，历史理由）：
  - 现状是"每条消息 spawn 一次进程 + 前端手工重发全部历史 + 手工定截断规矩"——等于绕开 DSH 现成的会话基建（会话持久化、恢复、自动压缩插件），自己手搓一个阉割版，吃力不讨好还容易出问题；
  - 每条消息省去秒级的进程启动开销；
  - 解锁框架能力：流式回复、会话恢复、上下文自动压缩；
  - 是"后台 Agent 待命"愿景（Agent 循环）的第一块基石。
- **技术事实（防误解）**：模型 API 本身永远无状态——即使会话常驻，每轮依然要把历史发给模型。常驻省的是进程开销与手工管理，不是"模型记忆"。

  - DSH 自带会话基建：会话 JSONL 持久化、web profile 支持 `--resume`、自动压缩历史的 compaction 插件——常驻会话选型的现成材料。
- **保留有效的产品决策**（重新立项时直接继承）：
  - 上下文组成：问题 + 选区（可选）+ 当前文档最新内容（含未保存）+ 全作品结构（排除回收站）；
  - 每次追问重新抓取当前文档最新快照（2026-08-27 拍板）；
  - 参考说明"本次参考了什么"如实可见、不打断对话；
  - 全程只读边界，AI 无任何写入能力；
  - AI 及时召唤（旧选区工具）行为不变；「思维扩展」已正式退场。

### 2A. 回答可靠性测试器（第一阶段已完成并归档）

- **第一阶段结果（已归档）**：真实 DSH driver 运行 9 个固定案例，结果 8 个
  PASS_LIKELY、1 个 NEEDS_REVIEW、0 个 RUNTIME_ERROR。判分与证据记录已能区分
  “运行失败 / 模型事实错误 / 自动评分无法确定 / 评分器误判”，不再把评分器误判
  当成模型答错。
- **评分器两轮修复（已归档，2026-09-03）**：先修中文否定引用误判
  （`fix-negated-quotation-screening`），再修裸实体词误判
  （`fix-screener-false-failures`）——否定词表补充「辞去/离开/放弃」等语义否定
  词，并确立 `mustNegate`/`wrongConclusions` 必须写完整命题短语、禁止裸实体名
  （如「盐城」「母亲」）的规范。详见 `.omo/回答可靠性测试器-借鉴与设计指引.md`。
- **下一步顺序**：LLM 幻觉压力测试已完成；测试器完成体已封装为可发布插件并拆分到独立仓库（见 2B）。

- **为什么先做**：2026-09-01 的官方 DeepSeek 长上下文压力测试已经初步证明真实
  DSH 链路、长剧本读取和 v1 → v2 版本切换可用，但现有自动判分主要依赖关键词，
  会把否定句、原文引用和“不确定”回答误判。继续扩大测试前，先把判分与证据记录
  做可靠，避免把“评分器误判”误认为“模型答错”。
- **定位**：先做一个不承担过多职责、但可长期复用的**回答可靠性测试器**。它不是
  宣判模型绝对正确的自动裁判，而是负责运行固定案例、保存完整证据、自动初筛明显
  问题，并把复杂语义交给人工复核。
- **建议的测试案例内容**：材料版本与哈希、对话步骤、问题、预期结论、允许的
  “不确定”表达、明确错误结论、原文依据位置及风险标签（直接事实 / 否定与未知 /
  版本冲突 / 多轮与压缩后的事实保持）。
- **建议的证据内容**：测试器版本或 Git 提交、模型与 API 配置标识、完整问题、
  完整模型回答、DSH 事件摘要、是否发生上下文压缩、耗时与运行错误。API Key 继续
  只通过测试进程环境传递，不进入报告或证据文件。
- **判分原则**：协议完成、空回答、运行错误等确定性项目可以自动判；自然语言内容
  只做保守初筛，至少区分“可能通过 / 可能失败 / 需要人工复核”。出现否定、引用、
  多版本、事实与推测混合等情况时，不用单个关键词直接下结论。
- **报告必须分开记录**：运行失败、模型事实错误、自动评分无法确定、评分器误判。
  四者不能混成同一种 FAIL。
- **下一轮优先验证**：不先盲目增加剧本长度或模型数量；用少量固定案例验证同一
  会话中 v1 → v2 更新、多轮追问、旧事实与最新快照冲突、上下文压缩前后关键事实
  是否保持，以及模型能否区分原文事实、推测和未知。
- **与产品运行时的关系（未来可能性，尚未立项）**：测试器稳定后，可评估把其中
  高确定性的事实冲突识别能力复用于只读的**实时回答核对层**。两者可共享案例格式、
  证据结构与冲突规则，但不能把离线测试器原样放进用户对话链路，也不能让核对层
  变成替用户解释或评价作品的第二个裁判。
- **实时核对的初步体验原则（2026-09-02 讨论）**：仅在发现回答与当前版本原文明
  显冲突、或把无依据推测冒充原文事实时触发；先明确告诉用户系统正在依据当前稿件
  重新核对，再把可追溯的原文证据交给 LLM，要求其重新回答一次。重答仍须再次核对；
  不无限循环。具体提示文字和用户帮助文档以后另议。
- **实时核对的保守边界**：核对器不直接改写模型回答；开放性解释、人物动机假设和
  创作可能性不因存在不同解读而被拦截；核对器自己无法确定、超时或失败时，不把它
  的猜测冒充作品事实。实时能力是否进入产品、失败时如何展示，仍须以后单独探索并
  走 OpenSpec 流程。

  `sidecar/reliability` 测试器，与插件共享同一套判分与证据语义。
- **二阶段目标**：
  - 扩展压力测试：LLM 幻觉、长文本、多版本冲突等容易误判的场景；
  - 结果对比：同一案例在不同模型 / 版本 / 配置下的输出对比；
  - 证据复核：人工复核流程与证据链的稳定化；
  - 可重复运行：案例、driver、证据、配置均可重复、可追溯地运行；
  - 封装稳定的案例 / driver / 证据 / 配置接口，为未来接入 Next Story 做准备。
- **边界（不变）**：当前仍是独立离线工具，不接入 Next Story UI / 实时对话 / 生产
  作品数据；未来接入另行走 OpenSpec 流程。

### 3. 产品验收（好问题验收）

- **是什么**：方向共识 §10.2。拿 3~5 个用户真实卡住的片段来测，AI 必须给出
  **有文字依据的**问题和可能性，不代写、不裁判、不套模板。
- **为什么排在 2 后面**：AI 看不见作品时，这条验收在结构上不可能过。

### 4. 聊天记录持久化 + 会话列表 + 快捷跳转

- **决策（已拍板）**：存；要会话列表；单个会话内做 ChatGPT 式快捷标识，
  点击跳到长会话中的具体某段问答。
- **边界澄清**：持久化的是**临时材料的档案**，不是作品事实源。AI 依然不能
  拿它直接改任何文档；用户复制采纳仍是唯一进作品路径。
- **规格影响**：现有 specs 中"不持久化且无会话列表"相关要求将被本 change 改写。
- **待定（propose 时定）**：存在哪里（作品文件夹内 or 应用数据）、会话按作品
  还是按文档分组、切换文档/作品时旧清理规则怎么改。

### 5. 稳定写作宽度

- **是什么**：编辑器稿纸化——固定宽度一栏居中，窗口只是背景，文字不随窗口
  伸缩摊开/折拢（现在一段字放大变一行、缩小变一段，用户体感鸡肋）。
- **关键事实**：文档按结构化块存储，折行纯属显示层，**不影响存储和导出**。
  本 change 只动显示层。

### 6. AI 可见性设置

- **决策（已拍板）**：用户可以设置某些文档不给 AI 看。**是开关，不是优先级。**
- **案底（防回潮）**：旧「四级 AI 参考优先级」（核心/一般/弱/不参考）及继承、
  覆盖已从用户概念中撤出（方向共识 §4）。本 change 不得引入任何分级、继承、
  覆盖模型。理由：把"AI 该看什么"的负担卸给用户，标错时用户无从察觉，
  只会觉得"AI 不行"。

### 7. 作品导入

- **格式（已拍板）**：Word、规范化 Markdown、PDF。
- **风险注记**：PDF 是三者中最硬的骨头——PDF 本质是打印指令，抽文字常丢结构、
  丢顺序。建议在三项中排最后，或明确定位为"有损导入"。
- **关联**：方向共识 §11 挂着的"旧作品迁移到内容树"可与本项一起想。

### 8. 多格式导出（部分完成）

- **状态**：Word 导出已完成（已归档），当前会把作品内全部文档汇集到一个 `.docx` 文件中，并已完成真实导出检查；PDF 与 Markdown 导出尚未完成。
- **格式（已拍板）**：Word（已完成）、PDF、Markdown。
- **原则**：按真实使用排序逐个做，用不到的坚决不做。
- **边界说明**：导出链路可用，不等于编辑器写作体验已经合格。编辑过程中的光标、选区、粘贴、链接、段落等问题应在事项 10 单独盘点；若发现编辑结果与导出结果不一致，再明确归入对应范围。

### 9. 前端 UI 全量更新

- **决策（已拍板）**：一次到位，不做逐模块翻新。
- **风险对冲**：大爆炸式翻新的风险用"先出完整设计稿再动手"对冲——
  先铺整套设计语言（字体、颜色、间距、气质，落进 design tokens），
  用户看过点头后再改代码。设计工作由 designer 主导。
- **时机**：默认排在功能项之后，用户可随时提前。

### 10. 文本编辑器体验专项梳理与整顿（待立项）

现在的文本编辑器已经能保存、恢复和导出，底层安全迁移也通过了测试，但实际写起来仍然不好用。有些操作方式和常见文本编辑器不一样，会打断已经形成的使用习惯。当前记录的两个现象只是已经发现的例子，不代表问题只有这些。后续需要把它当成一次较大型的编辑器体验整顿，从真实写作过程出发完整检查，而不是看到一个修一个。

- **规模判断**：这是一个尚未完成全貌摸底的大型任务，不是两个零散缺陷的修补。不得因为自动测试通过或功能按钮存在，就判断编辑器体验已经成熟。
- **当前基础**：Tiptap 已于 2026-09-16 从 2.27.2 迁移至 3.31.3；安全漏洞已清除，迁移前后的冻结金样本保持一致，说明已覆盖行为没有因升级发生非预期变化。这次迁移的目标是安全与兼容，不负责纠正原本就不合理的交互机制。
- **已知现象（不是完整清单）**：
  - 在编辑器内部复制一小段文字后粘贴，内容会作为独立段落插入，而不是像常见文本编辑器那样自然地插入当前位置；该行为在 Tiptap v2 与 v3 中都存在，不是本次升级造成的新回归。
  - 对短链接只放置光标时，链接操作弹层不会稳定出现，往往需要先选中文字；本次迁移保留了原有链接边界判定，因此仍属于待复核、待重做体验判断的既有问题。
- **后续盘点范围**：以真实连续写作为主线，系统检查输入与中文输入法、光标与选区、复制粘贴、段落与换行、链接、列表、撤销重做、查找替换、拖放、长文档操作，以及编辑结果与保存、重开、导出结果是否一致。盘点过程中可以继续增加问题，不把本节列举内容当成范围上限。
- **推进方式**：先集中体验、记录现象、确认常规预期和影响程度，再决定如何拆分 OpenSpec change 及执行顺序。不得直接把所有问题塞进一个无法验收的大 change，也不得在没有整体盘点时按“发现一个修一个”的方式反复打补丁。
- **完成判断**：除自动回归外，必须用真实写作流程验收。核心不是“功能能调用”，而是基本操作是否符合用户对常见文本编辑器的预期，能否支持长时间写作而不频繁打断思路。

## 三、决定与理由（防遗忘账本）

> 这一节记的是历次方向讨论中每个决定背后的"为什么"（2026-08-27 起）。将来任何讨论
> 想推翻这里的结论，先读理由，再说明情况变了什么。

1. **上下文给全作品结构**（不只当前文档）：标题列表很便宜（几百字），却让 AI
   知道"这部作品还有什么"，回答"角色和主线关系"这类问题时天壤之别。
2. **当前文档以未保存内容为准**：AI 看到的必须和用户眼前这版一致，否则用户
   盯着新稿问、AI 按旧稿答，信任崩塌。"数据来自前端"不破坏边界——方向仍是只读。
3. **超长用"截断 + 诚实告知"，不用摘要**：摘要是后台 LLM 炼出来的，文本一改
   就旧，重建要真金白银调用。截断规则一次 change 能落地；摘要进长期账本。
4. **"预加载"和"摘要"是两个概念**：预加载解决"什么时候读"（省时间），
   摘要解决"读进来怎么办"（省体积）。超长问题的对症药是后者。
   预加载省的时间（毫秒级组装）相对模型生成时间（秒级）可忽略。
5. **理论知识库搁置**：模型训练时已读过麦基和大量剧本，本地库增量近乎为零；
   反而往上下文塞理论文本会抬高理论在回答里的权重，AI 容易从"陪想"滑向
   "拿别人的规矩量你的故事"。理论作为"镜片"可以靠提示词约束实现，不需要建库。
6. **知识库的真正价值在作品自身内容**：模型缺的不是知识，是"这一部作品"的
   信息。喂作品内容现阶段用最笨的办法（请求时直接读）就行，不需要索引系统。
7. **不做优先级标记**：见事项 5 案底。
8. **组装提示词是毫秒级**：前端递内存 ~0ms、读结构几 ms、拼字符串 ~1ms；
   时间全花在模型生成上，那部分现在也在等。材料总量靠截断上限管住。
9. **折行不影响导出**：文档按结构化块存储，显示层折行与磁盘内容、导出映射
   是两码事（类比：剪辑结构不因幕布比例改变）。
10. **向量检索（普通 RAG）对剧本不对路**：语义相似 ≠ 故事相关。查"林晓的
    动机"该参考的可能是第一幕一场用词完全无关的戏。若将来做检索，考虑
    LightRAG 式关系链方案，且等作品大到塞不下模型胃口再启用。
11. **先做常驻会话，再做作品上下文**（2026-08-27 晚拍板）：一次性"用完即焚"
    模式下手搓上下文管理（手工重发历史、手工定截断）是阉割版，吃力不讨好
    还容易出问题；DSH 本身有会话持久化、恢复、自动压缩的现成基建，应该用。
    产品决策（给 AI 看什么）与运输细节（怎么送达）分离：前者持久有效，
    后者本就是临时脚手架，不值得先建。
12. **会话生命周期 = 对话生命周期**：用户召唤 AI 时确保会话就绪；退出应用、
    新建对话、切换作品时结束或更换会话。不按"每条消息"换会话。
13. **追问快照语义**：每次追问重新抓取当前文档最新内容（含未保存），
    发送时刻冻结——AI 看到的必须和用户眼前一致。
14. **对话材料超限不再手搓规则**：随常驻会话由框架的上下文压缩能力承接；
    框架能力不足时的兜底思路是报错提示新建对话（产品已有该出口），
    绝不静默砍历史——AI 带着残缺记忆陪想是慢性毒药。

> 注：账本第 3、8 条中的"截断规则 / 组装耗时"属于已搁置的运输层设计
> （见事项 2），其结论随 change `provide-work-context-to-ai` 的 design.md 存档；
> 第 1、2、13 条的产品决策在重新立项时继续有效。

### 2026-09-20 补记：陪想 Agent 的存在理由（方向级）

15. **需求原点（用户原话）**："我需要一个坐在旁边陪我一起写作的助手，陪想，但不私自决策。"创作者很孤独；有一个懂自己、懂作品的家伙在，会很棒。这是产品存在的种子，来自用户自己的需要——**具体形态未定**，本条只记存在理由，不新增工作项。命名说明：「小助手」只是这幅画面的口语描述，概念名仍是「陪想 Agent」（方向共识 §8 命名表），不设第二个名字。
16. **文字的"对"是私人的（陪想的认识论基础）**：代码的"对"有公开裁判（编译器、测试），AI 能自己朝"对"走，所以 AI 编程助手可以"提议→廉价验证→接受"，大量工作可外包。文字的"对"没有编译器——"这个人物此刻会不会说这句话"只存在于作者心里，且常常说不清。AI 拿不到这个私人目标时，只能朝所有文字的统计平均值优化；"AI 味"不是模型不够好，是它没有目标的访问权。所以写作现场的最优动作是**探针**（观察、问题、可能性），不是代笔；验证信号是作者的共鸣（"对，就是它"）。"不私自决策"与四项权利由此不只是道德姿态，而是认识论必然：写作的验证器就是作者本人，外包不出去。
17. **功能判断标尺（第 16 条的推论）**：帮用户瞄准自己目标更准的功能（例："这场戏的张力卡在哪，给你三种可能的原因"）＝对的路；朝平均值替用户打磨文字的功能（例："帮我把这段改得更好"）＝死路。新功能进版本前先拿这把尺子量（AGENTS.md 绝对边界第 9 条的具体化）。
18. **人群分界与护城河**：分界不是"懂不懂技术"，是**目标是公开还是私人**。只要"一段能用的文字"的人，通用 ChatGPT 严格更好，就该用 ChatGPT；要"必须是我讲的那个人"的人，才是本产品用户。护城河不在能力层（模型是租的，平台会逐步补齐），在三层：位置（坐在写作现场、看活稿子）、立场（永不写进文档——通用助手的产品方向恰好相反，结构上不会抄）、保管（本地文件、随作品版本化）。"省时间"是梯度优势，会被平台功能逐步抹平，不作为产品论点。
19. **写作空间先立住（Cursor 对照）**：AI 编程工具 Cursor 证明了"坐在旁边看活稿子"这个位置的价值，但它的地基（VS Code）是白捡的，magic 是每天几十次的高频微反馈；写作世界没有可白捡的地基，陪想的"哇"是卡住时才有的稀疏深时刻，稀疏的 wow 撑不起使用习惯。编辑器的日常手感（打字、阅读、专注）是占住使用频率的锚，AI 时刻是深水炸弹——事项 10 因此不只是修缺陷，是产品战略的一半（排期另议，不在本条内变动）。

## 五、不变的边界（每次动手前重读）

1. AI 永远不直接改用户文档——任何版本、任何授权下都不例外。
2. AI 输出永远是临时材料，用户亲手复制、粘贴、编辑、保存才算进作品。
3. 判断权永远在用户手里：内容权、解释权、评价权、方向权。
4. 一次只开一个 change，做完归档，再开下一个。
5. 一个概念只能有一个名字。
6. UI 里能选的每个模型，后端必须真实可调用。
7. 代码写出来之前，用户必须先确认"要做什么"（propose → 确认 → apply）。
