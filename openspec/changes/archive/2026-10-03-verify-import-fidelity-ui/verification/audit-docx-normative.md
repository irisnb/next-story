## 二、符号映射审计

### 2.1 Wingdings 映射

**实现规则**

`导入器:1319–1326` 将十六进制字符码解析为整数，将 `F000–F0FF` 转为低字节后，按字体名称查表。

`导入器:1331–1359` 定义 Wingdings 映射，成功后作为正文字符输出，不计损耗（`:638–648`）。

**依据**

Alan Wood 表按 Wingdings 编码列出 Unicode 对应字符；产品规格 `:57、71–75` 要求输出对应 Unicode 字符，无法可靠映射时告知，而不是输出另一种符号。

**判定：finding（F01）**

当前映射表存在大量明确出入，不能称为“高置信对应表”。全部不一致条目如下：

| 编码 | 当前输出 | 公开表对应 Unicode |
|---|---|---|
| FC | ✓ U+2713 | ✔ U+2714 |
| FD | ✗ U+2717 | U+1F5F7，带粗叉的投票框 |
| FE | ☑ U+2611 | U+1F5F9，带粗勾的投票框 |
| 4C | 🙁 U+1F641 | ☹ U+2639 |
| A8 | ▫ U+25AB | ◻ U+25FB |
| B7 | ● U+25CF | 🕐 U+1F550 |
| CB | ◦ U+25E6 | U+1F66A，实心拼布方形装饰 |
| D8 | ○ U+25CB | U+2B9A，右向立体箭头头部 |
| E8 | → U+2192 | U+1F87A，右向宽头重箭头 |
| E9 | ↔ U+2194 | U+1F879，上向宽头重箭头 |
| EA | ↑ U+2191 | U+1F87B，下向宽头重箭头 |
| EB | ↓ U+2193 | U+1F87C，左上向宽头重箭头 |
| F2 | ⇒ U+21D2 | ⇩ U+21E9 |
| AB | « U+00AB | ★ U+2605 |
| BB | » U+00BB | 🕔 U+1F554 |
| E7 | ← U+2190 | U+1F878，左向宽头重箭头 |
| DC | ✄ U+2704 | U+2B8A，黑圆内白色右箭头 |
| C7 | ✎ U+270E | U+2BB4，左转上方的带状箭头 |
| 28 | ☎ U+260E | U+1F57F，黑色按键电话 |
| 3F | ✈ U+2708 | ✍ U+270D |

其中 B7、BB、3F、E9、EA 等不仅是字形粗细差异，而是**符号含义或方向改变**。

以下已有条目与该表一致：`4A、4B、6E、6F、71、A7`。

### 2.2 Symbol 映射

**实现规则**

`导入器:1364–1395` 直接通过匹配表输出数学符号及希腊字母。

**依据**

Adobe Symbol 表明确规定：第一列为 Unicode，第二列为 Symbol 编码。存在一对多的条目，例如 `44、57、6D`，不能误判这些合法选择。

**判定：finding（F02）**

以下五项与表明确不符：

| Symbol 编码 | 当前输出 | 表中对应字符 |
|---|---|---|
| D6 | − U+2212 | √ U+221A |
| D7 | ≡ U+2261 | ⋅ U+22C5 |
| B2 | ⊃ U+2283 | ″ U+2033 |
| A1 | ¬ U+00AC | ϒ U+03D2 |
| D1 | ∴ U+2234 | ∇ U+2207 |

这些错误字符同样不会产生 `symbol_dropped`，用户可能被告知无损耗，却得到错误正文。

其余已列数学条目及希腊字母条目与该表一致，包括 `6D→μ、44→Δ、57→Ω`，均有对应行支持。

### 2.3 未知字符与冻结样本

**实现规则**

- 无匹配项返回 `None`：`导入器:1326、1359、1394`。
- 每个无法映射的 `w:sym` 增加一次损耗：`:647`。
- 共享管线输出 `symbol_dropped` 及数量：`共享管线:281–285`。
- Wingdings `FB` 没有映射项。

**依据**

- 产品规格 `:71–75`。
- 冻结记录 §6.2.4、§6.2.7：七个符号中，只有两个虚构字体允许损耗，其余五个要求保留。

**判定：符合**

限于“无法映射的符号进入后端损耗计数和说明”这一机制。前端实际展示不在本次验证范围。

**判定：finding（F03）**

按冻结记录所列输入静态推导，`F0FB` 会额外丢失，`symbol_dropped` 应为 **3**，不是冻结预期的 **2**。

同时，冻结记录自身有依据问题：

- `冻结记录:375` 声称 `FC→U+2713` 为公开表一致结论，但上述公开表为 U+2714。
- `:376` 将 `FB` 预期限定为 U+2717 或所列替代项，而该公开表提供 U+1F5F6。
- 因此不能直接把冻结预期的近似字符补进实现，就宣布忠实解码完成。

## 三、样式覆盖审计

### 3.1 已实现的覆盖顺序与直接属性优先

**实现规则**

- 文档默认属性：`导入器:202–220`。
- `basedOn` 链根到叶：`:264–281`。
- 默认值叠加段落样式链：`:292–309`。
- 段落直接属性最后叠加：`:403–408`。
- 字符样式链后叠加 run 直接属性：`:577–608`。

实际顺序为：

```text
字符：docDefaults → 段落样式链 → 显式字符样式链 → 直接 rPr
段落：docDefaults → 段落样式链 → 直接 pPr
```

表格样式及编号层段落属性没有进入上述合并流程；表格拍平时也未传入表格样式上下文（`:369–379`）。

**依据**

产品规格 `:57、65–69`；冻结记录 §6.2.5，尤其 P06 R3 的直接字号及颜色覆盖。

**判定：符合**

限于已经读取到的普通标量属性覆盖顺序。例如 P06 R3 的直接 `sz32` 和 `FFC000` 优先于字符样式的字号、颜色。

**判定：依据不足**

不能据此声明完整符合 OOXML 样式层级。表格样式、编号样式介入及完整 §17.7.2 正文，本次尚未取得充分核对材料。

另外，Bold 规范明确指出它属于 §17.7.3 **切换属性**，而当前统一使用普通替换。冻结记录中“字符样式 `b=0` 必定关闭继承粗体”的解释，尚不能据普通覆盖顺序直接认证。需要补齐该条款全文后单独判定，不能把当前输出与冻结预期相同当作正确性证明。

### 3.2 复合属性被整块替换

**实现规则**

`导入器:798–812` 只对 `fonts` 做子字段合并；其他对象直接整体替换。

因此，默认属性：

```text
lineSpacing = { after: 120, line: 276 }
```

遇到段落样式：

```text
lineSpacing = { after: 80 }
```

后，继承的 `line` 会从合并结果消失。后续仅在存在 `line` 时输出 `lineHeight`（`:984–998`）。

**依据**

- OOXML `spacing`／`line` 属性说明：未指定的行距值沿用样式层级已有设置。
- 冻结记录 `:389–390` 恰好包含上述默认行距与只覆盖段后间距的组合。
- 产品规格 `:57` 要求继承后映射行距、段距。

**判定：finding（F04）**

修改段后间距会连带丢失继承行距，且该损失没有被对应计入 `style_degraded`。

这里需要按属性语义合并，不能简单将所有嵌套对象一律替换；也不应未经区分地给所有对象套通用递归合并。

### 3.3 中英文字体选择

**实现规则**

`导入器:761–769` 固定优先选择 `eastAsia`，其次 `ascii/hiAnsi`，没有按 run 文本的字符类别选择。

**依据**

冻结记录 §6.2.5：

- P01/P02/P16 拉丁文字预期 Calibri。
- P02 R2 中文按 `eastAsia` 使用 Microsoft YaHei。
- §6.2.7 允许的是屏幕字体替换不判失败，并非允许导入数据主动将所有文字选成同一字体。

**判定：finding（F05）**

在该默认字体配置下，拉丁文字也会被标为 Microsoft YaHei。这是数据层字体选择差异，不只是系统缺字体后的显示替换。

## 四、编号规则审计

### 4.1 同 numId 续算、不同 numId 独立

**实现规则**

- 计数器键为 `(numId, ilvl)`：`导入器:180–181`。
- 普通段落无编号时直接返回，不清除计数：`:458–459`。
- 当前编号计数累加：`:479–487`。
- 分开的列表块以当前计数写入 `orderedList.attrs.start`：`:1017–1053`。

**依据**

产品规格 `:57、77–81`；冻结记录 §6.2.6。

**判定：符合**

限于计数数值：

- numId 10 顶层依次得到 `1、2、3、4、5、6、7`。
- numId 11 独立得到 `1、2、3`。
- P14 不会因普通段落中断而回到 1。
- 切换 numId 不会清除原 numId；首次使用新 numId 则从其自身起点开始。

这里“不同 numId 重置”应理解为**不同实例独立计数**，不是每次切换实例都重新从 1 开始。

### 4.2 `lvlOverride` 与 `startOverride`

**实现规则**

`导入器:87–98` 只消费 `override_start`，忽略 `override_level`。

依赖 `docx-rs 0.4.22` 的 `LevelOverride` 已具有 `override_level` 字段；因此不能归因为依赖完全没有提供覆盖层数据。

**依据**

OOXML：

- `lvlOverride`：覆盖抽象定义中对应层的外观及行为。
- 子项 `lvl`（§17.9.6）可提供替代层定义。
- `startOverride`（§17.9.27）优先于覆盖层中的起始编号。

产品规格 `:57` 禁止输出貌似正确的错误编号。

**判定：符合**

限于正常正整数 `startOverride` 的读取及优先于抽象层起点使用。

**判定：finding（F06）**

完整 `lvl` 覆盖被静默忽略。例如抽象层从 1 开始，而实例覆盖层从 4 开始、没有单独 `startOverride`，当前仍会使用抽象层起点。

覆盖层改变编号可见性或编号类型时，也可能输出错误列表且没有降级说明。

### 4.3 `ilvl`、重启与冻结序列

**实现规则**

- 遇浅层清除所有更深层计数：`导入器:468–478`。
- 无覆盖起点时，无论 `ilvl` 是多少，均回退到 **第 0 层**起点：`:480–484`。
- `ilvl > 0` 直接降级普通段落并计数：`:489–491`。
- 索引未保存 `lvlRestart`，也没有根据该属性决定重启。

**依据**

- OOXML §17.9.11：`lvlRestart=0` 表示不重启；未指定时按前一层使用触发重启。
- 冻结记录 §6.2.6：各层都从 1 起，因此不足以暴露错误层起点问题。
- 产品规格 `:36、57` 允许无法表达的多级编号降级并告知。
- 冻结记录 `:427` 却要求不得产生编号降级。

**判定：finding（F07）**

冻结验收基准与产品范围冲突。

根据当前代码，P18、P19、P20、P21、P23 共 **5 段**会降级普通段落。这符合产品规格允许多级编号降级的规则，但不符合冻结记录要求。

不能为了通过该冻结记录，未经范围确认就扩展多级编号能力。

**判定：finding（F08）**

内部多层计数不能称为完整 OOXML 语义实现：

1. 非零层无覆盖时取错起点，使用 L0 起点。
2. 忽略显式 `lvlRestart=0` 等重启配置。

当前这些深层段落已经降级，不能把内部计数问题夸大为本样本中已观察到的错误可见编号；但该状态也不能作为未来多层渲染的正确基础。

### 4.4 编号格式丢失

**实现规则**

`导入器:70–76` 将所有非 `bullet` 类型归为有序列表；输出仅保留 `start`，没有 `numFmt` 或 `lvlText`（`:1052–1055`）。

**依据**

冻结记录 §6.2.6 要求 numId 11 为 `A、B、C`；产品规格 `:57` 要求无法表达的编号体系降级并告知，不能输出貌似正确的错误编号。

**判定：finding（F09）**

字母编号的数值顺序虽保存为 `1、2、3`，其 `upperLetter` 类型已丢失，没有相应损耗计数。相同问题还会影响罗马数字及自定义编号文本。

本次未检查前端实际标记样式，但后端输出已经无法区分原来的字母编号和普通十进制编号。

## 六、无法验证项清单

1. **完整 OOXML 样式层级**：未取得足够的 §17.7.2 正文证据，未认证表格样式、编号样式与其他层级的完整优先顺序。
2. **切换属性完整语义**：已确认粗体属于 §17.7.3，但未取得该节完整正文；样式中的 `b=0` 与重复启用的最终语义暂记依据不足。
3. **零或负数编号起点**：实现使用 `.max(1)`；本次未完成合法值范围及目标语法承载核对，不作符合结论。
4. **全部符号字体及字体变体**：仅核对当前表中的 Wingdings 与 Adobe Symbol；不认证别名、版本差异和其他符号字体。
5. **F0 前缀归一化的完整标准边界**：符合冻结样本约定，但未证明对所有字体和所有 `w:sym` 写法普遍成立。
6. **夹具字节及源 XML 本次重新校验**：本报告的样本逐段推导依赖冻结记录所列输入；未重新解包并核验其哈希。
